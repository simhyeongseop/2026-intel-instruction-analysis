## 1. 연구 질문 (1회, 7회 재확인)

> **매뉴얼에 따라 작성한 어셈블리 명령어를 현재의 어셈블러(GNU as / Clang)가 제대로 처리하는가?**

이 질문에 답하기 위해 다음을 수행했습니다:
- Intel 64/IA-32 Architecture SDM Vol.2의 모든 명령어 행(4,210개)을 데이터화
- 매뉴얼의 규칙에 따라 어셈블리 입력 생성(7,276줄)
- 어셈블러(as, Clang) → 디스어셈블러(objdump) → 재어셈블의 파이프라인 실행
- 일부 입력은 CPU에서 직접 실행하여 동작 확인

### 3.2 발견된 이슈

#### ✅ **확정된 도구 결함 (1개, 3건의 동일 증상)**

**LSS/LFS/LGS 불완전한 표시 (objdump)**

- **문제:** objdump(Intel 문법)가 REX.W 형식(TBYTE, 80비트)을 FWORD(48비트)로 잘못 표시
- **사례:** 
  ```
  바이트: 48 0f b2 08
  objdump 출력: lss rcx,FWORD PTR [rax]  ← 틀림
  매뉴얼: LSS r64, m80 (TBYTE 사용 필요)
  재어셈블: 거부됨 ❌
  ```
- **도구:** GNU Binutils 2.42 ~ 2.47 **모두** 동일하게 재현
- **llvm-objdump:** 동일 바이트에서 올바르게 표시 → **objdump의 버그**
- **상태:** **확정**, 이후 binutils 보고 검토 예정

#### ⚙️ **지원 차이 (버그 아님)**

**UDB 명령어**

- **보고:** as가 "no such instruction" 거부
- **재현:**
  - binutils 2.42, 2.44, 2.45: 거부 ✘
  - **binutils 2.46, 2.47: 지원함** ✅
- **매뉴얼:** Intel 64-bit SDM p.1436에 `D6 UDB`로 정식 정의 (Valid in 64-bit mode)
- **결론:** 새 명령어를 지원하지 않는 구버전의 한계 → **버그가 아님**

#### ❓ **판단 보류 사항 (이전 재심, 발표에서 언급 필요)**

1. **MOV Sreg, r/m64 (메모리형):** 페이지 경계 CPU 실험 후 구현 버그 아님으로 재분류
2. **LAR/LSL 비대칭 폭:** 재심 후 매뉴얼 정확성 확인 ← 그대로 유지
3. **VSCATTERDPD vm32y/vm32z:** 매뉴얼 표기 문제 가능성
4. **SYSEXIT/SYSRET:** as의 오퍼랜드 크기 결정 방식 특이

## 4. 입력 생성 오류 분석 (우리 탓, 약 40~50건)

56건의 거부된 입력 중 약 40건이 생성기 결함:

| 원인 | 건수 | 예시 |
|------|------|------|
| 매뉴얼의 표기 `k1+1`, `zmm2+3` 을 그대로 넣음 (덧셈으로 해석됨) | 18 | `vpaddd xmm0, xmm0, xmm0{k1+1}` |
| 크기 고정 m512에 `zmmword ptr` 붙임 (as는 엄격, clang은 관대) | 10 | `fxsave zmmword ptr [rax]` |
| 암묵 오퍼랜드를 명시로 넣음 | 7 | `rep lods al` 에서 `<EAX>` 명시 |
| 표기 관례를 그대로 옮김 (e.g. `rep lods al`) | 4 | — |
| 추출기 오류: 문자열 `imm8/r` 그대로 포함 | 2 | — |
| 레지스터 모드·폭 제약 미반영 | 2+1 | `senduipi ecx`, `umonitor cx` |

**영향:** 이 오류들을 고쳐야 결과의 신뢰도가 높아집니다.

## 5. 검증 과정에서 드러난 한계

생성기가 교수님 요청(4~5회)을 완전히 구현하지 않음:

| 요청 | 현재 구현 | 차이 |
|------|----------|------|
| 메모리 addressing 다양화 | `[eax]` 3,461개, **rip-relative 0개** | 0x67 프리픽스 처리의 어려움 |
| 즉시값: 최대값(16진수) | imm8 거의 모두 `1`, imm16/32는 `0x100`/`0x10000` | 고정 대표값만 생성 |
| 행마다 약 10번 랜덤 생성 | **행마다 1~2개의 고정값** | 단순화된 구현 |
| 오퍼랜드 다양화 (7회) | 동일 오퍼랜드 **2,161줄** (`xmm0, xmm0, xmm0`) | 순서 오류 감지 불가능 |
| AVX-512 마스크/브로드캐스트 활용 | 1,640행 중 실제 `{k1}` 사용은 **64줄** | 고급 기능 미활용 |

**예시:** `ADD r32, r/m32` 행  
- 의도한 인코딩: `03 /r` (reg-to-r/m)
- 생성된 입력: `add ecx, ecx`
- as 출력: `01 c9` ← **다른 인코딩**
- 결론: **의도한 인코딩이 실제로 테스트되지 않음**

## 7. 도구 시연: asm_linter

**목적:** 한 줄의 어셈블리 입력에서 다음을 빠르게 검증
- 수용 여부 (as vs clang)
- 생성되는 바이트 코드
- 거부 원인 (있다면)

**사용 예:**
```bash
$ python asm_linter.py "add ecx, ecx"
┌─────────────────────────────────────────┐
│ Instruction: add ecx, ecx              │
├─────────────────────────────────────────┤
│ GNU as:      ✅ 01 c9                  │
│ Clang:       ✅ 01 c9                  │
│ Match:       ✅ Yes                    │
│ Objdump:     add %ecx, %ecx            │
└─────────────────────────────────────────┘
```

**중요 기록:** 도구가 제시하는 판단(수용/거부)은 우리가 정한 것이라 완전히 객관적이지 않습니다.

## 10. 기술 용어 정리 (발표 시 참고)

| 용어 | 뜻 |
|------|-----|
| **REX.W** | 64비트 레지스터 지시자 (0x48 프리픽스의 W 비트) |
| **FWORD** | 매뉴얼의 48비트 세 워드 (objdump 오표시) |
| **TBYTE** | 80비트 열 개 바이트 (80-bit extended float) |
| **차등 테스트** | 여러 도구/버전 결과 비교 (differential testing) |
| **m512** | 512바이트 메모리 피연산자 (AVX-512) |
| **암묵 오퍼랜드** | 명시 없이 암암리에 사용되는 레지스터 (예: REP LODS는 `<EAX>` 자동 사용) |
