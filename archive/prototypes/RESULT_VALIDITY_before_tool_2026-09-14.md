# 결과의 유효 범위와 버그 판정 기준

정리일: 2026-09-14. 대상: 커밋 `d64b2d3` 및 현재 작업 폴더에 저장된 결과.

이 문서는 현재 결과를 보고할 때 적용하는 기준이다. 기존 CSV의 `verdict`는 당시 분류 기록이며, 아래 기준에 따른 최종 확정 상태와 동일하지 않다. 이번 작업은 저장된 CSV의 재집계와 코드·기록 대조다. CPU 실험, 전체 파이프라인, SDM 원문의 개별 사안 재검증을 새로 수행한 것은 아니다.

## 1. 연구 질문과 기준의 역할

연구 질문은 **“인텔 매뉴얼의 명령어 형식을 구체적인 소스로 옮겼을 때, 지정한 도구·옵션에서 어떤 지원 차이나 잘못된 처리가 발생하는가?”**이다.

판정에는 세 기준을 구분해서 사용한다.

| 기준 | 판단하는 것 | 이것만으로 판단할 수 없는 것 |
|---|---|---|
| Intel SDM의 Opcode, Description, Operation, Exceptions, 각주 | 해당 모드·기능 조건에서 기계어가 뜻하는 동작과 제약 | 특정 버전의 GNU as가 모든 SDM 표기를 그대로 입력 문법으로 지원할 의무 |
| 대상 도구의 문서·지원 범위·옵션 | 입력 문법, ISA 선택, 인코딩 선택 정책, 출력 표기의 의미 | 실제 생성 바이트가 SDM에 맞는지 |
| 실제 소스·바이트·출력·실행 기록 | 해당 환경과 입력에서 관측된 사실 | 다른 버전·CPU·모든 오퍼랜드 조합에서의 일반적 동작 |

**ISA 동작의 기준은 SDM이고, 도구 문법 지원의 기준은 해당 도구의 계약이다.** SDM 표 한 행과 도구 출력의 차이를 발견하면 연구 결과로 기록하되, 그 차이가 곧 구현 버그라는 결론으로 이어지지는 않는다. SDM 내부가 상충하면 표뿐 아니라 본문·Operation·각주를 대조하고, 해결되지 않으면 보류한다.

GNU as는 `.intel_syntax`와 크기 지시자의 의미를 문서화한다. 예를 들어 `fword ptr`와 `tbyte ptr`는 각각 48비트와 80비트 메모리 참조를 가리킨다. 이는 크기 표기가 단순한 장식인지 판단할 때 사용할 도구 측 근거다. [GNU as 문법 문서](https://sourceware.org/binutils/docs/as/i386_002dVariations.html)

ISA 선택과 문법 선택도 구분한다. `--64`, `-mintel64`, `.intel_syntax noprefix`는 같은 설정이 아니다. 옵션에 따른 지원 차이는 동일 옵션 조건으로 맞춰 비교한다. 최신 온라인 문서는 기준 정리에 참고했으며, 과거 바이너리의 동작을 입증하는 자료로 소급 적용하지 않는다. [GNU as 옵션 문서](https://sourceware.org/binutils/docs/as/i386_002dOptions.html)

## 2. 현재 실험이 다룬 범위

| 축 | 실제 범위 | 미검증 또는 제한 |
|---|---|---|
| 매뉴얼 | 로컬 `intel_manual.pdf`에서 추출한 DB 4,210행 | 다른 SDM 개정판, ISA 전체의 완전한 추출·의미 검증 |
| 문법·모드 | Intel syntax, x86-64 타깃; GNU as `--64 -mintel64` | AT&T 전체 비교, 16/32비트 실행 모드, 옵션 전 조합 |
| 어셈블러 | 기본 배치 GNU as와 Clang; 일부 사례에 추가 버전 비교 기록 | 모든 사례를 모든 버전에서 교차 검증한 것은 아님 |
| 입력 | 각 조합을 별도 파일의 한 명령어로 처리; 공통 헤더와 `.Ltarget` 사용 | 일반 프로그램 전체의 링크·제어 흐름·ABI 정확성 |
| 오퍼랜드 | 대표 레지스터·메모리·즉시값; `r/m` 대안 등을 전개 | 전체 레지스터 조합, 경계값, 모든 주소 방식·마스크·별칭 제약 |
| 인코딩 | 성공 여부, objdump 텍스트, 두 어셈블러 바이트, 재어셈블 바이트 | 모든 성공 사례의 실제 opcode 행·REX/VEX/EVEX·ModRM 의미 독립 검증 |
| 실행 | 고정주소 ELF의 손설계 6개 시나리오 + 자동 선별 19개 사례 | 모든 7,276개 테스트의 실행 의미, 모든 CPU 기능·OS 상태 |

환경 기록상 기본 도구는 GNU as/binutils 2.42, Clang 18.1.3이며 일부 재검토에 19/20 및 binutils 2.47 기록이 있다. **결과 CSV에는 행별 바이너리 버전·해시와 실행 환경이 완전히 기록돼 있지 않다.** 이 문서에서 최신 버전에서도 동일하다고 주장하지 않는다. 정확한 버전별 주장은 해당 사례의 재현 기록이 있는 범위로 한정한다.

현재 `run.py`는 11단계까지만 등록돼 있다. 12단계 모듈과 저장된 산출물의 존재를 “전체 실행기 한 번으로 12단계가 모두 재현된다”는 뜻으로 설명하지 않는다.

## 3. 수치와 그 수치가 입증하는 것

아래 수치는 2026-09-14에 CSV를 다시 읽어 확인했다. 같은 소스라도 다른 DB 행에서 생성될 수 있으므로 행·테스트·고유 소스·결함 유형을 구분한다.

| 수치 | 유효한 해석 | 피해야 할 해석 |
|---|---|---|
| DB 4,210행 → 조합 7,277행 | DB의 4,210개 `row_id` 모두에 조합이 있음 | 인텔 ISA 전체 또는 모든 실제 인코딩을 100% 검증 |
| 생성 테스트 7,276개, 포함 DB 행 4,209개 | 조합에서 한 건을 제외해 어셈블 입력을 생성 | 4,210행 전부를 실제로 어셈블 검사 |
| 고유 `asm_line` 문자열 6,024개 | 같은 소스가 여러 테스트 행에 반복됨 | 독립적인 서로 다른 소스 7,276개 |
| as 성공 7,162 / 실패 114 | 해당 입력과 옵션에서의 수용 여부 | 성공=정확한 의미, 실패=버그 |
| 텍스트 same 5,706 / different 1,456 | 원본과 objdump의 정규화된 텍스트 비교 | same=SDM 적합, different=결함 |
| as·Clang 바이트 동일 7,058 | 두 구현이 해당 입력에 동일한 바이트를 생성 | SDM의 의도한 행과 일치하거나 모든 CPU에서 정상 실행 |
| 재어셈블 바이트 동일 1,326 | 해당 경로에서 바이트가 보존됨 | 원본 소스의 의도까지 증명, 오탐 판정 1,326개를 모두 확정 |
| triage 1,585행 | 컴파일 에러·예상과의 불일치·텍스트 차이의 합집합, combo 중복 제거 | 전체 테스트 수, 서로 독립인 버그 수 |

생성 제외는 `ENCODEKEY256`의 `row_id=570`, `combo_id=1028` 한 건이다. [제외 기록](../out/generator_skipped.csv)

### 예상 성공 여부와 실제 성공 여부

`expected_valid`는 추출한 행의 모드 표기를 생성기가 전달한 값이다. 오퍼랜드 제약·CPUID·실제 선택된 인코딩까지 검증한 정답 레이블이 아니다.

| 생성기의 expected_valid | as 성공 | as 실패 |
|---|---:|---:|
| True | 7,110 | 56 |
| False | 52 | 58 |

따라서 예상과 다른 108개(56+52)는 **조사 대상**이다. 도구의 오수용·오거부율로 바로 계산하지 않는다. 114개 실패에는 예상대로 거부된 58개도 들어 있다.

### 바이트 동일성의 한계: 실제 교차 집계

재어셈블 바이트 동일 1,326개를 `combo_id`로 기존 triage에 연결하면 **false_alarm 1,313개 + unsure 13개**다. 13개를 자동으로 false_alarm으로 내리지 않는다. 이미 잘못 생성된 바이트가 왕복 과정에서 그대로 보존될 수도 있고, 소스에서 요구한 폭을 처음부터 보존하지 않았을 수도 있다.

바이트 차이 5개도 결함 5개라는 뜻은 아니다. 기존 증거에는 PREFETCHIT0/1 두 사례의 오탐 철회와 TILE 계열 세 사례의 추가 변위 인코딩 관찰이 있다. 이때 주소가 같다는 확인만으로 성능·명령어 길이·모든 실행 상태까지 동일하다고 확대하지 않는다. 상대 타깃 재배치 한계 99개, 재어셈블 실패 26개도 각각 원인을 따져야 한다. [재어셈블 결과](../out/reassemble_check.csv), [개별 근거](../out/reassemble_check_evidence.md)

## 4. 버그의 정의와 분류

이 프로젝트에서 **도구 버그**는 “입력과 실행 조건을 명시했을 때, 도구가 지원한다고 하는 동작 또는 출력의 의미를 위반하며, 매뉴얼·입력 생성·관측 방법의 오류로 설명되지 않는 재현 가능한 결함”으로 정의한다.

**CPU 실행 결과가 달라져야만 버그인 것은 아니다.** 잘못된 기계어 생성과 잘못된 역어셈블 표시는 각각 해당 도구의 기능 결함이 될 수 있다. 다만 그 영향과 집계는 분리한다.

| 유형 | 확정에 필요한 핵심 근거 | 그 자체로는 불충분한 관찰 |
|---|---|---|
| `encoding_defect` 인코딩 결함 | 유효하고 의미가 명확한 소스가 허용되지 않는 다른 동작의 바이트로 변환됨; 필드 해독과 SDM 대조 | as와 Clang의 바이트 차이, 한쪽 접두어 생략 |
| `syntax_defect` 문법 처리 결함 | 해당 버전·옵션에서 지원하는 유효 문법을 잘못 거부하거나, 진단해야 할 입력을 잘못 처리한다는 근거 | SDM 표기를 그대로 붙였더니 거부됨; Invalid 행인데 어셈블 성공 |
| `disassembly_defect` 해독·표시 결함 | 모드·옵션을 맞춘 실제 바이트의 폭·레지스터·타깃·명령어 의미와 출력이 모순됨 | 원본과 텍스트 다름, 재어셈블 실패만 관찰 |
| `support_gap` 지원 차이 | 매뉴얼상 형식/니모닉이 해당 도구에서 지원되지 않음 | 미지원 사실만으로 구현 버그 확정 |
| `equivalent_representation` 동등 표현 | 적용 조건 내에서 별칭·표기·복수의 유효 인코딩으로 차이가 설명됨 | 단순 바이트 차이를 무시하거나 의미를 추측 |
| `test_or_measurement_issue` 테스트·관측 문제 | 추출 오류, 잘못된 오퍼랜드, 다른 opcode 행 선택, 링크 문맥 소실 등 | 도구 버그로 합산 |
| `spec_ambiguity` 명세 해석 문제 | SDM 표·본문·각주 사이 충돌 또는 실제 의미 미확정 | 다른 어셈블러 다수결로 확정 |
| `environment_condition` 환경 조건 | CPU 기능, 권한, 메모리 매핑, OS 활성화 조건으로 결과가 설명됨 | SIGSEGV/SIGILL/exit0만으로 도구 버그 확정 |

`support_gap`은 유용한 연구 결과이며, 기존에 지원하던 기능의 회귀나 명시적인 지원 약속 위반이 입증되면 `syntax_defect`로 승격할 수 있다. 알려진 제한인지, 새 결함인지도 따로 기록한다. 유지보수자의 확인은 강한 추가 근거지만 논리적으로 충분한 재현을 대신하거나 반드시 필요한 조건은 아니다.

### 역어셈블과 왕복 검증

GNU objdump 문서는 디스어셈블 모드와 출력 옵션을 제공한다. 본 연구는 그 문서를 근거로 **모든 출력이 원본 소스로 복원되거나, 그대로 재어셈블 가능하다고 가정하지 않는다.** 라벨·재배치·메타데이터 문맥을 복원하지 않은 왕복 실패는 먼저 검사 방법의 한계로 분리한다. [GNU objdump 문서](https://sourceware.org/binutils/docs/binutils/objdump.html)

반대로 실제 바이트가 나타내는 80비트 포인터를 48비트 크기 표기로 보여준다는 식의 모순이 입증되면 표시 결함으로 보고할 수 있다. 이미 생성된 기계어의 CPU 실행을 바꾸지는 않더라도 사용자의 해독을 오도한다. 왕복 실패는 이때의 추가 영향 증거이며 유일한 판정 근거가 아니다.

### 인코딩과 실행 검증

소스가 하나의 의미를 명확히 요구하는데 바이트 해독 결과가 그 의미와 다르다면, 정적 대조만으로도 인코딩 결함을 입증할 수 있다. 모든 명령어를 CPU에서 실행해야 하는 것은 아니다. 반대로 메모리 접근 폭처럼 정적 근거가 모호한 사안은 페이지 경계 등 가설을 구분하는 실험이 필요할 수 있다.

실행할 때에는 입력 레지스터·메모리·권한·CPU/OS 기능을 함께 기록한다. 종료 시그널만으로 정확한 예외 원인이나 어느 명령어에서 실패했는지 단정하지 않는다. 정상 종료만으로 결과 레지스터·메모리·플래그까지 맞았다고 주장하지 않는다. 정의된 예외를 의도적으로 발생시키는 명령어의 예외 발생도 정상 동작일 수 있다.

## 5. 확정 수준은 유형과 별도로 기록한다

| 상태 | 의미 |
|---|---|
| 관측됨 | 입력·출력·바이트 등 차이는 기록됐지만 원인은 미결 |
| 근거 있음·재심 중 | 원인 설명을 지지하는 증거가 있으나 제기된 반론 또는 재현 조건 정리가 미완료 |
| 확정 | 아래 근거 항목이 갖춰졌고, 남은 핵심 반론이 해소됨 |
| 기각 | 처음 주장한 도구 결함이 다른 원인으로 설명됨; 새 후보까지 일괄 기각하는 것은 아님 |

확정 사례에는 다음을 남긴다.

1. 사례 ID, **주장의 정확한 문장**, 도구·결함 유형, 적용 버전과 옵션.
2. PDF 개정/해시, 페이지와 Opcode·Description·Operation·각주 근거; 관련 도구 문서.
3. 완전한 최소 소스, 명령행, 종료코드, 표준 출력·에러, 원본 바이트와 재배치 정보.
4. 의도한 SDM 행과 실제 인코딩 행의 대응. 접두어·ModRM 등 쟁점 필드 해독.
5. 별칭·유효한 대체 인코딩·도구 옵션·명세 오류·생성기 오류라는 반대 설명의 검토.
6. 실행을 근거로 삼았다면 CPU/OS 기능·초기 상태·관측 위치·기대 결과·실제 결과.
7. 영향, 우회 방법, 미검증 범위, 재현 확인일. 다른 구현/버전의 결과는 보조 근거로 별도 표기.

`row_id`와 `combo_id`는 이 데이터 스냅샷 내부 키다. 재생성 후에도 같은 사례라고 추적하려면 원본 명령어·opcode·소스 페이지와 실제 소스/바이트를 함께 보존한다.

## 7. 보고 문구와 집계 원칙

현재 보고서에는 다음 문구를 사용한다.

> 추출 DB 4,210행에서 7,277개 조합을 만들고, 4,209개 DB 행에 해당하는 7,276개 테스트를 어셈블했다. 이 중 고유 소스 문자열은 6,024개다. GNU as는 7,162개를 수용했고, Clang과의 비교에서는 7,058개의 기계어 바이트가 같았다. 기존 triage에는 bug 4행, false_alarm 1,557행, unsure 24행이 기록돼 있다. bug 4행은 현재 표시 결함 한 유형의 세 사례와 니모닉 미지원 한 사례로 나눠 보고하며, 새 기준에 따른 최종 확정 버그 수는 아직 산정하지 않는다. 이 결과는 해당 데이터·도구·옵션에서의 관측이며 ISA 전체의 정확성을 입증하지 않는다.

- **사례 수**, **결함 유형 수**, **확정된 근본 원인 수**를 따로 센다. 같은 문제가 세 니모닉에 발생해도 독립 버그 세 개라고 단정하지 않는다.
- `false_alarm`은 당시의 **대상 도구 버그 주장**이 기각됐다는 뜻이다. 생성기 오류나 지원 차이까지 없어졌다는 뜻이 아니다.
- 새 기준으로 전량 재분류하지 않았으므로 새 확정 수를 4 또는 0이라고 쓰지 않는다. “아직 산정하지 않음”으로 표기한다.
- 같은 결과를 여러 단계에서 관찰한 수치를 더해 독립 증거 개수나 버그 수로 만들지 않는다.
- 표·본문·개발 기록이 충돌하면 날짜와 원시 결과를 대조한다. 과거 보고서의 “확정” 문구보다 이 문서의 현재 보고 기준을 적용한다.

## 8. 후속 작업의 완료 조건

1. **개별 재심 종료:** LSS/LFS/LGS, MOV Sreg, UDB에 대해 `spec.md`의 반론과 이 문서의 지원 계약 구분을 함께 해결하고 사례별 근거를 남긴다.
2. **인코딩 후보 분리:** LAR/LSL의 명확한 r64 소스를 별도 사례로 만들고, 원래 false_alarm 사례와 다른 주장임을 명시한다.
3. **판정 데이터 반영:** 사례별 근거가 갖춰지면 유형·확정 수준·영향을 반영할 필드를 설계한다. 기존 `category/verdict`와 변경 이력을 보존하고 triage·린터·보고서를 함께 갱신한다. 이번에는 기존 데이터 스키마와 판정을 그대로 두었다.
4. **커버리지 개선:** DB 행에 조합을 만드는 비율과 실제 의도한 인코딩 행을 검사한 비율을 별도 산출한다. 아직 없는 후자 수치를 100%로 보고하지 않는다.
5. **재현 기록 개선:** 실행별 도구 버전/해시·명령행·PDF와 입력 해시·CPU/OS 조건·결과를 묶어 보존한다.
