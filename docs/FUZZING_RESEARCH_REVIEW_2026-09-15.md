## 1. 종합 평가

**현재 프로젝트는 명령어 입력과 도구 간 차이를 조사하는 연구용 프로토타입으로 가치가 있다. 그러나 다른 퍼징 실험에서 입력을 자동으로 통과·탈락시키는 최종 판정기로 사용하기에는 아직 부족하다.**

가장 큰 성과는 명령어 수를 늘린 것보다, 원본 문장·의도한 매뉴얼 행·생성 바이트·역어셈블 표기·CPU 관측을 구분하기 시작한 점이다. 과거 버그 주장을 실제 바이트와 대조 실험으로 정정한 과정도 연구 성과다. 특히 MOV Sreg의 페이지 경계 대조 실험은 경쟁하는 설명을 구분할 수 있도록 설계되어 있다.

가장 큰 약점은 이 구분이 문서에는 있지만 **실제 API 상태와 자동 성공 판정에 일관되게 구현되지 않았다는 것**이다. 이번 검토에서는 어셈블러 비정상 종료의 일반 거부 처리, 지정 인코딩 불일치가 반영되지 않는 배치 상태, 검사 실패가 누락되는 배치 성공 판정을 확인했다. 따라서 현재 `accepted`나 `ALL SELECTED TESTS PASSED`만으로 후속 연구의 입력 정확성을 보증하면 안 된다.

| 사용 목적 | 현재 평가 | 이유 |
|---|---|---|
| 사람이 사례를 조사하고 원시 결과를 모으기 | 사용 가능 | 바이트·명령행·stderr·환경 기록이 유용함 |
| 퍼징 결과의 사후 분류·주석 달기 | 조건부 사용 가능 | 원시 입력을 보존하고 미확인 결과를 별도 보관해야 함 |
| 퍼징 입력의 자동 통과·폐기 결정 | 보완 필요 | 서로 다른 실패와 검사 범위가 하나의 상태에 섞임 |
| 특정 SDM 인코딩 행을 시험했다는 판정 | 보완 필요 | 다른 유효 인코딩으로 조립되는 경우와 미검사 필드가 많음 |
| 여러 명령어로 된 프로그램의 정확성·실행 가능성 판정 | 현재 범위 밖 | 각 줄을 독립 검사하며 상태·제어 흐름·링크 문맥을 연결하지 않음 |
| 새 퍼징 기법의 효과 또는 보안 취약점 발견을 입증 | 근거 부족 | 실제 퍼징 대상에 대한 비교 실험·검출률·근본 원인별 버그 검증이 없음 |

이 평가는 “연구를 중단해야 한다”는 뜻이 아니다. **다음 개발의 중심을 파일 정리와 사례 추가에서 판정 신뢰성 및 실제 퍼징 기여도 검증으로 옮겨야 한다는 뜻이다.**

## 2. 검토 방법과 근거의 범위

이번에는 공통 검사 API, 오퍼랜드·opcode 비교, 생성기, 7·11·12·13단계, CLI, Ubuntu 실행기, 재심 코드와 회귀 테스트를 읽었다. 저장된 CSV를 다시 집계하고 Ubuntu의 GNU as 2.42·Clang 18.1.3으로 소수의 소스만 조립했다. 외부 도구 실패는 `unittest.mock`으로 주입해 판정 전달 경로를 확인했다.

**실제 GNU/LLVM 크래시를 새로 발견한 것은 아니다.** 아래의 SIGSEGV·SIGABRT와 전량 검사 실패 사례는 검사기의 보고 동작을 확인하는 인위적 대조 실험이다. 입력 기계어를 CPU에서 실행하지 않았고, 기존 실험 산출물을 덮어쓰지 않았다. 전체 PDF 재추출, 모든 기존 판정 재심, 최신 upstream에서의 버그 존속 확인도 이번 검토에 포함하지 않았다.

본문의 근거 표시는 다음 의미다.

- **실측:** 이번 Ubuntu 소규모 조립으로 확인.
- **재집계:** 현재 저장된 데이터에서 계산.
- **실패 주입:** 의도적으로 만든 도구 결과를 현재 코드에 전달해 확인.
- **코드 검토:** 구현 경로에서 확인했지만 해당 실패를 실제 대상에서 유발하지 않음.
- **제안:** 앞으로 검증할 설계·실험이며 현재 구현의 성과가 아님.

## 3. 연구 과정에서 잘한 점과 되풀이된 문제

### 3.1 유지해야 할 성과

1. **매뉴얼 행을 추적할 수 있는 입력 생성:** PDF→DB→조합→소스의 관계가 있어서 무작위 문장을 수집하는 것보다 원인을 좁히기 쉽다.
2. **오탐의 정정:** CALL/JMP의 near/far 구분, VPMOVQD 표기 문제, MOV Sreg와 LAR/LSL 재심은 “차이가 있다”에서 “어느 가정이 틀렸는가”로 발전한 사례다.
3. **원시 바이트 보존:** 새 검사기는 `objcopy`로 `.text` 전체를 추출하고 디스어셈블 결과의 연속성도 확인한다. 긴 명령어의 첫 줄만 비교하는 오류를 피했다.
4. **문맥 의존성의 일부 표시:** 재배치·분기, 모드 변경과 매크로 등에 제한을 명시했다. 조립 성공을 바로 실행 성공이라고 보고하지 않는 방향은 맞다.
5. **구별 가능한 CPU 대조군:** MOV Sreg에서 1·2·8바이트 경계와 일반 64비트 MOV 대조군을 두고, LAR에서는 정의되지 않은 결과 비트를 비교에서 제외했다. 단순한 정상 종료 횟수보다 설명력이 높다.
6. **이력 보존:** 기존 판정과 파일을 `legacy_*` 및 `archive/`에 남겨 결론이 바뀐 이유를 추적할 수 있다.

근거: [재심 보고서](CASE_REVIEW_2026-09-14.md), [CPU 재심 소스](../tests/review_cpu_cases.c), [기록 보관 안내](../archive/README.md).

### 3.2 아직 남은 방법론적 문제

[5회 회의록](MEETING_NOTES/5회_미팅_내용.md)은 규칙 안에서 다양한 값을 생성하는 실험을, [7회 회의록](MEETING_NOTES/7회_미팅_내용.md)은 표현 차이와 실제 오류의 구분을 강조한다. 현행 생성기는 규칙 기반 구조는 갖췄지만 주로 대표값을 고정해서 사용한다. 도구는 여러 관측을 수집하지만 그 관측을 후속 연구의 선택 정책으로 연결하는 부분이 미완성이다.

따라서 교수님의 과거 피드백을 문서로부터 해석하면, 부족했던 것은 단순히 “테스트를 더 많이 실행하지 않아서”라기보다 **어떤 규칙을 시험했고, 실제로 그 규칙이 시험되었으며, 무엇을 근거로 오류라고 판정하는지의 연결**로 보인다. 이는 회의록에 근거한 해석이며 교수님의 현재 의도를 단정하는 설명은 아니다.

현재 직접 시험하는 것은 GNU `as`와 Clang의 어셈블러 경로다. C/C++ 최적화 컴파일러 전체를 시험한 것으로 범위를 확대해서 설명하지 말아야 한다.

## 5. 구체적 결함과 보완 사항

P0는 후속 퍼징에서 자동 판정을 사용하기 전에 해결할 항목, P1은 연구 효과를 주장하기 전에 해결할 항목, P2는 그 이후의 확장이다. 보안 취약점 등급이나 CVSS 점수가 아니다.

### R1. P0 — 어셈블러 비정상 종료가 일반 거부로 분류됨

**근거: 실패 주입 + 코드 검토.** [instruction_check.py](../pipeline/instruction_check.py)의 `assemble()`은 `run['failure']`가 없으면 0 이외의 반환값을 모두 `rejected`로 만든다. `command()`는 프로세스가 신호로 종료되어도 `failure=None`을 반환한다. POSIX에서 음수 반환값이 신호 종료를 의미한다는 점은 [Python subprocess 문서](https://docs.python.org/3/library/subprocess.html#subprocess.CompletedProcess.returncode)에 정의되어 있다.

| 주입한 GNU as 반환값 | 의미 | 현재 최종 상태 |
|---|---|---|
| `-11` | SIGSEGV 종료 | `rejected` |
| `-6` | SIGABRT 종료 | `rejected` |
| `1` + 문법 오류 진단 | 일반적인 입력 거부 | `rejected` |

원시 반환값은 남지만 요약 상태에서 구분되지 않는다. 후속 퍼저가 `rejected`를 버리면 중요한 크래시 입력을 놓칠 수 있다. `SIGKILL`이나 자원 부족처럼 외부 환경에 의한 종료도 있으므로 신호 종료를 곧바로 버그 확정으로 처리하는 것 역시 부적절하다.

**보완:** `accepted`, `diagnostic_rejection`, `process_crash`, `timeout`, `unavailable`, `resource_failure`, `inspection_failure`를 관측 계층에서 분리한다. 크래시·타임아웃에는 원본 입력, 종료 신호, 도구 버전, stderr, 재현 횟수를 보존한다. sanitizer와 컴파일러 내부 오류도 일반적인 문법 진단과 구분한다.

**완료 기준:** 정상 거부, 신호 종료, timeout, 실행 파일 부재를 주입했을 때 서로 다른 상태와 저장 경로로 전달되어야 한다. 크래시·timeout 입력은 일반 거부 필터로 폐기되지 않아야 한다.

### R2. P0 — 일괄 검사에서 지정 인코딩 불일치가 최종 상태에 반영되지 않음

**근거: 재집계 + 실측.** [m13_lint.py](../pipeline/m13_lint.py)는 `check_instruction(code, rows)`로 결과를 얻은 후 별도로 `check_opcode_template()`를 호출한다. 이때 별도 결과를 최종 `status`에 합치지 않는다. 반면 API에 `expected_row`를 직접 전달하면 불일치가 `needs_review`에 반영된다.

실제 예시는 다음과 같다.

```text
case_id:          combo_74
row_id:           44
입력:             add ecx, ecx
지정 opcode:      03 /r
GNU/Clang 바이트: 01 c9
기존 batch status: accepted
opcode_fields:     different_encoding
expected_row를 전달한 API status: needs_review
```

두 인코딩은 이 입력에서 정상적인 다른 인코딩 선택일 수 있다. 이번 발견은 **ADD를 잘못 실행한다는 주장이 아니라, 지정했던 인코딩을 시험하지 않았다는 사실이 자동 판정에서 약해진다는 문제**다. 이와 같은 배치 행이 118개다.

**보완:** 바이트 관측은 소스 기준으로 캐시하되, 지정 행과 비교하는 판정은 `(소스, 매뉴얼 버전, 기대 행, 검사 정책)`마다 수행한다. `representation_match`와 `encoding_target_match`를 구분하고 CLI·배치·Python API가 같은 최종 결정을 내리도록 한다.

**완료 기준:** 같은 입력·기대 행·정책을 주었을 때 세 진입점의 판정이 같아야 한다. 위 118건은 정상 동작 가능성을 유지하면서도 `target_encoding_not_exercised` 등으로 명시해야 한다.

### R3. P0 — 검사 도구의 실패가 배치 성공에서 누락됨

**근거: 실패 주입 + 코드 검토.** `m13_lint.py`의 `tool_error`는 GNU/Clang의 조립 상태만 확인한다. 조립 후 `objdump`·`objcopy`·`readelf` 검사나 왕복 검사 실패가 최종 `incomplete`로 전달되어도 배치 실패에 합산되지 않을 수 있다.

이번 감사에서는 정상 관측을 바탕으로 GNU/Clang의 역어셈블 검사 실패를 주입하고 임시 디렉터리에서 배치를 실행했다.

```text
status_counts: {"incomplete": 7283}
manifest.tool_error: false
m13_lint 종료 코드: 0
현재 run_ubuntu_tests.sh의 lint manifest 검사 조건: 통과
```

이 실험은 기존 7,283개 결과가 실제로 모두 실패했다는 뜻이 아니다. **현재 성공 검사 조건이 이 정도의 인프라 실패도 탐지하지 못함을 보여준다.** 알려진 미지원 입력을 배치에 허용하는 것은 가능하지만, 실행 도구의 장애와는 구분해야 한다.

추가로 `option_comparison`에서 `as --64` 조립은 성공하되 역어셈블 검사가 실패하도록 주입했을 때 최종 상태는 `accepted`로 남았다. `command()`의 timeout 처리도 예외에 들어 있던 부분 stdout/stderr를 버린다.

**보완:** 모든 필수 하위 검사에 대해 완료 여부와 실패 이유를 집계한다. `unsupported`와 `tool_failed`를 분리하고, 필수 도구 실패는 배치 비정상 종료로 연결한다. 옵션 비교가 선택 사항이면 선택적 미완료 사실을 별도 기록한다. timeout의 부분 출력도 보존한다.

**완료 기준:** 각 하위 도구 실패를 하나씩 주입하는 검증을 통과해야 한다. 전량 역어셈블 실패 배치는 실패로 종료하고, 알려진 미지원 사례를 포함한 정상 수집 배치는 지정한 정책에 따라 성공할 수 있어야 한다.

### R4. P1 — 테스트 실행 성공과 연구 가설 검증 성공이 섞여 있음

**근거: 코드 검토.** [review_cases.py](../scripts/review_cases.py)의 27개 조립 사례는 결과 수집과 도구 오류 여부를 확인한다. 각 소스의 예상 수용 여부·바이트·표시 결함이 여전히 재현되는지를 대조하는 기대값 검사는 아니다. 반면 20개 CPU 사례는 C 코드 안에서 기대 조건을 검사한다. 이 두 숫자를 같은 의미의 “사례 통과”로 표현하면 안 된다.

[12단계](../pipeline/m12_execute_edge_cases.py)도 19건의 신호·종료 상태를 관찰한다. 레지스터·메모리 상태를 사례별로 설계하지 않고, Ubuntu 실행기는 결과가 존재하며 도구 오류가 없는지를 주로 확인한다. 따라서 “CPU 19건 통과”보다 “19건 실행 관측을 수집했고 도구 오류가 없었다”가 정확하다.

회귀 테스트 20개는 유용하지만, 독립적인 바이트 기대값은 일부 작은 사례에 한정되고 기존 정답지 23개는 주로 수용 여부를 검사한다. 이 숫자만으로 7,283건에 대한 오탐률·미탐률을 알 수 없다. Windows 기록 역시 `Ran 20 ... skipped=7`이면 **13개 통과·7개 생략**으로 보고해야 한다.

**보완:** `수집 완료`, `기대값 일치`, `현재 버전에서 재현`, `명세 판정 확정`을 별도 집계한다. 고정 사례에는 버전별 예상 관측과 허용 가능한 변화 사유를 둔다. 알려진 표시 결함이 수정된 새 버전에서 테스트가 실패하면 이를 제품 회귀와 구별해 기대값을 검토한다.

### R5. P1 — 오퍼랜드·opcode의 부분 검사를 전체 유효성 판정으로 쓰기 어려움

**근거: 코드 검토 + 재집계.** [operand_forms.py](../pipeline/operand_forms.py)의 형태 비교는 모드·CPUID를 결정 조건으로 쓰지 않고, 접두어·마스크·일부 토큰은 미확인으로 둔다. opcode 대조는 일부 opcode 바이트·mandatory prefix·REX.W·ModRM.reg만 확인한다. ModRM의 모든 필드, SIB, 변위·즉시값, 전체 길이·모드 제약을 검사하는 디코더는 아니다.

이러한 제한 자체는 문서화된 설계 선택이다. 문제는 후속 프로그램이 최종 `status` 하나를 읽으면 이 제한을 잃기 쉽다는 점이다. 예를 들어 SDM 형태 미완료는 2,688건인데 최종 `incomplete`는 3건이다. `rep nop`도 이번 실측에서 SDM 형태는 `incomplete`, 최종 상태는 `needs_review`였다.

**보완:** 아래 세 계층을 독립 필드로 둔다.

1. 관측: 도구가 무엇을 수용하고 어떤 바이트를 냈는가.
2. 검증 범위: 검사한 필드, 지원하지 않는 필드, 필요한 문맥은 무엇인가.
3. 사용 정책: 현재 퍼징 목적에서 이 입력을 보관·전달·추가 검토할 것인가.

`unknown`은 참도 거짓도 아니다. `fields_match`는 “검사한 필드의 일치”라는 의미를 유지하고 `row_match`나 `valid`로 승격하지 않아야 한다.

### R6. P1 — 단일 문자열과 단일 디코더에 의존한 판정 구조

**근거: 코드 검토.** GNU와 Clang으로 조립 경로를 두 개 사용하는 것은 유익하다. 하지만 두 오브젝트 모두 GNU objdump로 해독하므로 독립적인 디코더 두 개를 비교한 것은 아니다. 또 `as → objdump → as` 왕복이 같더라도 최초 as가 입력 의도를 잘못 인코딩했는지를 단독으로 판별할 수 없다. 일치하는 두 구현에 공통 결함이 있을 수도 있다.

**보완:** 독립적인 디코더를 추가하고 표시 문자열보다 구조화된 결과를 비교한다. 후보는 [Intel XED](https://intelxed.github.io/ref-manual/)와 LLVM MC/llvm-objdump 등이다. XED는 인코딩·디코딩 라이브러리이며 CPU 실행 의미의 보편적 정답으로 취급하지 않는다. LLVM 디코더와 Clang 어셈블러는 같은 프로젝트 계열이라는 점도 기록한다.

비교할 필드는 명령 종류, 길이, 명시적 오퍼랜드, operand/address size, 메모리 폭, 상대 변위, 실제 접두어, 해당 모드의 해독 가능 여부다. 같은 뜻의 별칭이나 기본 출력 스타일은 정규화할 수 있지만, REX.W 존재 여부처럼 실험 목적과 관계있는 차이는 지우면 안 된다. 결과가 갈리면 다수결로 버그를 확정하지 않고 근거를 조사한다.

### R7. P1 — 대표값 생성은 경계값 탐색을 대신하지 못함

**근거: 코드 검토.** [m3_combine.py](../pipeline/m3_combine.py)는 레지스터·즉시값·주소에 소수의 고정 대표값을 사용하고, 오퍼랜드 후보를 같은 인덱스끼리 조합한다. 모든 후보의 곱집합이나 랜덤 변이는 수행하지 않는다. 소스가 같은 매뉴얼 행도 반복된다.

이 방식은 작은 재현 자료를 만드는 데 좋지만, 인코딩의 예외 처리를 넓게 탐색하는 방법은 아니다. 특히 양쪽 피연산자가 같은 레지스터이면 순서·필드 선택 오류가 눈에 잘 드러나지 않는다. R2의 `add ecx, ecx`가 그 한 예다.

**보완:** 전체 ISA의 조합을 무작정 늘리기보다 선택한 명령군에 대해 아래 축을 조합한다.

| 축 | 우선 추가할 입력 |
|---|---|
| 레지스터 | 서로 다른 값, 같은 값, 낮은/확장 레지스터, AH 계열과 REX 제약 |
| 메모리 주소 | base만 사용, base+index×scale, RSP/RBP/R12/R13, RIP-relative, 32/64비트 주소 |
| 즉시값·변위 | 해당 인코딩의 최소·최대, 경계 직전·직후, 부호 확장 경계 |
| 접두어 | 허용/금지 조합, 중복·순서, mandatory prefix, REX 관련 상호작용 |
| SIMD | lane width, 마스크 k0/비제로, zeroing, broadcast, rounding 제약 |
| 부정 사례 | 하나의 제약만 위반하도록 만든 입력과 대응하는 정상 대조군 |

유효 입력의 다양성 확대는 5회 회의록의 방향과 부합한다. 의도적 부정 사례는 어셈블러의 견고성을 평가하는 별도 실험으로 표시한다. 생성 seed, 변경한 축, 기대 제약을 저장하고, 여러 제약이 동시에 깨져 원인을 알 수 없는 입력부터 늘리지 않는다.

### R8. P1 — 판정의 버전 연결과 실행 증거 보존이 불완전함

**근거: 코드 검토.** [review_verdicts.py](../pipeline/review_verdicts.py)는 combo ID와 소스가 같은지 확인하지만 현재 바이트·도구 버전·재심 증거 해시를 확인해서 판정을 적용하지는 않는다. 새 objdump에서 표시가 수정되어도 과거 `confirmed`를 그대로 적용할 위험이 있다.

DB의 `row_id`는 CSV의 위치다. PDF 재추출로 행 순서가 바뀌면 기존 조합과 새 DB를 섞어 잘못된 기대 행을 대조할 수 있다. 해시를 기록하는 것과 실제로 입력 간 버전 일치를 강제하는 것은 다르다.

또한 `out/lint/`와 `out/review/cases.json`은 다음 실행에 덮어써진다. 실행 manifest에 해시가 남아도 대응하는 옛 바이트·출력 파일이 보존되지 않으면 과거 결과를 완전히 재검사할 수 없다. 5·8단계 오브젝트와 일부 도구·빌드 정보도 재현 묶음 관점에서 보완이 필요하다.

**보완:** `(manual_hash, form_id, generator_version, source_hash, tool_hash, options)`로 증거를 연결한다. `out/runs/<run_id>/` 아래에 해당 실행의 JSON/CSV/원시 출력을 함께 저장하고 원자적으로 완료 처리한다. 다음 실행은 새 디렉터리에 기록한다. 판정은 근거가 된 실행을 참조하고 버전이 달라지면 재확인 대상으로 돌린다. 숫자 위치 ID와 별도로 내용에 기반한 안정적인 form ID를 둔다.

**완료 기준:** 다른 환경에서 한 실행 묶음을 받아 동일 입력과 옵션을 재실행할 수 있어야 한다. DB·조합 버전 혼합과 오래된 재심 자동 적용을 탐지해야 한다.

### R9. P0(임의 입력 실행으로 확장할 때) — CPU 관측과 실행 격리의 경계

**근거: 코드 검토.** 현재 11단계는 고정 시나리오지만 12단계는 CSV에서 `expected_valid=False`이고 조립된 항목을 자동 선택한다. 따라서 생성 데이터가 바뀌면 실행 대상도 바뀐다. 지금의 19개라는 숫자가 실행기 자체의 고정 허용 목록은 아니다.

현재의 자식 프로세스와 timeout은 유용하지만 실행 권한·파일시스템·네트워크를 격리하는 보안 경계는 아니다. CLI가 입력 명령어를 실행하지 않더라도 GNU/LLVM 같은 네이티브 파서가 그 입력을 처리하므로, 이 도구 자체가 퍼징 대상을 호출하는 하네스라는 관점도 필요하다.

**보완:** CPU 경로는 승인된 사례 ID와 소스/바이트 해시를 확인하는 목록으로 제한한다. 임의 코드 실행 연구를 시작할 때는 일회성 VM 등 별도 환경, 프로세스 트리 종료, CPU·메모리·출력 제한을 설계한다. 어셈블러·디코더 견고성 실험에도 작업 디렉터리·자원 제한·전체 사례 deadline을 적용한다.

CPU 결과는 레지스터·플래그·읽기/쓰기 메모리·fault 주소를 사례별 기대 조건과 비교해야 한다. 정상적인 예외 발생, 기능 미지원, 초기 상태 문제를 대상 구현의 오류와 구분한다. 기존 MOV Sreg 대조 실험의 방식을 제한된 명령군에 확장하는 편이 합리적이다.

### R10. P1 — 퍼징 성능과 연구 효과가 아직 측정되지 않음

**근거: 코드 검토 및 저장된 평가 자료의 범위.** 현재 배치는 정해진 입력을 재검사한다. coverage에 따른 입력 선택, 지속적인 mutation, 실패 최소화, 근본 원인별 중복 제거, 외부 퍼징 대상의 검출률 비교는 현재 자료에서 확인되지 않는다. 이는 도구의 보조 역할을 부정하는 지적이 아니라, “퍼징 연구에 도움이 된다”는 주장을 입증할 다음 실험이 필요하다는 뜻이다.

정상 수용 사례는 기본 설정에서 조립·추출·해독·재배치 확인을 GNU·Clang·왕복·옵션 대조에 반복해 대략 16개의 외부 프로세스를 호출한다. CLI는 입력과 결과를 모은 뒤 JSONL을 출력하므로 지속적으로 입력을 받아 즉시 결과를 내는 서비스도 아니다. 고속 mutation마다 이 전체 경로를 호출하면 병목이 될 가능성이 있다. 이번에는 처리량·지연을 계측하지 않았으므로 수치로 성능을 단정하지 않는다.

**보완:** 빠른 정적 검사/주석, 선택한 입력의 동적 비교, 흥미로운 결과의 정밀 재심으로 비용을 나눈다. DB 인덱스와 도구·버전·옵션을 포함한 캐시를 사용하고, 캐시 cold/warm, p50/p95 지연, 최대 메모리, 시간당 처리량을 측정한다. 프로세스 내 디코더 도입은 크래시 격리 비용과 함께 판단한다.

## 6. 먼저 정해야 할 퍼징 활용 목적

“바른 명령어만 통과시킨다”는 정책은 무엇을 퍼징하느냐에 따라 오히려 중요한 입력을 제거할 수 있다.

| 실제 퍼징 대상 | 도구의 적절한 역할 | 피해야 할 정책 |
|---|---|---|
| 어셈블러 파서의 크래시·메모리 오류 | 정상·비정상 문법을 모두 보존하고 결과 주석 | GNU가 거부한 입력을 실행 전에 전부 폐기 |
| 바이너리 디코더의 경계 처리 | raw bytes·길이·모드별 결과 비교 | as가 만들 수 있는 바이트만 허용 |
| 에뮬레이터/JIT의 의미 오류 | 정의된 전제조건의 코드와 상태를 생성·비교 | 단일 명령어의 조립 성공을 프로그램 정확성으로 사용 |
| 특정 인코딩의 CPU 관측 | 실제 인코딩과 실행 전제조건을 고정 | assembler가 다른 유효 인코딩을 골라도 시험 완료 처리 |

LLVM은 어셈블리 텍스트를 받는 `llvm-mc-assemble-fuzzer`와 기계어를 받는 `llvm-mc-disassemble-fuzzer`를 구분한다. 이 구분은 본 프로젝트의 입력 채널 설계에도 직접 참고할 수 있다. [LLVM FuzzingLLVM 문서](https://llvm.org/docs/FuzzingLLVM.html#llvm-mc-assemble-fuzzer)

권장 시작점은 **기존 퍼징 입력을 폐기하지 않고 의도·바이트·미확인 항목을 주석으로 남기는 보조 도구**다. 자동 필터링은 정확도와 놓치는 사례를 평가한 뒤 별도 정책으로 추가한다. “명령어 조합”이 한 명령의 오퍼랜드 조합인지 여러 명령어의 실행 순서인지도 실험 계획에서 명시해야 한다.

## 7. 연구로서 설득력 있게 만드는 비교 실험

### 7.1 연구 질문을 측정 가능한 형태로 좁히기

다음 세 질문을 권장한다.

1. 도구가 **생성기의 의도와 실제 인코딩의 불일치**를 얼마나 정확히 찾는가?
2. 퍼징 결과에 주석을 붙였을 때 **오탐 조사 시간과 잘못된 폐기**가 줄어드는가?
3. 같은 시간·CPU 예산에서 **대상 코드 도달 범위와 재현 가능한 서로 다른 오류**가 개선되는가?

단순한 두 구현 비교 자체는 기존 방법이다. 예를 들어 [Csmith](https://github.com/csmith-project/csmith)는 랜덤 프로그램 생성과 차등 검사를 사용한다. 본 프로젝트의 연구 기여 후보는 SDM 행의 의도가 소스 생성과 조립을 지나며 유지되었는지 추적하고, 그 정보가 후속 퍼징의 잘못된 판단을 줄인다는 것을 보여주는 데 있다. 신규성은 별도의 선행연구 비교로 검증해야 한다.

### 7.2 정답 집합과 평가 집합을 분리하기

현재 알려진 사례로 규칙을 만들고 같은 사례로 성능을 평가하면 일반화 능력을 알기 어렵다. 추가 평가 집합은 입력의 생성 규칙과 기대값을 검토하고, 구현자가 규칙을 조정할 때 보지 않은 명령군·인코딩 계열을 포함해야 한다.

정상 표현 차이, 실제 target encoding 불일치, 지원 차이, 미지원 분석, 도구 크래시, 재배치 문맥, 알려진 수정 전/후 오류를 각각 포함한다. 가능한 경우 서로 다른 사람의 검토를 거치고, 판단이 불일치한 사례도 기록한다. 이는 향후 평가 절차 제안이며 이번 감사에 별도 검토자가 참여한 것은 아니다.

측정값은 경고의 precision, 목표 결함의 recall, 정상 입력 오경보율, 미확인 비율, 필터링으로 잃은 입력·실제 오류, 사례당 검토 시간이다. 모든 지표에 분모와 제외 기준을 명시한다.

### 7.3 실제 대상 하나에 연결하는 최소 실험

초기 대상은 접근 가능한 어셈블러 또는 디코더 하나로 좁힌다. 동일한 퍼징 엔진·대상 빌드·시간 예산에서 아래 조건을 비교한다.

| 조건 | 내용 | 확인 목적 |
|---|---|---|
| A | 기존 퍼징, 도구 없이 실행 | 기준 성능 |
| B | 기존 퍼징 + GNU 수용 여부만 기록 | 단순 수용 검사 효과 |
| C | 기존 퍼징 + 현재 도구의 사후 주석 | 추가 관측의 효과 |
| D | 개선된 의도/인코딩 판정과 사례 분류 | 제안한 보완의 효과 |

구문 오류 탐색 대상에는 B~D를 입력 폐기 필터로 쓰지 않는다. 필터를 평가하고 싶다면 추가 조건으로 분리하고 버린 입력도 재실행 가능하게 보존한다. 분석 시간을 포함한 동일한 실제 시간 예산의 비교를 주 결과로 하고, 입력 수를 고정한 분석은 비용을 분리하는 보조 결과로 둔다.

여러 seed로 반복하고 실행별 분포·효과 크기·신뢰구간을 보고한다. 예를 들어 20~30회는 시작 계획으로 삼을 수 있지만 필요한 반복 수는 변동성과 예산을 보고 정해야 한다. 한 번의 실행이나 평균만으로 퍼저의 우열을 단정하지 말아야 한다는 근거는 [Evaluating Fuzz Testing, CCS 2018](https://arxiv.org/html/1808.09700v2)의 반복 실험 분석에 있다.

새 coverage를 만든 입력, 시간당 처리량, 시간당 재현 가능한 오류, 근본 원인별 중복 제거 결과를 기록한다. 파일 개수나 서로 다른 크래시 주소를 독립 버그 수로 그대로 집계하지 않는다. LLVM의 libFuzzer 문서도 coverage 기반 corpus 갱신과 크래시·timeout 입력 보존을 핵심 동작으로 설명한다. [libFuzzer 문서](https://llvm.org/docs/LibFuzzer.html#corpus)

## 8. 실행 우선순위와 완료 기준

아래는 달력상 완료 약속이 아니라 작업 순서다. 각 묶음의 완료 기준을 충족한 뒤 다음으로 넘어간다.

| 순서 | 보완 작업 | 완료를 판단할 산출물 |
|---|---|---|
| 1 | 대상·입력 채널·도구 역할 확정 | 퍼징 대상, 찾아야 할 오류, 통과/보관 정책을 적은 1쪽 실험 계약 |
| 2 | R1~R3 판정 전달 수정 | 크래시/timeout/검사 실패 반례와 CLI·API·배치 일관성 검증 |
| 3 | 버전·행·증거 연결 | 수정 전후를 보존하는 실행 묶음, 입력 버전 혼합 탐지 |
| 4 | 제한된 명령군의 인코딩 검사 보강 | 구조화된 결과, 독립 디코더 비교, 구별 가능한 레지스터·경계값 입력 |
| 5 | 평가 집합 확보 | 알려진 사례와 분리한 정답 집합, precision/recall/unknown 집계 |
| 6 | 실제 퍼징 대상 연결 | A~D 반복 실험과 비용·검출·검토 시간 비교 |
| 7 | 재현·공개 가능한 사례 정리 | 최소 재현 입력, 해당 버전, 기대/실제 근거, 근본 원인별 집계 |

CPU 실행 범위를 넓히는 작업은 R9의 실행 제한을 먼저 충족해야 한다. 새로운 니모닉을 대량 추가하거나 16/32비트·AT&T·VEX/EVEX 전체를 한꺼번에 지원하는 작업은 이 기반을 만든 뒤 범위를 선택한다.

## 9. 다음 미팅에서 설명할 내용

다음 설명이 현재 근거와 가장 잘 맞는다.

> 매뉴얼에서 생성한 입력을 GNU와 Clang으로 조립하고, 실제 바이트와 역어셈블 결과를 연결하는 도구를 만들었습니다. 기존 버그 후보를 재심하면서 입력 생성 오류·표현 차이·지원 차이를 구분했습니다. 현재 도구는 사례 수집과 분석에는 쓸 수 있지만, 자동 판정에서 실패 전달과 기대 인코딩 반영을 보완해야 합니다. 다음 단계에서는 실제 퍼징 대상 하나에 연결해 잘못된 판단과 조사 비용을 줄이는지 평가하겠습니다.

합의가 필요한 연구 결정은 다섯 가지다.

1. 실제 퍼징 대상은 어셈블러·디코더·에뮬레이터/JIT·CPU 중 무엇인가?
2. 연구의 성공 기준은 도구 결함 발견, 입력 의도 보존, 조사 비용 감소 중 무엇인가?
3. 의미가 같은 다른 인코딩을 허용하는가, 특정 인코딩 행을 반드시 시험해야 하는가?
4. 우선 명령군과 실행 모드, 명세에서 정의되지 않은 동작의 제외 기준은 무엇인가?
5. 도구를 붙이지 않은 기존 방식보다 나아졌음을 어떤 기준으로 인정할 것인가?

**현재 단계에서 가장 중요한 보완은 “더 많은 테스트” 자체가 아니라, 실패를 놓치지 않는 관측·의도와 결과를 연결하는 판정·후속 퍼징에서의 효과를 측정하는 평가다.**
