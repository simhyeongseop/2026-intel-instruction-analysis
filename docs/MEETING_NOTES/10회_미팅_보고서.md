## 0. 먼저 — 현재 확정 버그 현황 (4건, 잠정)

9회 보고서의 "확정 버그 8건"은 재검토로 **4건으로 하향**됐다. 이번 라운드에서 그 4건을 **성격별로 분리**했다. 뭉뚱그리면 서로 다른 종류의 발견이 섞인다.

| 성격 | 건수 | 대상 | category |
|---|---|---|---|
| **SDM vs `as`** (어셈블러가 매뉴얼 문법을 거부) | **1건** | UDB | `gas_missing_mnemonic` |
| **SDM vs `objdump`** (어셈블러는 정확한데 디스어셈블러 표시가 틀림) | **3건** | LSS / LFS / LGS | `objdump_farptr_size_ignores_rexw` |

`out/triage.csv` 1,585행 집계: **bug 4 / false_alarm 1,557 / unsure 24**

> **⚠️ 4건도 잠정치다.** 형섭이 제기한 이의 3건(LSS·LFS·LGS / MOV Sreg / UDB)이 재검증 대기 중이라 더 줄어들 수 있다 (9절 참고). 이번 보고에서 "확정"이라는 표현은 쓰지 않는다.

**8건 → 4건은 후퇴가 아니라 검증 체계가 작동한 결과다.** codex 교차검증 + PDF 문자 단위 폰트크기 재추출 + as/clang 4종 바이트 레벨 대조로 자체 판정 절반을 스스로 기각했다. CLAUDE.md 7절("LLM 판단만으로 버그라고 결론짓지 않는다")을 실제로 지킨 사례다.

### 🔑 오탐의 근본 원인 — 같은 패턴이 7번 반복됐다

개별 버그 4건보다 이 구조적 발견이 연구로서 값어치가 크다.

> SDM은 같은 니모닉 + 같은 오퍼랜드 텍스트를 **레지스터/주소 폭이 다른 여러 표 행**으로 나눠 문서화하는데, **그 폭 차이가 Intel 문법만으로는 구분되지 않는다.** 그래서 조합 생성기(3단계 combiner)가 "N.E. 행을 테스트하려 했는데 `as`가 다른 유효한 행으로 인코딩해버리는" 상황이 반복된다.

| # | 니모닉 그룹 | 실측된 실제 사정 |
|---|---|---|
| 1·2 | CALL / JMP | 8회 "확정 버그 7건" 중 2건이 정확히 이 문제 (ModRM 직접 디코딩으로 확인) |
| 3 | DEC/INC r16·r32 | `dec cx`/`dec ecx`는 단일바이트 N.E. 폼이 아니라 `FF /1` Valid 폼으로 인코딩됨 |
| 4 | LEAVE | 32비트 N.E. 행이 **어떤 Intel 문법으로도 선택 불가능한** 표 행 |
| 5 | LGDT/LIDT | SIGSEGV는 N.E.와 무관하게 특권 명령어라서 (ring 3 → #GP) |
| 6 | BNDCL/BNDMOV | `/proc/cpuinfo` 실측 → 이 커널/CPU가 MPX 미지원 → 오퍼랜드 무관 무조건 NOP |
| 7 | LAR/LSL | REX.W 한 비트로 두 GPR 오퍼랜드 폭을 독립 지정 불가 |

이건 **테스트 생성 자체가 편향된다**는 지적이므로, as-fuzzer류 접근 전반에 적용된다. 남은 4건은 방향이 반대(SDM이 **허용**하는 문법을 도구가 **거부/오표시**)라서 이 편향의 영향을 받지 않는다.

## 2. 배경 — 왜 이 도구가 필요한가

지금까지(1~12단계)의 파이프라인은 **사후 배치 검증** 구조다. SDM 표를 통째로 뽑아 조합을 생성하고, 7,276건을 한꺼번에 어셈블·역어셈블·비교해서 판정 CSV를 남긴다. 유용하지만 결과가 `out/*.csv`와 리포트 안에만 남는다.

이번 라운드에서는 **그 축적된 근거를 실제로 쓸 수 있는 형태로 바꿨다.** 사람이 어셈블리 한 줄을 쓸 때,

- 인텔 매뉴얼 기준으로 뭐가 틀렸는지
- 실제 `as`/`clang`을 돌리면 어떤 에러가 나는지
- **그 에러가 왜 나는지** (지금까지 파이프라인으로 알아낸 원인)

를 한 번에 알려주는 도구다.

| | 기존 파이프라인 (1~12단계) | 이번 도구 (`asm_linter`) |
|---|---|---|
| 입력 | SDM PDF 전체 | 어셈블리 한 줄 / `.s` 파일 |
| 시점 | 사후 배치 (7,276건 일괄) | 작성 시점 (즉시) |
| 출력 | 판정 CSV + 리포트 | 사람이 읽는 진단 + 원인 해설 |
| 판정 근거 | 도구 실행 결과 | **파이프라인이 이미 확정한 근거를 규칙으로 내장** |
| 역할 | 버그를 **찾는다** | 찾은 것을 **설명한다** |

파일: `scripts/asm_linter.py` (약 560줄, 외부 의존성 없음)

## 3. 설계 — 세 갈래에서 고른 것

도구를 만들기 전에 성격을 정하는 갈림길이 세 개 있었다. 셋 다 명시적으로 선택했다.

| # | 쟁점 | 선택 | 이유 |
|---|---|---|---|
| 1 | 어셈블러 에러 메시지를 어떻게 얻을까 | **동적-정적 혼합** — 실제 `as`/`clang`을 백그라운드에서 조용히 한 번 돌려 진짜 에러를 가로챈다 | 에러 문구를 코드에 하드코딩하면 어셈블러 버전이 바뀔 때 거짓말이 된다. 실측이면 항상 맞다 |
| 2 | 우리 해설을 어떻게 매칭할까 | **사전 정적 분석 기반** — 정적 규칙이 먼저 플래그를 세우고, 어셈블러가 실패하면 그 플래그의 해설을 붙인다 | 에러 텍스트 매칭 방식(`"lss" + "operand size mismatch"` 패턴)은 어셈블러 문구가 바뀌면 깨진다. 플래그 기반이면 우리 규칙만 관리하면 된다 |
| 3 | 어셈블러는 통과시켰는데 매뉴얼 기준과 다르면 | **실용주의** — 성공을 알리고 `[참고]` 수준 정보성 메시지만 | 기계어가 나왔으면 목적은 달성됐다. 강한 경고를 남발하면 도구를 안 쓰게 된다 |

CLAUDE.md 원칙과의 관계: 선택 1이 **"LLM 판단만으로 버그라고 결론짓지 않는다, 근거는 항상 도구 결과다"**(7절)를 도구 차원에서 강제한다. 린터는 자기 규칙을 믿지 않고 매번 `as`를 돌려 확인한다.

## 4. 구조와 사용법

```
어셈블리 한 줄
   │
   ▼
[파서]         mnemonic + operand(레지스터/메모리/크기 지시자)로 분해
   ▼
[정적 규칙 6개] isa_db.csv(SDM DB)와 대조 → 플래그 세움  ← 설계 2
   ▼
[어셈블러 실측]  as --64 -mintel64 / clang 을 조용히 실행  ← 설계 1
   ▼
[교차 확인]     -mintel64 없이도 되는지 / objdump 출력을 되먹여 round-trip
   ▼
[판정 출력]     에러면 플래그 해설 붙임 / 성공이면 [참고]만  ← 설계 3
```

`as`/`objdump`/`clang`은 WSL(Ubuntu)에만 있으므로 WSL에서 실행한다.

```bash
# 한 줄 검사
wsl -d Ubuntu -- bash -lc "cd /mnt/c/Users/wltjq/OneDrive/assembler-testing && \
  python3 scripts/asm_linter.py 'lss rcx, fword ptr [eax]'"

# 대표 케이스 9개 시범
python3 scripts/asm_linter.py --demo

# 파일 검사 (파이프라인이 만든 tests.s도 그대로 먹는다)
python3 scripts/asm_linter.py -f out/tests.s --limit 300

# 어셈블러 없이 정적 검사만 (Windows에서도 동작)
python3 scripts/asm_linter.py --static-only 'mov ds, qword ptr [eax]'
```

`as`가 없는 환경(Windows)에서는 자동으로 정적 전용 모드로 내려간다.

## 5. 내장한 정적 규칙 6개

규칙은 전부 **이 프로젝트가 파이프라인으로 이미 확인한 실측 + SDM 인용**에 근거한다. 새로 추측한 규칙은 없다.

| rule_id | 잡는 것 | SDM 근거 | 실측 근거 | 프로젝트 판정 |
|---|---|---|---|---|
| `farptr_size_mismatch` | LSS/LFS/LGS의 메모리 크기 ≠ 목적지 폭 + 16 | `LSS r16,m16:16` / `r32,m16:32` / `REX.W + r64,m16:64` (p.658) | as가 `incorrect register ... used with 'X' suffix` 또는 `operand size mismatch`로 거부 | (문법 오류 예방) |
| `farptr_r64_objdump_display` | LSS/LFS/LGS의 r64 폼 → objdump가 `FWORD PTR`로 오표시 | p.658 Description이 "80-bit pointer"로 명시 → `TBYTE PTR`이어야 함 | as는 `67 48 0f b2 08`로 정확히 인코딩, objdump 출력 되먹이면 as가 거부 | **bug** (combo 1527/1532/1535) |
| `mov_sreg_mem_size` | `MOV Sreg, <word 아닌 크기> ptr [...]` | 표는 `REX.W + 8E /r MOV Sreg, r/m64` Valid인데, 같은 행 Description은 "Move **lower 16 bits** of r/m64 to segment register" (p.731) | as `operand type mismatch`, clang 18/19/20 `invalid operand` — **어셈블러 4종 일치** | unsure (combo 1683) |
| `mov_sreg_reg_width` | `MOV Sreg, r16/r64` → as와 clang의 인코딩이 갈림 | 세그먼트 로드는 폭 무관 하위 16비트만 사용 | as는 전부 `8e d8`, clang은 `66 8e d8` / `48 8e d8`로 폭 유지 | (정보성) |
| `ambiguous_asymmetric_width` | LAR/LSL의 비대칭 폭 표기 | `LAR r32, r64/m16` (p.651), `LSL r64, r32/m16` (p.691) — REX.W 한 비트로 두 GPR 폭을 독립 지정 불가 | as(2.42/2.47)는 대칭 폼조차 REX.W를 못 만듦, clang은 목적지 이름만 보고 결정 | **false_alarm** (combo 1516/1571) |
| `sdm_mnemonic_unknown_to_assembler` | `udb` | `D6 UDB`, 64비트 Valid (p.1436) | as `no such instruction: udb`, clang `invalid instruction mnemonic 'udb'` | 재검증 중 |
| `sdm_operand_count_mismatch` | SDM 표에 없는 오퍼랜드 개수 (`isa_db.csv` 기반 일반 규칙) | 해당 니모닉의 모든 폼 | as `number of operands mismatch` | (일반 규칙) |

마지막 규칙만 특정 사안이 아니라 **`isa_db.csv` 4,210행을 그대로 활용하는 일반 규칙**이다. 예: `ud0` 한 단어만 쓰면 "SDM에는 2오퍼랜드 폼(`UD0 r32, r/m32`)만 있습니다"라고 잡는다.

## 6. 실제 출력

### (a) 매뉴얼 기준 위반 → as 거부 → 원인 해설

```
입력: lss rcx, fword ptr [eax]
  정적 분석: 2건
    [에러 예상] (farptr_size_mismatch)
      LSS의 메모리 크기가 목적지 폭과 안 맞습니다. 목적지 'rcx'(64비트)면
      메모리는 'tbyte ptr'(80비트)여야 하는데 'fword ptr [eax]'(48비트)로 적혀 있습니다.
      SDM 근거 : far pointer는 [세그먼트 셀렉터 16비트 + 오프셋 64비트] = 80비트다.
                 SDM 폼: LSS r64,m16:64 (REX.W + 0F B2 /r, Valid, p.658)
      권장 수정 : lss rcx, tbyte ptr [eax]
  어셈블러 실측:
    as (--64 -mintel64)    : ERROR incorrect register `rcx' used with `l' suffix
    clang                  : ok    67480fb208
  판정:
    정적 분석이 예측한 대로 as가 거부했습니다. 원인 해설:
      - as는 Intel 크기 지시자를 내부적으로 AT&T 접미사로 바꿔 오퍼랜드 폭을 정한다
        (실측: dword ptr->'w', fword ptr->'l', tbyte ptr->'q').
        참고: clang은 크기 지시자를 사실상 무시하고 목적지 레지스터 이름만 보고 인코딩한다.
              clang이 통과시켜도 매뉴얼에 맞는 건 아니다.
```

**주목할 점:** clang은 이 잘못된 줄을 조용히 통과시킨다(`67480fb208` = 올바른 인코딩). 즉 **"clang이 받아줬다"는 건 매뉴얼에 맞다는 증거가 아니다.** 린터가 이걸 명시적으로 알려준다.

### (b) 매뉴얼대로 썼는데 objdump가 틀리게 표시 (현재 bug 판정 케이스, 설계 3 적용)

```
입력: lss rcx, tbyte ptr [eax]
  정적 분석: 1건
    [참고] (farptr_r64_objdump_display)
  어셈블러 실측:
    as (--64 -mintel64)    : ok    67480fb208     -> lss rcx,FWORD PTR [eax]
    clang                  : ok    67480fb208
    as (-mintel64 없이)      : ERROR operand size mismatch for `lss'
      -> 이 폼은 as에 '-mintel64' 옵션이 있어야 어셈블됩니다.
  판정:
    어셈블 성공. 다만 매뉴얼 기준과 다음 차이가 있으니 유의하세요:
      - GNU objdump는 REX.W로 승격된 r64 폼의 메모리 크기를 m16:32용인 'FWORD PTR'로
        표시한다. r16/r32 폼은 정상 표시된다.
        참고: llvm-objdump는 같은 바이트에 이 오표기를 하지 않는다 -> GNU objdump만의 결함.
    round-trip 실패: objdump가 찍은 'lss rcx,FWORD PTR [eax]'를 다시 as에 넣으면 거부됩니다
      (as 에러: incorrect register `rcx' used with `l' suffix)
```

어셈블은 성공했으므로 강한 경고를 띄우지 않고 `[참고]`로만 알린다(설계 3). 대신 **round-trip 검사가 자동으로 돌아 그 자리에서 재현한다** — 이건 규칙에 하드코딩된 게 아니라 objdump 출력을 실제로 as에 되먹여서 얻은 결과다.

### (c) 어셈블러 4종이 일치해서 SDM 표가 의심되는 케이스

```
입력: mov ds, qword ptr [eax]
    [에러 예상] (mov_sreg_mem_size)
      'ds'는 16비트 세그먼트 레지스터라 메모리에서 16비트 셀렉터만 읽습니다.
      SDM 근거 : 표에는 'REX.W + 8E /r MOV Sreg, r/m64'가 Valid로 실려 있으나, 같은 행
                 Description이 "Move lower 16 bits of r/m64 to segment register"라고 적어
                 실제 전송 폭은 16비트임을 밝힌다. (p.731)
  어셈블러 실측:
    as (--64 -mintel64)    : ERROR operand type mismatch for `mov'
    clang                  : ERROR invalid operand for instruction
  판정:
      참고: 이 프로젝트의 현재 판정은 'unsure'다(combo 1683).
```

린터가 **판정이 미확정이라는 사실까지 그대로 노출한다.** 확정된 것처럼 단정하지 않는다.

## 7. 🔑 이 도구를 만들면서 새로 확인한 사실 3가지

### (1) `as`의 LSS/LFS/LGS r64 폼은 `-mintel64` 옵션이 없으면 거부된다

린터에 "`-mintel64` 없이도 되는지" 비교 기능을 넣으면서 발견했다.

```bash
$ printf '.intel_syntax noprefix\n.Ltarget:\nlss rcx, tbyte ptr [eax]\n' > /tmp/m.s
$ as --64 -o /tmp/m.o /tmp/m.s
/tmp/m.s:3: Error: operand size mismatch for `lss'
$ as --64 -mintel64 -o /tmp/m.o /tmp/m.s      # 성공
$ objdump -d -M intel /tmp/m.o | tail -2
   0:  67 48 0f b2 08    lss    rcx,FWORD PTR [eax]
```

파이프라인 5단계(`m5_assemble.py`)가 `as --64 -mintel64`를 쓰고 있어서 지금까지 드러나지 않았다. **`as`의 기본 동작(`--64`만)에서는 매뉴얼대로 쓴 LSS r64 폼이 거부된다**는 뜻이므로, 이 프로젝트의 관심사("매뉴얼대로 작성했는데 어셈블러가 처리하지 못하는 경우")에 정확히 해당한다. 다만 옵션 하나로 해결되므로 결함이라기보다 **"매뉴얼대로 쓰려면 비기본 옵션이 필요하다"**는 성격이다.

> 파이프라인 결과에는 영향이 없다. `asm_result.csv`의 combo 1527 `ok`는 `-mintel64`를 준 결과로 정상이다.

### (2) `as`는 Intel 크기 지시자를 내부적으로 AT&T 접미사로 바꾼다 — 에러 메시지가 그 증거

LSS의 3×4 매트릭스를 돌려 확인했다 (`as --64 -mintel64`, LFS/LGS도 동일):

| 목적지 \ 크기 지시자 | 생략 | `dword ptr` | `fword ptr` | `tbyte ptr` |
|---|---|---|---|---|
| `cx` (16) | ok `67660fb208` | **ok** | ERR `... 'cx' used with 'l' suffix` | ERR `operand size mismatch` |
| `ecx` (32) | ok `670fb208` | ERR `... 'ecx' used with 'w' suffix` | **ok** | ERR `operand size mismatch` |
| `rcx` (64) | ok `67480fb208` | ERR `operand size mismatch` | ERR `... 'rcx' used with 'l' suffix` | **ok** |

에러 문구에 나오는 접미사가 `dword ptr`→`w`, `fword ptr`→`l`, `tbyte ptr`→`q`로 대응한다. far pointer에서 접미사는 **전체 크기가 아니라 오프셋 폭**을 가리킨다(m16:16→`w`, m16:32→`l`, m16:64→`q`). 즉 `as`의 이 동작은 **일관되고 정확하다** — 대각선(정답)만 성공한다.

이 해독이 린터 해설의 핵심 재료가 됐다. `incorrect register 'rcx' used with 'l' suffix`처럼 Intel syntax로 쓴 사용자에게는 뜻이 통하지 않는 에러를 **"fword ptr을 썼기 때문"**이라고 번역해준다.

### (3) UDB 행의 `op_en`이 `Z0`(숫자 영)이다 — 재검증 과제 C의 확인 지점

`isa_db.csv`의 UDB 행: `opcode=D6`, `instruction=UDB`, `operands=(빈칸)`, **`op_en=Z0`**, `mode_support=Valid`, `description='Raise invalid opcode exception.'`

표 행 형태는 정상적으로 갖춰져 있어 단순 추출 아티팩트로 보기 어렵다. 다만 **`op_en`이 `Z0`(숫자 영)** 인데, UD2 등 다른 무오퍼랜드 행은 `ZO`(문자 O = Zero Operands)다. PDF 원문 대조 시 확인할 지점이다.

비교군 실측 (`as --64 -mintel64` / clang 18.1.3):

| 입력 | as | clang |
|---|---|---|
| `udb` | ERR `no such instruction: 'udb'` | ERR `invalid instruction mnemonic 'udb'` |
| `ud0` | ERR `number of operands mismatch` | ERR `invalid instruction mnemonic 'ud0'` |
| `ud1` | ERR `number of operands mismatch` | ERR `invalid operand for instruction` |
| `ud2` | **ok** `0f 0b` | **ok** `0f 0b` |

`ud0`/`ud1`은 as가 **니모닉은 알고** 오퍼랜드만 요구한다. **`udb`만 니모닉 자체를 모른다.**

## 8. 검증 체계

### 이중 검증 구조

모듈 에이전트가 구현 → **`@agent-verifier`**(정답지·회귀 검증) + **codex 교차검증**(독립 전문가 판단, 유도 금지)을 병행한다. verifier 라운드 수가 이 프로젝트의 엄격함을 보여준다.

- **11단계: 7라운드.** 매 라운드 "실행 결과는 맞는데 메커니즘 설명이 부정확"하다는 지적이 반복됐다 — 단순 "매핑 안 된 주소"가 아니라 non-canonical → #GP(#PF 아님) / canonical 경계가 4-level(47비트)·5-level(56비트) paging에 따라 다름 / ASLR 때문에 "결정적"이라는 표현이 과장 → `setarch x86_64 -R`로 수정. 6차에는 "매핑 공백을 추측 말고 **실측하라**"는 요구 → syscall로 자기 `/proc/self/maps`를 직접 출력해 확인.
- **12단계: 9라운드(최다).** BNDCL 원인 오설명 → `/proc/cpuinfo` 실측으로 이 CPU의 MPX 미지원 확인. 이후 7라운드는 "레지스터를 직접 안 찍어봤으면서 값을 단정하지 말라"가 6~7회 반복 지적됨.

**판정 기준이 "결과가 맞다"가 아니라 "왜 그런지 설명까지 정확해야 한다"**는 것이 이 체계의 핵심이다.

### 🔑 방법론적 교훈 3가지

1. **병렬 fork가 영역을 침범하면 상충 결론이 난다.** LAR/LSL 담당 fork는 "bug 유지", VPMOVQD 담당 fork는 (맡은 범위를 넘어 재검토하며) "false_alarm"으로 **정반대** 결론을 냈다. 두 fork의 원시 실험 데이터(as/clang 바이트)는 실제로 일치했고 **해석만 갈렸다.** 형섭이 직접 5×3 매트릭스(as 2.42 / 소스빌드 as 2.47 / clang 20)로 재현해 해소했다. → **최종 판정은 오케스트레이터가 원시 데이터를 직접 재현해서 확정해야 한다.**
2. **fork는 "수정 금지" 지시를 어길 수 있다.** 병렬 에이전트가 `out/triage.csv`를 직접 고친 사고가 있었다. → **fork 종료 후 항상 `git diff`로 실제 변경 범위를 확인한다.**
3. **새 버그를 주장하기 전에 기존 리포트를 먼저 검색해야 한다.** verifier가 PREFETCHIT0/1을 새 버그로 오주장했으나, SDM은 RIP-relative 주소가 아니면 NOP으로 동작한다고 명시하고 있었고 `out/triage_report.md`에 이미 그 이유로 false_alarm 기록까지 있었다. **codex 교차검증이 없었으면 이 오류가 보고서에 그대로 남았을 것이다.**

### 이번 도구(`asm_linter`) 검증

CLAUDE.md 4절에 따라 `@agent-verifier`로 검증했다. 검증 항목:

- **A. 코드에 내장된 실측 주장이 실제와 일치하는가** — LSS 3×4 매트릭스, MOV Sreg 인코딩(as `8e d8` vs clang `66/48 8e d8`), LAR/LSL 대칭 폼 REX.W 부재, UDB 에러 문구, `-mintel64` 의존성을 각각 재현 대조
- **B. SDM 인용 정확성** — p.658 "80-bit pointer", MOV 8E 행 Description, D6 UDB p.1436을 `isa_db.csv`와 `intel_manual.pdf` 원문으로 확인
- **C. 프로젝트 판정과의 일관성** — 코드가 인용하는 verdict(1683=unsure, 1516/1571=false_alarm, 1527/1532/1535=bug, 4597=재검증 중)가 `m7_triage.py` override 및 `out/triage.csv`와 일치하는가
- **D. 파서 견고성·오탐** — 레지스터 표 누락, `-f out/tests.s --limit 300` 무예외 완주, 정상 명령어에 불필요한 경고가 붙지 않는가
- **E. CLAUDE.md 준수** — 쉬운 파이썬, 짧은 함수, 한국어 주석

> 검증 결과는 verifier 판정 후 이 절에 채운다.
