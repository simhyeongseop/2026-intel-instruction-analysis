# 11회 보고 — 발표 대본

발표: 2026-09-21 · 수치 검증: `python3 scripts/check_report_numbers.py --check docs/MEETING_NOTES/11회_발표_대본.md`

이 대본은 **예외 사항(뜻대로 안 된 것) 하나하나가 무엇이고 왜 생겼는지**를 중심으로 구성했다.
상세 표와 근거는 [발표자료](11회_발표자료.md), 시연 절차는 [시연 가이드](11회_LSS_시연_가이드.md)에 있다.

---

## 0. 먼저 용어 세 개

| 말 | 뜻 |
|---|---|
| **어셈블한다** | 사람이 쓴 명령어 글자(`add ecx, ecx`)를 CPU가 읽는 숫자, 곧 **바이트**(`01 c9`)로 바꾼다 |
| **역어셈블한다** | 반대로 바이트(`01 c9`)를 다시 글자(`add ecx,ecx`)로 되돌린다 |
| **왕복 검사** | 글자 → 바이트 → 글자로 돌아왔을 때 처음 글자와 같은지 본다. 다르면 둘 중 하나가 잘못한 것이다 |

이 도구가 하는 일: **매뉴얼에서 명령어 글자를 만들어 → 바이트로 바꿔 보고 → 다시 글자로 되돌려서 → 처음과 같은지 확인한다.**

---

## 1. 이 프로젝트는 무엇인가 (한 문장)

> **Intel 매뉴얼에 적힌 명령어 인코딩 표를 그대로 테스트 입력으로 바꿔, 실제 어셈블러·디스어셈블러가 매뉴얼대로 처리하는지 전수 대조하는 도구다.**

SDM Vol.2의 인코딩 행 4,210개에서 어셈블리 <!-- num:입력줄 -->23,323줄을 자동 생성해 돌린다.

## 2. 왜 해야 하는가

1. **아무도 전수로 확인하지 않는 영역이다.** 어셈블러 테스트는 보통 "자주 쓰는 명령어가 되는가"를 본다.
   매뉴얼 4,210행이 **행 단위로** 제대로 처리되는지 확인한 자료는 없다.
2. **퍼징의 앞단이 비어 있다.** AsFuzzer 같은 기존 연구는 문법을 **망가뜨린** 입력을 넣는다.
   우리는 반대로 **매뉴얼상 정확한** 입력을 만든다. 퍼저의 시드로 쓰거나, 퍼저가 낸 차이를 분류하는 데 쓴다.
3. **차이가 났을 때 "누구 탓인지" 가려야 한다.** 도구 결함인지, 우리 입력 오류인지, 표기 차이인지,
   버전 지원 차이인지 구분하지 못하면 결과가 쓸모없다. 이번 라운드가 실제로 그 구분을 했다.

## 3. 파이프라인 — 숫자가 어떻게 흘러가는가

```
Intel 매뉴얼 표 4,210줄
        ↓ 매뉴얼 규칙대로 명령어 글자를 만든다 (1~4단계)
테스트 입력 23,323줄
        ↓ GNU as로 어셈블 (5단계)
   ┌────┴────┐
받아줌 23,219   거부 104          ← 예외 ①
   ↓ 역어셈블해서 원래 글자와 비교 (6단계)
   ┌────┴────┐
같음 13,228   다름 9,991          ← 예외 ②
   ↓ Clang으로도 똑같이 해서 대조 (8·9단계)
   ┌────┴────┐
완전 일치 23,020   갈림 211       ← 예외 ③
   ↓ 지정한 매뉴얼 행을 실제로 때렸는지 확인 (13단계)
                   못 때림 349    ← 예외 ④
```

핵심은 **10단계**다. 6단계에서 "다르다"고 나온 것을 사람이 판단하지 않고,
**역어셈블 결과를 다시 어셈블해서 바이트가 같은지** 기계로 재확인한다. LSS 결함도 이 경로로 찾았다.

# 예외 사항 분석

"예외"는 뜻대로 안 된 것 전부다. 여섯 가지가 나왔고 하나씩 원인을 봤다.

## 예외 ① — 어셈블러가 거부한 <!-- num:as거부 -->104건

### ①-A. 매뉴얼도 "안 된다"고 한 것 — <!-- num:기대된거부 -->87건 (정상)

매뉴얼에 **Invalid 44 / N.E. 38 / N.S. 5**로 적힌 행들이다. `push`, `pop`, `call`, `jmp`,
`arpl`, `bound`, `lds`, `les` 같은 **32비트 시절 명령어**이고 64비트 모드에서는 쓸 수 없다.

→ **어셈블러가 맞게 거부한 것이다. 오히려 정상 동작의 증거다.**

### ①-B. 매뉴얼은 "된다"는데 거부한 것 — <!-- num:valid거부 -->17건

원래 **56건**이었다. 그중 약 40건이 **우리 입력이 틀린 것**이어서 9/19에 고쳤고 17건이 남았다.

| 건수 | 무엇 | 왜 그런가 | 누구 탓 |
|---:|---|---|---|
| 5 | `vpmovqd xmmword ptr [eax], xmm0` → `operand size mismatch` | 매뉴얼은 이 자리를 `m128`(16바이트)로 적었는데 실제로 쓰는 건 8바이트다. **매뉴얼 표 오탈자로 추정** | 매뉴얼 |
| 4 | `sysexit`, `sysret` → `ambiguous operand size` | 매뉴얼은 오퍼랜드 없이 적는데 as는 크기를 붙인 `sysexitq`/`sysretq`만 받는다. **표기 관례 차이** | 판단 보류 |
| 3 | `mov ds, qword ptr [eax]` → `operand type mismatch` | 세그먼트 레지스터에 8바이트 메모리. **재심에서 구현 버그 아님으로 정리**(CPU 실험으로 접근 폭 확인) | 정리됨 |
| 2 | `lar ecx, rcx`, `lsl rcx, ecx` → `register type mismatch` | 앞뒤 레지스터 폭이 다르다. **REX.W 비트 하나로 두 자리의 폭을 따로 정할 수 없다** | 정리됨 |
| 2 | `vscatterdpd [eax + ymm1] {k1}, ymm0` → `invalid VSIB address` | 주소 계산용 벡터 레지스터 크기가 매뉴얼 표와 맞지 않는다. **매뉴얼 표기 문제일 수 있다** | 판단 보류 |
| 1 | `udb` → `no such instruction` | 매뉴얼에 `D6 UDB`로 정식 정의돼 있는데 as 2.42가 모른다. **버전 차이 — 2.46.1부터 받아준다**(오늘 확인) | 버전 |

**→ 17건 중 어셈블러가 잘못한 것은 0건이다.** 매뉴얼 쪽 7건, 표기 관례 4건, 이미 정리된 것 5건, 버전 차이 1건.

## 예외 ② — 역어셈블 결과가 원래 글자와 다른 <!-- num:왕복다름 -->9,991건

**대부분 버그가 아니다.** 같은 뜻을 다르게 적은 것이다.

| 건수 | 무엇이 달라졌나 | 예시 | 왜 |
|---:|---|---|---|
| <!-- num:표기_숫자 -->7,736 | 숫자 표기 | `adc al, 1` → `adc al,0x1` | objdump는 숫자를 항상 16진수로 쓴다. **값은 같다** |
| <!-- num:표기_브로드캐스트 -->860 | 브로드캐스트 표기 | `qword ptr [eax]{1to2}` → `QWORD BCST [eax]` | 같은 인코딩의 다른 이름 |
| <!-- num:표기_별명 -->729 | 같은 명령의 다른 이름 | `cmovc` → `cmovb` | 한 명령에 별명이 여럿. `jnz`=`jne`, `sal`=`shl`도 같다 |
| <!-- num:표기_숨은오퍼랜드 -->210 | 숨은 오퍼랜드 | `cmps byte ptr [eax], …` → `cmps BYTE PTR ds:[esi],BYTE PTR es:[edi]` | 문자열 명령은 레지스터를 자동으로 쓴다. objdump가 펼쳐 보여준다 |
| 118 | 크기 표기 | `call far ptr [eax]` → `call FWORD PTR [eax]` | 생략한 크기를 objdump가 채운다 |
| 86 | 인코딩 형식 표시 | `vpslldq …` → `{evex} vpslldq …` | 같은 글자가 두 형식으로 인코딩될 수 있어 표시해 준다 |
| 71 | x87 스택 표기 | `fadd st(0), st(0)` → `fadd st,st(0)` | `st(0)`을 짧게 `st`로 쓴다 |
| 42 | 분기 대상 | `call .Ltarget` → `call 0x0` | 라벨 이름은 바이트에 안 남는다. 복원할 방법이 없다 |

**어떻게 확신하는가:** 사람이 눈으로 판단하지 않았다. **objdump가 내놓은 글자를 다시 어셈블해서
바이트가 원래와 같은지** 기계로 확인했다 → <!-- num:재조립동일 -->9,834건이 바이트까지 동일.
표기만 다르고 뜻은 같다는 증거다.

## 예외 ③ — GNU as와 Clang이 갈린 211건

### ③-A. 둘 다 받았는데 바이트가 다름 — <!-- num:바이트다름 -->125건

| 예시 | as | clang | 왜 |
|---|---|---|---|
| `call dword ptr [eax]` | `67 66 ff 18` | `67 ff 18` | **clang이 `66` 프리픽스를 안 붙인다** |
| `iret` | `cf` | `66 cf` | 반대로 여기선 clang이 붙인다 |

→ 어느 쪽이 틀렸다고 단정하지 않고 **차이로 기록**했다. 판정하려면 매뉴얼 본문 해석이 더 필요하다.

### ③-B. as만 받아준 것 — <!-- num:as만수용 -->74건

`bndcl bnd0, dword ptr [rax]` → clang은 `invalid instruction mnemonic 'bndcl'`.
**MPX 기능 명령어인데 Intel이 사실상 폐기해 clang이 지웠다.** (bndmov 11 / movsxd 10 / ud0 5건 등)

### ③-C. clang만 받아준 것 — <!-- num:clang만수용 -->12건

`call word ptr [eax]` → as는 `operand type mismatch`.
**64비트 모드에서 2바이트 간접 호출을 as가 막는다.** 엄격도 차이다.

**→ 두 어셈블러는 99.5%에서 바이트까지 같고, 갈리는 지점은 "폐기된 기능을 남겼는가"와 "프리픽스를 어떻게 붙이는가"다.**

## 예외 ④ — 받아줬는데 사실은 시험을 못 한 <!-- num:미타격합계 -->349건

매뉴얼은 같은 명령어를 **여러 줄로** 나눠 적는다.

- 23행 `ADC r32, r/m32` → 바이트 `13`
- 22행 `ADC r/m32, r32` → 바이트 `11`

23행을 시험하려고 `adc ecx, ecx`를 넣었는데 어셈블러는 `11`을 만들었다. **어셈블러가 잘못한 게 아니다.**
둘 다 맞는 답이고 하나를 고른 것뿐이다. 문제는 **우리가 시험하려던 행은 결국 못 건드렸다**는 것이다.
통과 여부만 보는 도구는 이걸 "성공"으로 넘긴다.

| 건수 | 원인 | 예 | 고칠 수 있나 |
|---:|---|---|---|
| <!-- num:미타격_대칭행 -->264 | **두 줄을 글자로 구분할 방법이 없다** | `adc cl, cl`은 앞뒤가 같아 어느 줄인지 지정 불가 | **원리상 불가능.** 도구의 한계로 명시해야 한다 |
| <!-- num:미타격_분기축약 -->64 | **어셈블러가 짧은 형식을 골랐다** | `ja .Ltarget`에 긴 형식을 기대했는데 `77 fe`가 나옴 | **가능.** 점프 목표를 멀리 두면 긴 형식이 강제된다 |
| <!-- num:미타격_rexw -->21 | **REX.W가 안 붙었다** | `lar ecx, word ptr [eax]` | **일부 가능.** 입력 형태를 고쳐야 한다 |

**→ "349건 시험 못 함"이 아니라 "원리상 불가능 264 + 고칠 수 있는 85"다.** 85건이 다음 라운드 1순위다.

## 예외 ⑤ — 아직 판단 못 한 <!-- num:unsure -->47건

| 건수 | 무엇 |
|---:|---|
| 22 | 레지스터 폭 표기가 바뀐 것 (LSS 계열 포함) |
| 16 | 매뉴얼은 무효라는데 as가 받아준 것 — 원인 미확인 |
| 4 | 오퍼랜드 없는 명령의 크기가 모호한 것 |
| 5 | 기타 |

→ **확정으로 보고하지 않는다.** 근거가 부족한 건 미확인으로 두는 것이 이 프로젝트의 원칙이다.

## 예외 ⑥ — 진짜 결함 1종류 3사례

**objdump가 LSS / LFS / LGS를 잘못 보여준다.**

```
매뉴얼:  LSS r64, m16:64   → 16비트 + 64비트 = 80비트짜리 메모리

1) 매뉴얼대로 써서 어셈블   lss rcx, tbyte ptr [rax]   → 48 0f b2 08   성공
2) 그 바이트를 역어셈블      → lss rcx,FWORD PTR [rax]
                                     ↑ FWORD는 48비트. 80비트인데 틀리게 적었다
3) 그 글자를 다시 어셈블      → 거부됨
```

**왜 문제인가:** 역어셈블 결과를 그대로 다시 쓸 수 없다. 바이너리를 분석해 코드를 복원하는 작업이 여기서 막힌다.

**얼마나 확실한가:** 오늘 binutils **2.42 · 2.45 · 2.46.1 · 2.47(최신)** 을 직접 빌드해 네 버전 모두 확인했다.
llvm-objdump는 크기를 아예 안 적어서(`lss rcx, [rax]`) 이 문제가 없다.

**왜 3건인가:** LSS·LFS·LGS는 하는 일이 같은 형제 명령어다.
**서로 다른 버그 3개가 아니라 한 결함의 세 명령어다.**

## 5. 도구의 결과

> **어셈블러(as, clang)는 깨끗했다.** 매뉴얼대로 쓴 입력을 잘못 처리해서 확정된 어셈블러 버그는 **0건**이다.
> 매뉴얼이 Valid라는데 거부한 <!-- num:valid거부 -->17건도 전부 원인이 설명된다.
>
> **대신 디스어셈블러에서 하나 나왔다.** objdump의 LSS/LFS/LGS 표시 결함이고 최신 2.47에서도 재현된다.
>
> **도구의 값어치는 이것이다.** 앞으로 어셈블러·디스어셈블러를 테스트할 때, 매뉴얼 기준으로 입력을 만들고 →
> 수용 여부·실제 바이트·역어셈블 왕복까지 자동으로 확인하고 → 차이가 나면 **도구 결함인지, 우리 입력
> 오류인지, 표기 차이인지, 버전 차이인지 분류해서** 사람이 볼 것만 남긴다.

반드시 덧붙일 것:

- "버그 0건"은 **우리가 확정할 수 있는 것이 0건**이라는 뜻이다. 미재심 <!-- num:not_reassessed -->10,109행,
  `unsure` <!-- num:unsure -->47건은 확정으로 보고하지 않는다.
- 수용 성공과 바이트 동일은 **실행 의미의 검증이 아니다.**

## 6. 실제 이용 예시 (전부 실제 출력)

**① 맞는 입력 — 두 어셈블러 결과를 한 번에**

```
$ python3 scripts/asm_linter.py "add ecx, ecx"
[수용됨 (실행 의미는 미검증)] add ecx, ecx
  gnu_as: accepted  01c9
  clang:  accepted  01c9
  SDM 형태: form_match (동작 일치 판정 아님)
  바이트 왕복: same_bytes
종료 코드 0
```

**② 틀린 입력 — 두 도구의 진단을 나란히**

```
$ python3 scripts/asm_linter.py "mov rax, ecx"
[GNU as 거부] mov rax, ecx
  gnu_as: rejected   Error: operand type mismatch for `mov'
  clang:  rejected   error: invalid operand for instruction
종료 코드 1
```

**③ 핵심 — "됐는데 안 된 것"을 잡아낸다**

```
$ python3 scripts/asm_linter.py "adc ecx, ecx" --expect-row 23
```
