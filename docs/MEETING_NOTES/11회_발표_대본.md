## 0. 먼저 용어 세 개

| 말 | 뜻 |
|---|---|
| **어셈블한다** | 사람이 쓴 명령어 글자(`add ecx, ecx`)를 CPU가 읽는 숫자, 곧 **바이트**(`01 c9`)로 바꾼다 |
| **역어셈블한다** | 반대로 바이트(`01 c9`)를 다시 글자(`add ecx,ecx`)로 되돌린다 |
| **왕복 검사** | 글자 → 바이트 → 글자로 돌아왔을 때 처음 글자와 같은지 본다. 다르면 둘 중 하나가 잘못한 것이다 |

이 도구가 하는 일: **매뉴얼에서 명령어 글자를 만들어 → 바이트로 바꿔 보고 → 다시 글자로 되돌려서 → 처음과 같은지 확인한다.**

---

## 1. 이 프로젝트는 무엇인가 (한 문장)

> **Intel 매뉴얼에 적힌 명령어 인코딩 표를 그대로 테스트 입력으로 바꿔, 실제 어셈블러·디스어셈블러가 매뉴얼대로 처리하는지 전수 대조하는 도구다.**

SDM Vol.2의 인코딩 행 4,210개에서 어셈블리 <!-- num:입력줄 -->23,323줄을 자동 생성해 돌린다.

## 2. 왜 해야 하는가

1. **아무도 전수로 확인하지 않는 영역이다.** 어셈블러 테스트는 보통 "자주 쓰는 명령어가 되는가"를 본다.
   매뉴얼 4,210행이 **행 단위로** 제대로 처리되는지 확인한 자료는 없다.
2. **퍼징의 앞단이 비어 있다.** AsFuzzer 같은 기존 연구는 문법을 **망가뜨린** 입력을 넣는다.
   우리는 반대로 **매뉴얼상 정확한** 입력을 만든다. 퍼저의 시드로 쓰거나, 퍼저가 낸 차이를 분류하는 데 쓴다.
3. **차이가 났을 때 "누구 탓인지" 가려야 한다.** 도구 결함인지, 우리 입력 오류인지, 표기 차이인지,
   버전 지원 차이인지 구분하지 못하면 결과가 쓸모없다. 이번 라운드가 실제로 그 구분을 했다.

## 3. 파이프라인 — 숫자가 어떻게 흘러가는가

```
Intel 매뉴얼 표 4,210줄
        ↓ 매뉴얼 규칙대로 명령어 글자를 만든다 (1~4단계)
테스트 입력 23,323줄
        ↓ GNU as로 어셈블 (5단계)
   ┌────┴────┐
받아줌 23,219   거부 104          ← 예외 ①
   ↓ 역어셈블해서 원래 글자와 비교 (6단계)
   ┌────┴────┐
같음 13,228   다름 9,991          ← 예외 ②
   ↓ Clang으로도 똑같이 해서 대조 (8·9단계)
   ┌────┴────┐
완전 일치 23,020   갈림 211       ← 예외 ③
   ↓ 지정한 매뉴얼 행을 실제로 때렸는지 확인 (13단계)
                   못 때림 349    ← 예외 ④
```

핵심은 **10단계**다. 6단계에서 "다르다"고 나온 것을 사람이 판단하지 않고,
**역어셈블 결과를 다시 어셈블해서 바이트가 같은지** 기계로 재확인한다. LSS 결함도 이 경로로 찾았다.

# 예외 사항 분석

"예외"는 뜻대로 안 된 것 전부다. 여섯 가지가 나왔고 하나씩 원인을 봤다.

## 예외 ① — 어셈블러가 거부한 <!-- num:as거부 -->104건

### ①-A. 매뉴얼도 "안 된다"고 한 것 — <!-- num:기대된거부 -->87건 (정상)

매뉴얼에 **Invalid 44 / N.E. 38 / N.S. 5**로 적힌 행들이다. `push`, `pop`, `call`, `jmp`,
`arpl`, `bound`, `lds`, `les` 같은 **32비트 시절 명령어**이고 64비트 모드에서는 쓸 수 없다.

→ **어셈블러가 맞게 거부한 것이다. 오히려 정상 동작의 증거다.**

### ①-B. 매뉴얼은 "된다"는데 거부한 것 — <!-- num:valid거부 -->17건

원래 **56건**이었다. 그중 약 40건이 **우리 입력이 틀린 것**이어서 9/19에 고쳤고 17건이 남았다.

| 건수 | 무엇 | 왜 그런가 | 누구 탓 |
|---:|---|---|---|
| 5 | `vpmovqd xmmword ptr [eax], xmm0` → `operand size mismatch` | **매뉴얼 표기 오류로 확정.** 우리는 매뉴얼 줄(`xmm1/m128`)을 그대로 옮겼는데, 같은 페이지의 설명·Tuple Type(`Half Mem`)·형제 명령어 줄이 모두 `m64`를 가리킨다 | 매뉴얼 |
| 4 | `sysexit`, `sysret` → `ambiguous operand size` | **매뉴얼 표기의 구조적 한계.** SDM에 니모닉 글자가 같은 두 행(`0F 35` / `REX.W + 0F 35`)이 있어 구분할 수단이 없다. `sysexitd`/`sysexitq`로 쓰면 두 행 모두 시험 가능 | 표기 한계 |
| 3 | `mov ds, qword ptr [eax]` → `operand type mismatch` | 세그먼트 레지스터에 8바이트 메모리. **재심에서 구현 버그 아님으로 정리**(CPU 실험으로 접근 폭 확인) | 정리됨 |
| 2 | `lar ecx, rcx`, `lsl rcx, ecx` → `register type mismatch` | 앞뒤 레지스터 폭이 다르다. **REX.W 비트 하나로 두 자리의 폭을 따로 정할 수 없다** | 정리됨 |
| 2 | `vscatterdpd [eax + ymm1] {k1}, ymm0` → `invalid VSIB address` | **매뉴얼 표기 오류로 확정.** 쌍둥이 VPSCATTERDQ는 인덱스를 절반(`vm32x`)으로 적는데 VSCATTERDPD만 전체 크기(`vm32y`)로 적었다 | 매뉴얼 |
| 1 | `udb` → `no such instruction` | 매뉴얼에 `D6 UDB`로 정식 정의돼 있는데 as 2.42가 모른다. **버전 차이 — 2.46.1부터 받아준다**(오늘 확인) | 버전 |

### VPMOVQD 5건 — "왜 `xmmword ptr`로 썼나?"에 대한 답

매뉴얼 줄을 그대로 옮겼기 때문이다. PDF 원문(p.2054)이 이렇다.

```
EVEX.128.F3.0F38.W0 35 /r   VPMOVQD xmm1/m128 {k1}{z}, xmm2
```

`m128` = 16바이트 = `xmmword ptr`. **추출도 생성도 매뉴얼대로 했다. 틀린 것은 매뉴얼 줄이다.**
같은 페이지 안에 반대 근거가 셋 있다.

1. **같은 줄의 설명** — "Converts **2** quad-words … into **2** double-words" → 2 × 32비트 = **64비트**
2. **같은 페이지 Operand Encoding 표** — Tuple Type이 **`Half Mem`**(벡터 길이의 절반) → EVEX.128이면 **64비트**
3. **형제 명령어** — VPMOVDB `m32` / VPMOVDW `m64` / VPMOVQB `m16` / VPMOVQW `m32` / VPMOVWB `m64`.
   **전부 줄어든 크기인데 VPMOVQD만 `m128`이다**

도구로도 확인된다.

```
vpmovqd xmmword ptr [eax], xmm0  → 거부              (매뉴얼 줄 그대로)
vpmovqd qword ptr   [eax], xmm0  → 62 f2 7e 08 35 00   EVEX.128 = 노렸던 바로 그 행
vpmovqd xmmword ptr [eax], ymm0  → 62 f2 7e 28 35 00   EVEX.256 (m128은 ymm과 짝)
```

**그래서 이건 우리가 고칠 수 있다.** 오퍼랜드 열의 `m128` 대신 **Tuple Type을 읽어 크기를 정하면**
이 행을 실제로 시험할 수 있다. 거부 17건 중 **5건은 다음 라운드에서 해소 가능**하다.

### VSCATTERDPD 2건 — 같은 방법으로 확정했다

VSIB 명령어는 **인덱스 개수 = 데이터 원소 개수**다. 인덱스가 32비트, 원소가 64비트면
**인덱스 레지스터는 데이터의 절반**이어야 한다. 쌍둥이 명령어와 나란히 보면 바로 드러난다.

| EVEX | VPSCATTERDQ (매뉴얼) | VSCATTERDPD (매뉴얼) |
|---|---|---|
| 256 | `vm32x {k1}, ymm1` | **`vm32y {k1}, ymm1`** ← 어긋남 |
| 512 | `vm32y {k1}, zmm1` | **`vm32z {k1}, zmm1`** ← 어긋남 |

```
vscatterdpd [eax + ymm1] {k1}, ymm0  → 거부            (매뉴얼 줄 그대로)
vscatterdpd [eax + xmm1] {k1}, ymm0  → 67 62 f2 fd 29 a2 04   EVEX.256 = 노렸던 행
vpscatterdq [eax + xmm1] {k1}, ymm0  → 67 62 f2 fd 29 a0 04   쌍둥이, 매뉴얼 그대로 수용
```

scatter 계열 32건 중 거부는 이 2건뿐이고 쌍둥이는 전부 수용됐다.
**이것도 우리가 고칠 수 있다** — 인덱스 크기를 비율로 계산하면 된다.

### SYSEXIT/SYSRET 4건 — 매뉴얼 오류가 아니라 표기의 한계

매뉴얼에 이 두 줄이 나란히 있다. **니모닉 글자가 완전히 같다.**

```
0F 35           SYSEXIT   Fast return to privilege level 3 user code.
REX.W + 0F 35   SYSEXIT   Fast return to 64-bit mode privilege level 3 user code.
```

오퍼랜드가 없으니 REX.W를 표현할 문법도 없다. 그래서 as가 "어느 행인지 모르겠다"고 거부한다.

| 입력 | as | clang |
|---|---|---|
| `sysexit` (매뉴얼 그대로) | **거부** `ambiguous operand size` | **수용** — 조용히 `sysexitd`(`0f 35`) |
| `sysexitd` / `sysexitq` | 수용 `0f 35` / `48 0f 35` | 수용 |

**두 행 모두 시험할 수 있다.** 크기 접미사를 붙이면 된다.

**여기서 중요한 것:** clang은 경고 없이 REX.W 없는 행을 고른다. 매뉴얼 글자를 그대로 clang에 넣으면
`REX.W + 0F 35` 행은 **한 번도 시험되지 않은 채 "성공"으로 넘어간다.**
as의 거부는 불편해 보이지만 **"어느 행인지 모르겠다"는 정확한 신호**다.
이 4건은 뿌리가 예외 ④와 같다 — 같은 글자를 여러 SDM 행이 공유하는 문제다.

#### 덤으로 나온 것: 비REX.W 행에는 **두 도구가 공통으로 받는 표기가 없다**

`data/cases.csv`에 등록하면서 확인됐다.

| 입력 | GNU as | Clang |
|---|---|---|
| `sysexit` (매뉴얼 표기) | 거부 | **수용** `0f 35` |
| `sysexitd` | **수용** `0f 35` | 거부 |
| `sysexitq` | 수용 `48 0f 35` | 수용 `48 0f 35` |

REX.W 행(`48 0f 35`)은 `sysexitq`라는 공통 표기가 있지만, **비REX.W 행(`0F 35`)은
as와 clang이 받는 글자가 서로 다르다.** 차등 테스트에서 "같은 입력을 두 도구에 넣는다"는
전제가 이 행에서는 성립하지 않는다. SYSRET도 같다.

**→ 이 17건 안에서 어셈블러가 잘못한 것은 0건이다.** (전체 결론이 아니다 — 예외 ⑥의 LAR/LSL 참조) 매뉴얼 표기 오류 7건(VPMOVQD·VSCATTERDPD), 표기 한계 4건(SYSEXIT/SYSRET), 재심 완료 5건(MOV Sreg·LAR/LSL), 버전 차이 1건(UDB).
**이 중 11건은 우리 입력을 고치면 다음 라운드에서 실제로 시험할 수 있다.**

### 여기서 새로 나온 것: clang이 레지스터를 조용히 바꾼다

`lar`/`lsl`은 as가 거부하는데 clang은 받아준다. 그런데 **쓴 것과 다른 레지스터로 바꿔서 조립한다.**

| 입력 | clang 18 | clang 23.1 | clang 24(trunk) |
|---|---|---|---|
| `lar ecx, rcx` | `lar ecx,ecx` (`0f 02 c9`) | **`lar ecx,cx`** | `lar ecx,ecx` |
| `lsl rcx, ecx` | `lsl rcx,rcx` (`48 0f 03 c9`) | — | — |

`rcx`라고 썼는데 결과는 `ecx`(또는 `cx`)다. **경고도 없다.** 게다가 **버전마다 고른 레지스터가 다르다.**
확정할 준비가 안 된 새 관측이라 예외 ⑤로 넘겨 추적한다.

## 예외 ② — 역어셈블 결과가 원래 글자와 다른 <!-- num:왕복다름 -->9,991건

**대부분 버그가 아니다.** 같은 뜻을 다르게 적은 것이다.

| 건수 | 무엇이 달라졌나 | 예시 | 왜 |
|---:|---|---|---|
| <!-- num:표기_숫자 -->7,736 | 숫자 표기 | `adc al, 1` → `adc al,0x1` | objdump는 숫자를 항상 16진수로 쓴다. **값은 같다** |
| <!-- num:표기_브로드캐스트 -->860 | 브로드캐스트 표기 | `qword ptr [eax]{1to2}` → `QWORD BCST [eax]` | 같은 인코딩의 다른 이름 |
| <!-- num:표기_별명 -->729 | 같은 명령의 다른 이름 | `cmovc` → `cmovb` | 한 명령에 별명이 여럿. `jnz`=`jne`, `sal`=`shl`도 같다 |
| <!-- num:표기_숨은오퍼랜드 -->210 | 숨은 오퍼랜드 | `cmps byte ptr [eax], …` → `cmps BYTE PTR ds:[esi],BYTE PTR es:[edi]` | 문자열 명령은 레지스터를 자동으로 쓴다. objdump가 펼쳐 보여준다 |
| 118 | 크기 표기 | `call far ptr [eax]` → `call FWORD PTR [eax]` | 생략한 크기를 objdump가 채운다 |
| 86 | 인코딩 형식 표시 | `vpslldq …` → `{evex} vpslldq …` | 같은 글자가 두 형식으로 인코딩될 수 있어 표시해 준다 |
| 71 | x87 스택 표기 | `fadd st(0), st(0)` → `fadd st,st(0)` | `st(0)`을 짧게 `st`로 쓴다 |
| 42 | 분기 대상 | `call .Ltarget` → `call 0x0` | 라벨 이름은 바이트에 안 남는다. 복원할 방법이 없다 |

**어떻게 확신하는가:** 사람이 눈으로 판단하지 않았다. **objdump가 내놓은 글자를 다시 어셈블해서
바이트가 원래와 같은지** 기계로 확인했다 → <!-- num:재조립동일 -->9,834건이 바이트까지 동일.
표기만 다르고 뜻은 같다는 증거다.

## 예외 ③ — GNU as와 Clang이 갈린 211건

### ③-A. 둘 다 받았는데 바이트가 다름 — <!-- num:바이트다름 -->125건

| 예시 | as | clang | 왜 |
|---|---|---|---|
| `call dword ptr [eax]` | `67 66 ff 18` | `67 ff 18` | **clang이 `66` 프리픽스를 안 붙인다** |
| `iret` | `cf` | `66 cf` | 반대로 여기선 clang이 붙인다 |

→ 어느 쪽이 틀렸다고 단정하지 않고 **차이로 기록**했다. 판정하려면 매뉴얼 본문 해석이 더 필요하다.

### ③-B. as만 받아준 것 — <!-- num:as만수용 -->74건

`bndcl bnd0, dword ptr [rax]` → clang은 `invalid instruction mnemonic 'bndcl'`.
**MPX 기능 명령어인데 Intel이 사실상 폐기해 clang이 지웠다.** (bndmov 11 / movsxd 10 / ud0 5건 등)

### ③-C. clang만 받아준 것 — <!-- num:clang만수용 -->12건

`call word ptr [eax]` → as는 `operand type mismatch`.
**64비트 모드에서 2바이트 간접 호출을 as가 막는다.** 엄격도 차이다.

**→ 두 어셈블러는 99.5%에서 바이트까지 같고, 갈리는 지점은 "폐기된 기능을 남겼는가"와 "프리픽스를 어떻게 붙이는가"다.**

## 예외 ④ — 받아줬는데 사실은 시험을 못 한 <!-- num:미타격합계 -->349건

매뉴얼은 같은 명령어를 **여러 줄로** 나눠 적는다.

- 23행 `ADC r32, r/m32` → 바이트 `13`
- 22행 `ADC r/m32, r32` → 바이트 `11`

23행을 시험하려고 `adc ecx, ecx`를 넣었는데 어셈블러는 `11`을 만들었다. **어셈블러가 잘못한 게 아니다.**
둘 다 맞는 답이고 하나를 고른 것뿐이다. 문제는 **우리가 시험하려던 행은 결국 못 건드렸다**는 것이다.
통과 여부만 보는 도구는 이걸 "성공"으로 넘긴다.

| 건수 | 원인 | 예 | 고칠 수 있나 |
|---:|---|---|---|
| <!-- num:미타격_대칭행 -->264 | **두 줄을 글자로 구분할 방법이 없다** | `adc cl, cl`은 앞뒤가 같아 어느 줄인지 지정 불가 | **원리상 불가능.** 도구의 한계로 명시해야 한다 |
| <!-- num:미타격_분기축약 -->64 | **어셈블러가 짧은 형식을 골랐다** | `ja .Ltarget`에 긴 형식을 기대했는데 `77 fe`가 나옴 | **가능.** 점프 목표를 멀리 두면 긴 형식이 강제된다 |
| <!-- num:미타격_rexw -->21 | **REX.W가 안 붙었다** | `lar ecx, word ptr [eax]` | **일부 가능.** 입력 형태를 고쳐야 한다 |

**→ "349건 시험 못 함"이 아니라 "원리상 불가능 264 + 고칠 수 있는 85"다.** 85건이 다음 라운드 1순위다.

### 오늘 풀린 것: MPX는 버그가 아니라 버전 차이였다

`bndcl bnd0, dword ptr [rax]`를 도구 7종에 넣어 봤다.

| 도구 | 결과 |
|---|---|
| as **2.42** | **수용** `f3 0f 1a 00` |
| as 2.45 / 2.46.1 / 2.47 | **거부** — `` `bndcl' is not supported on `x86_64' `` |
| Godbolt gas 2.42 / 2.44 | 수용 / 거부 |
| clang 18 / 23.1 / 24 | 전부 거부 |

**→ Intel이 MPX를 폐기하면서 binutils가 2.42 이후 지원을 뺐다.** "as가 이상하게 관대하다"고
표시했던 것은 **우리가 낡은 버전을 쓰고 있었기 때문**이다. 도구 결함이 아니다.

→ 나머지는 **확정으로 보고하지 않는다.** 근거가 부족한 건 미확인으로 두는 것이 이 프로젝트의 원칙이다.

### 오늘 새로 확인된 것: LAR/LSL의 REX.W 행을 as가 만들지 못한다 (왕복 실패 2번째 유형)

미확정으로 남아 있던 "clang이 레지스터를 조용히 바꾼다"를 파고들다가 **더 큰 것**이 나왔다.
clang의 치환은 곁가지였고, 문제는 **GNU as 쪽**이다.

**먼저 매뉴얼부터.** PDF 원문(p.651, p.691)의 REX.W 행이 서로 반대로 적혀 있다.

```
LAR   REX.W + 0F 02 /r   LAR r32, r64/m16      ← 목적지 r32, 원본 r64
LSL   REX.W + 0F 03 /r   LSL r64, r32/m16      ← 목적지 r64, 원본 r32
각주 1: Regardless of operand size, only bits 15:0 of a register source operand are used.
```

REX.W 비트 **하나**로 두 자리의 폭을 따로 정할 수는 없다. 각주가 "원본은 하위 16비트만 쓴다"고
하므로 원본 폭은 의미가 없는데, 표기는 그걸 폭으로 적어 두 행이 어긋나 보인다.
**우리 생성기는 이 표기를 그대로 옮겨 `lar ecx, rcx` / `lsl rcx, ecx`를 만들었고 as가 거부했다.**

**그런데 대칭으로 써 보면 진짜 문제가 드러난다.**

| 입력 | GNU as 2.42~2.47 | Clang 18 |
|---|---|---|
| `lar ecx, ecx` | `0f 02 c9` | `0f 02 c9` |
| `lar rcx, rcx` | **`0f 02 c9`** ← REX.W가 사라진다 | `48 0f 02 c9` |
| `lsl rcx, rcx` | **`0f 03 c9`** | `48 0f 03 c9` |

**as는 `rcx`라고 쓴 것을 조용히 32비트 인코딩으로 바꾼다. 경고가 없다.**
AT&T 문법으로도, 크기 접미사를 붙여도 마찬가지다 — `lar %rcx,%rcx`, `larq %rcx,%rcx` 모두 `0f 02 c9`다.

### ⚠️ 판정 정정 (2026-09-21, 외부 검토 반영)

처음에 **"as는 어떤 문법으로도 REX.W 형식을 만들 수 없다"고 적었으나 틀렸다.**
`rex64` 의사 프리픽스를 쓰면 만들어진다.

```
lar rcx, rcx          → 0f 02 c9        ← 기본 렌더링. REX.W가 빠진다
rex64 lar rcx, rcx    → 48 0f 02 c9     ← 원하는 행이 나온다
```

**이 사실은 결론을 약화시키는 게 아니라 강화한다.** ISA 표현력의 한계가 아니라
**어셈블러의 기본 인코딩 선택 문제**임이 확정되기 때문이다. 사용자가 유효한 SDM 행을
명시적으로 지정(`rcx`)했는데 경고 없이 다른 행을 고른다.

### 이미 보고된 결함이다

외부 검토에서 확인했다 — binutils **bug gas/32813 "Missing REX prefix for LSL"**.
보고자 댓글: *"Earlier versions of gas correctly added the REX prefix, and other assemblers
(I tested nasm and XED) also encode this correctly with a REX prefix."*

원인도 특정됐다. 2022년 커밋 **"x86: correct handling of LAR and LSL"** 이 레지스터 크기 일치를
강제하고 디스어셈블러를 16비트 전용(`Mw`)으로 분리하면서 생긴 **회귀**다. 같은 커밋이
`lar ecx, rcx` 거부(예외 ①-B 2건)의 원인이기도 하다.

**우리가 처음 찾은 것이 아니다.** 대신 **우리 파이프라인이 실제로 보고된 binutils 결함을
독립적으로 재현해 냈다**는 검증 사례가 된다.

**그래서 왕복이 깨진다.** 네 버전 전부에서 같다.

```
바이트     48 0f 02 c9          ← SDM의 REX.W + 0F 02 /r 행 (Valid)
objdump →  lar rcx,rcx          ← 올바른 표시
as      →  0f 02 c9             ← REX.W가 사라진 다른 바이트. 오류도 경고도 없다
```

| 도구 | 2.42 | 2.45 | 2.46.1 | 2.47 |
|---|---|---|---|---|
| objdump 표시 | `lar rcx,rcx` | 〃 | 〃 | 〃 |
| 그 글자를 as에 | `0f 02 c9` | 〃 | 〃 | 〃 |
| 원본과 같나 | **다름** | **다름** | **다름** | **다름** |

LSL(`48 0f 03 c9` → `0f 03 c9`)도 같다.

#### 예외 ⑥(LSS)과 비교하면 — 이쪽이 더 위험하다

| | LSS/LFS/LGS (예외 ⑥) | LAR/LSL REX.W (오늘 확인) |
|---|---|---|
| objdump 표시 | **틀림** (`FWORD` = 48비트) | **맞음** (`lar rcx,rcx`) |
| 그 출력을 as에 | **거부** — 시끄럽게 실패 | **수용, 다른 바이트** — **조용히 실패** |
| 알아채기 | 에러가 나서 바로 보인다 | **아무 표시가 없다** |

**거부는 눈에 띄지만 조용한 바이트 변경은 안 띈다.** 역어셈블 → 수정 → 재조립 흐름에서
이런 손실은 그대로 통과한다.

#### 어디까지 확정인가

- **확정:** `48 0f 02 c9`는 SDM의 Valid 행이고, objdump 출력을 as에 다시 넣으면 **바이트가 달라진다.**
  as에는 이 인코딩을 만드는 문법이 없다. 2.42·2.45·2.46.1·2.47에서 재현. clang은 만들 수 있다.
- **미확정:** 두 인코딩의 **실행 의미가 다른지는 확인하지 않았다.** 32비트 쓰기는 상위 32비트를
  0으로 채우므로 결과가 같을 수 있다. **그래서 오늘은 버그 건수를 3→4로 올리지 않는다.**
  올리려면 CPU 실행으로 두 인코딩의 결과를 대조해야 한다.
- **우리 파이프라인이 이걸 놓친 이유:** 매뉴얼 행이 비대칭(`r32, r64`)이라 우리는 `lar ecx, rcx`를
  만들었고 as가 거부했다. **대칭형 `lar rcx, rcx`를 만들었다면 잡혔을 것이다.**
  → 예외 ④의 "REX.W 미부착 21건"에 lar 4 · lsl 4가 들어 있던 것이 같은 뿌리였다.

## 예외 ⑥ — 진짜 결함 1종류 3사례

**objdump가 LSS / LFS / LGS를 잘못 보여준다.**

```
매뉴얼:  LSS r64, m16:64   → 16비트 + 64비트 = 80비트짜리 메모리

1) 매뉴얼대로 써서 어셈블   lss rcx, tbyte ptr [rax]   → 48 0f b2 08   성공
2) 그 바이트를 역어셈블      → lss rcx,FWORD PTR [rax]
                                     ↑ FWORD는 48비트. 80비트인데 틀리게 적었다
3) 그 글자를 다시 어셈블      → 거부됨
```

**왜 문제인가:** 역어셈블 결과를 그대로 다시 쓸 수 없다. 바이너리를 분석해 코드를 복원하는 작업이 여기서 막힌다.

**얼마나 확실한가:** 오늘 binutils **2.42 · 2.45 · 2.46.1 · 2.47(최신)** 을 직접 빌드해 네 버전 모두 확인했고,
Godbolt의 2.42 · 2.44에서도 같았다.

**여기서 한 걸음 더 나갔다.** objdump가 낸 `lss rcx,FWORD PTR [rax]`를
**clang은 받아준다**(같은 바이트 `48 0f b2 08`을 만든다). 즉 문법적으로 불가능한 글자가 아니라,
**as가 `FWORD`(48비트)와 `rcx`(64비트) 조합을 허용하지 않는 것**이다.
→ 정확한 이름은 **GNU objdump의 표시 결함**이다. "objdump와 as가 서로 안 맞는다"는 증상일 뿐이다.
**어셈블러는 정상이다** — 의도한 기계어 `48 0f b2 08`이 정확히 생성된다. 재조립이 깨지는 것은
objdump가 내놓은 **잘못된 크기 표기 때문**이다. 이 사례로 **실행 의미 오류나 보안 취약점이 입증되지는 않는다.**
llvm-objdump는 크기를 아예 안 적어서(`lss rcx, [rax]`) 이 문제를 피한다.

**왜 3건인가:** LSS·LFS·LGS는 하는 일이 같은 형제 명령어다.
**공통된 표시 결함 유형 1개가 세 명령어에서 관측된 것**이지, 어셈블러 코드 생성 버그 3개를 찾은 것이 아니다.

## 5. 도구의 결과

> **어셈블러 쪽 결함은 "0건"이라고 말하면 안 된다.** 말할 수 있는 것은
> **"기존 triage가 확정 표시한 어셈블러 버그가 0건"** 까지다. 실제로는 GNU as의 LAR/LSL REX.W

> 오류인지, 표기 차이인지, 버전 차이인지 분류해서** 사람이 볼 것만 남긴다.

- "버그 0건"은 **우리가 확정할 수 있는 것이 0건**이라는 뜻이다. 미재심 <!-- num:not_reassessed -->10,109행,

- 수용 성공과 바이트 동일은 **실행 의미의 검증이 아니다.**

## 6. 실제 이용 예시 (전부 실제 출력)

**① 맞는 입력 — 두 어셈블러 결과를 한 번에**

```
$ python3 scripts/asm_linter.py "add ecx, ecx"
[수용됨 (실행 의미는 미검증)] add ecx, ecx
  gnu_as: accepted  01c9
  clang:  accepted  01c9
  SDM 형태: form_match (동작 일치 판정 아님)
  바이트 왕복: same_bytes
종료 코드 0
```

**② 틀린 입력 — 두 도구의 진단을 나란히**

```
$ python3 scripts/asm_linter.py "mov rax, ecx"
[GNU as 거부] mov rax, ecx
  gnu_as: rejected   Error: operand type mismatch for `mov'
  clang:  rejected   error: invalid operand for instruction
종료 코드 1
```

**③ 핵심 — "됐는데 안 된 것"을 잡아낸다**

```
$ python3 scripts/asm_linter.py "adc ecx, ecx" --expect-row 23
[추가 확인 필요] adc ecx, ecx          ← SDM 23행 = ADC r32, r/m32 (13 /r)
  gnu_as: accepted  11c9
  clang:  accepted  11c9
  바이트 왕복: same_bytes
  [encoding_selection] 지정한 SDM 행과 다른 인코딩을 관측했습니다.
집계: needs_review=1
```

두 어셈블러가 다 받아줬고 바이트도 같고 왕복도 된다. 보통은 "통과"다.
그런데 **매뉴얼 23행을 시험하려 했는데 실제로는 다른 행이 나왔다.** 통과 여부만 보는 도구는 이걸 놓친다.
이런 경우가 예외 ④의 349건이다.

**④ 파일 통째로 + JSON**

```bash
python3 scripts/asm_linter.py -f mycode.s --format json --output report.json
```
