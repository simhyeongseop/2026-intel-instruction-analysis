## 4. 발견 — objdump의 LSS/LFS/LGS 표시 (오늘 4개 버전에서 재현)

**증상:** objdump의 Intel 문법 출력이 REX.W 형식을 `FWORD PTR`(48비트)로 표시하는데,
**그 출력을 같은 도구모음에 다시 넣으면 거부된다.** 역어셈블 출력이 입력으로 되돌아가지 않는다.

```
SDM p.658:  REX.W + 0F B2 /r   LSS r64, m16:64   (Valid)
                                        └─ 16+64 = 80비트

$ as --64 -mintel64  (입력)  lss rcx, tbyte ptr [rax]    → 48 0f b2 08   수용
$ objdump -d -M intel        48 0f b2 08 →  lss rcx,FWORD PTR [rax]
$ as --64 -mintel64  (그 출력을 다시)                     → 거부
                             Error: incorrect register `rcx' used with `l' suffix
```

`llvm-objdump`는 같은 바이트를 `lss rcx, [rax]`로 출력한다. 크기를 **표기하지 않아서** 틀린 크기를
적지 않고, 그 출력은 다시 조립된다. 즉 "틀린 크기를 적는 쪽"은 objdump다.

### 오늘 재빌드해서 확인한 버전별 관측

소스에서 직접 빌드해 같은 명령으로 관측했다(시스템 도구는 그대로 두었다).

| binutils | objdump -M intel 표시 | 그 출력 재조립 | SDM 표기(`tbyte`) 조립 | UDB |
|---|---|---|---|---|
| 2.42 (Ubuntu 24.04 기본) | `lss rcx,FWORD PTR [rax]` | 거부 | 수용 `48 0f b2 08` | **거부** |
| 2.45 | `lss rcx,FWORD PTR [rax]` | 거부 | 수용 `48 0f b2 08` | **거부** |
| 2.46.1 | `lss rcx,FWORD PTR [rax]` | 거부 | 수용 `48 0f b2 08` | **수용** |
| 2.47.20260726 | `lss rcx,FWORD PTR [rax]` | 거부 | 수용 `48 0f b2 08` | **수용** |

- **LSS 표시·왕복 실패는 최신 2.47에서도 그대로다.** 3사례(LSS/LFS/LGS)는 서로 다른 버그가 아니라
  같은 결함의 세 명령어다.
- **UDB는 버그가 아니라 지원 차이다.** SDM p.1436에 `D6 UDB`로 정식 정의돼 있고, 2.42는 거부하지만
  2.46.1부터 수용한다. 구버전의 한계일 뿐이다.

### 옆에서 같이 나온 관측

`-mintel64` 옵션이 없으면 as 2.42는 SDM 표기 그대로인 `lss rcx, tbyte ptr [rax]`도 거부한다
(`operand size mismatch`). 같은 입력이 옵션에 따라 수용/거부가 갈린다. 우리 파이프라인은
`--64 -mintel64`로 고정해 돌린다. **"어셈블러가 거부했다"는 말은 옵션까지 적어야 뜻이 통한다.**

## 5. 거부한 <!-- num:as거부 -->104건 — 무엇이고 왜 그런가

거부를 둘로 나눠야 한다. **매뉴얼도 안 된다고 한 것**과 **매뉴얼은 된다는데 거부한 것**은 뜻이 다르다.

### 5.1 매뉴얼도 "안 된다"고 한 것 — <!-- num:기대된거부 -->87건 (정상 동작)

매뉴얼에 Invalid 44 / N.E. 38 / N.S. 5로 적힌 행이다. `push`, `pop`, `call`, `jmp`, `arpl`,
`bound`, `lds`, `les` 같은 **32비트 시절 명령어**로 64비트 모드에서는 쓸 수 없다.
→ **어셈블러가 맞게 거부한 것이다. 정상 동작의 증거다.**

### 5.2 매뉴얼은 "된다"는데 거부한 것 — <!-- num:valid거부 -->17건

9/16 자체 점검에서 "56건 중 약 40건은 우리 생성기 탓"이라고 정리했고, **그 40건을 고치고 다시 돌렸다.**

| 유형 | 9/16 | 수정 내용 | 현재 |
|---|---:|---|---:|
| 매뉴얼 표기 `k1+1`, `zmm2+3`을 그대로 입력 | 18 | 표기 정규화 (`k1+1` → `k1`) | 0 |
| 고정 크기 m512에 `zmmword ptr` | 10 | 크기 지시자 제거 (`fxsave [eax]`) | 0 |
| 암묵 오퍼랜드를 명시로 입력 | 7 | `<EAX>`, `<XMM0-7>` 자리 제거 | 0 |
| `rep lods al` 등 표기 관례 | 4 | 누산기 표기 교정 | 0 |
| 추출 잔여 문자열 `imm8/r` | 2 | 3단계에서 걸러냄 | 0 |
| 모드·폭 제약 미반영 (`umonitor cx`) | 3 | 주소 폭에 맞춘 레지스터 선택 | 0 |
| **우리 입력 결함 소계** | **~40** | | **0** |

**남은 <!-- num:valid거부 -->17건 전부**를 오류 메시지까지 확인해 원인별로 갈랐다.

| 건수 | 입력 → 오류 | 왜 그런가 | 누구 탓 |
|---:|---|---|---|
| 5 | `vpmovqd xmmword ptr [eax], xmm0` → `operand size mismatch` | 매뉴얼은 `m128`(16바이트)로 적었는데 실제로 쓰는 건 8바이트다 | **매뉴얼 표 오탈자 추정** |
| 4 | `sysexit`, `sysret` → `ambiguous operand size` | 매뉴얼은 오퍼랜드 없이 적는데 as는 `sysexitq`/`sysretq`만 받는다 | 표기 관례 — 판단 보류 |
| 3 | `mov ds, qword ptr [eax]` → `operand type mismatch` | 세그먼트 레지스터에 8바이트 메모리 | 재심 완료, 구현 버그 아님 |
| 2 | `lar ecx, rcx`, `lsl rcx, ecx` → `register type mismatch` | REX.W 비트 하나로 두 자리의 폭을 따로 정할 수 없다 | 재심 완료, 구현 버그 아님 |
| 2 | `vscatterdpd [eax + ymm1] {k1}, ymm0` → `invalid VSIB address` | 주소용 벡터 레지스터 크기가 매뉴얼 표와 안 맞는다 | 판단 보류 |
| 1 | `udb` → `no such instruction` | as 2.42가 모른다 — **2.46.1부터 받아준다**(오늘 확인) | 버전 지원 차이 |

**→ 17건 중 어셈블러가 잘못한 것은 0건이다.**

## 6. 역어셈블 결과가 원래 글자와 다른 <!-- num:왕복다름 -->9,991건

|---:|---|---|---|

## 8-1. 지정한 SDM 행을 시험하지 못한 <!-- num:미타격합계 -->349건 — 원인별로 나누면

"몇 건이 안 됐다"로 두면 **고칠 수 있는 것과 구조적 한계가 섞인다.** 관측한 바이트와 지정 opcode를
대조해 원인을 나눴다.

| 건수 | 원인 | 예 | 고칠 수 있나 |
|---:|---|---|---|
| <!-- num:미타격_대칭행 -->264 | **같은 문법에 SDM 행이 둘** | `adc cl, cl` → 지정 `12 /r`, 실제 `10 c9` | **원칙적으로 불가.** 오퍼랜드가 대칭이라 Intel 문법으로 두 행을 구분할 수단이 없다 |
| <!-- num:미타격_분기축약 -->64 | **분기 변위 축약** | `ja .Ltarget` → 지정 `0F 87 cd`(rel32), 실제 `77 fe`(rel8) | **고칠 수 있다.** 타깃을 rel8 범위 밖에 두면 긴 형식을 강제할 수 있다 |
| <!-- num:미타격_rexw -->21 | **REX.W 미부착** | `lar ecx, word ptr [eax]` → 지정 `REX.W + 0F 02 /r`, 실제 `67 0f 02 08` | **일부 가능.** LAR/LSL은 재심에서 정리된 건, `call/jmp far ptr`은 입력 형태를 바꿔야 한다 |

→ **"349건을 시험 못 했다"가 아니라 "구조적 한계 264건 + 우리가 고칠 수 있는 85건"이다.**
264건은 도구의 한계로 명시해야 할 것이고, 85건은 다음 라운드의 작업 목록이다.

이 분류는 `scripts/check_report_numbers.py`가 `out/lint/observations.jsonl`에서 다시 계산한다.
바이트와 지정 opcode 문자열만 보고 나눈 것이며, 의미가 같은지는 판정하지 않았다.

> 13단계 manifest의 `different_encoding`은 <!-- num:different_encoding -->347건이다. 차이 2건은
> `data/cases.csv`의 보충 사례(`lar rcx, rcx`, `lsl rcx, rcx`)이고, 생성 입력 347 + 보충 2 = 349다.

## 9. 도구 시연 — `asm_linter`

한 줄을 넣으면 두 어셈블러의 수용 여부, 실제 바이트, 역어셈블, 바이트 왕복을 함께 보여준다.
아래는 **오늘 실제 실행한 출력 그대로**다.

```
$ python3 scripts/asm_linter.py "add ecx, ecx"
[수용됨 (실행 의미는 미검증)] add ecx, ecx
  gnu_as: accepted  01c9
    objdump: add    ecx,ecx
  clang: accepted  01c9
    objdump: add    ecx,ecx
  SDM 형태: form_match (동작 일치 판정 아님)
  바이트 왕복: same_bytes
집계: accepted=1
종료 코드 0. 0도 전체 ISA 적합성이나 CPU 실행 안전성을 보증하지 않습니다.
```

`.s` 파일·stdin·JSON/JSONL 출력·종료 코드를 지원해 다른 실험에 붙일 수 있다.
판정의 방향(무엇을 문제로 볼지)은 우리가 정한 것이므로 완전히 객관적이지 않다.

### 아직 여쭐 것

**① 퍼징 대상을 언제 정할까요?** (지금은 미정)

대상에 따라 **도구가 해야 할 일이 정반대가 됩니다.**

| 대상 | 넣는 입력 | 판정 근거(오라클) | 찾는 결함 |
|---|---|---|---|
| 어셈블러 (as/clang) | 어셈블리 **텍스트** | SDM 표 + 다른 어셈블러 | 매뉴얼대로 쓴 문법을 거부, 틀린 바이트 |
| 디스어셈블러 (objdump) | **바이트** | 재조립 왕복 + 다른 디코더 | 표시가 틀림, 출력이 입력으로 안 돌아옴 |
| 에뮬레이터 (QEMU) | 실행 가능한 **프로그램** | 실제 CPU 실행 결과 | 실행 결과가 실제 CPU와 다름 |

예를 들어 **파서 크래시를 찾는 퍼징이라면 "거부된 입력"이 가장 중요한 자료인데, 시드 생성기로 쓴다면
거부된 입력은 버려야 합니다.** 같은 도구가 필터가 되기도 하고 수집기가 되기도 해서, 대상이 정해지지
않으면 통과/보관 정책을 정할 수 없습니다.

지금까지 찾은 LSS는 **디스어셈블러** 결함이고, 1~10단계는 어셈블러·디스어셈블러 쪽,
11·12단계가 에뮬레이터/CPU 쪽 인프라입니다.

**② objdump 표시 결함을 binutils에 보고해도 됩니까?**

보고 = 공개 버그 추적 시스템(Sourceware Bugzilla)에 최소 재현 입력(바이트 4개), 관측 출력, 기대 출력,
버전, 환경을 적어 이슈를 여는 것입니다. 2.47에서도 재현되는 것을 확인했습니다.
아직 **기존 보고를 검색하지 않았고** 새로 보고하지도 않았습니다.

## 부록. 용어

| 용어 | 뜻 |
|---|---|
| 어셈블한다 | 명령어 글자(`add ecx, ecx`)를 CPU가 읽는 바이트(`01 c9`)로 바꾼다 |
| 역어셈블한다 | 반대로 바이트를 다시 글자로 되돌린다 |
| 왕복 검사 | 글자 → 바이트 → 글자로 돌아왔을 때 처음과 같은지 본다. 다르면 둘 중 하나가 잘못한 것이다 |
| REX.W | 64비트 오퍼랜드 크기를 지정하는 프리픽스 비트 (0x48의 W) |
| FWORD / TBYTE | 48비트 / 80비트 메모리 크기 표기 |
| m16:64 | 16비트 세그먼트 셀렉터 + 64비트 오프셋 = 80비트 |
| 차등 테스트 | 같은 입력을 여러 도구에 넣고 결과 차이로 결함을 찾는 방법 |
| VEX / EVEX | AVX·AVX-512의 인코딩 형식. legacy opcode 필드로는 대조할 수 없다 |
| 암묵 오퍼랜드 | 매뉴얼이 `<EAX>`처럼 적는, 문법에 쓰지 않는 자리 |
