## 1. 프로젝트 목표

> **Intel 매뉴얼(SDM)에 적힌 명령어 인코딩 표를 그대로 테스트 입력으로 바꿔, 실제 어셈블러·디스어셈블러가
> 매뉴얼대로 처리하는지 전수 대조하는 도구를 만든다.**

- 매뉴얼의 인코딩 행 **4,210개**를 데이터로 만든다.
- 그 행에서 어셈블리 입력 **<!-- num:입력줄 -->23,323줄**을 자동 생성한다.
- 어셈블 → 역어셈블 → 재조립 → 두 어셈블러 대조까지 자동으로 돌린다.
- 차이가 나면 **원인별로 분류해서** 사람이 볼 것만 남긴다.

**최종 산출물은 도구다.** 버그 사례집이 아니라 다른 퍼징 실험에서 쓸 수 있는 도구를 만드는 것이 목표다.

### 먼저 용어 세 개

| 말 | 뜻 |
|---|---|
| **어셈블한다** | 명령어 글자(`add ecx, ecx`)를 CPU가 읽는 **바이트**(`01 c9`)로 바꾼다 |
| **역어셈블한다** | 반대로 바이트를 다시 글자로 되돌린다 |
| **왕복 검사** | 글자 → 바이트 → 글자로 돌아왔을 때 처음과 같은지 본다. 다르면 둘 중 하나가 잘못한 것이다 |

## 2. 필요성 — 왜 해야 하는가

**① 아무도 전수로 확인하지 않는 영역이다.**
어셈블러 테스트는 보통 "자주 쓰는 명령어가 되는가"를 본다. 매뉴얼에 적힌 4,210개 행이
**행 단위로** 제대로 처리되는지 확인한 자료는 없다.

**② 퍼징의 앞단이 비어 있다.**
AsFuzzer 같은 기존 연구는 문법을 **망가뜨린** 입력을 넣는다. 우리는 반대로 **매뉴얼상 정확한**
입력을 만든다. 퍼저의 시드로 쓰거나, 퍼저가 낸 차이를 분류하는 오라클로 쓸 수 있다.

**③ 차이가 났을 때 "누구 탓인지" 가려야 한다.**
도구 결함인지, 우리 입력 오류인지, 표기 차이인지, 버전 지원 차이인지 구분하지 못하면 결과가 쓸모없다.
이번 라운드가 실제로 그 구분을 했다 — 9/16에 "우리 탓"으로 지목한 40건을 고치고 다시 돌렸다.

**④ 실제로 쓸 데가 있다.**
바이너리를 분석해 코드를 복원하는 작업은 역어셈블 결과가 다시 조립된다는 전제 위에 선다.
그 전제가 깨지는 지점을 찾는 것이 예외 ⑥이다.

# 6. 예외 분석

## 예외 ① — 어셈블러가 거부한 <!-- num:as거부 -->104건

### ①-A. 매뉴얼도 "안 된다"고 한 것 — <!-- num:기대된거부 -->87건 (정상)

매뉴얼에 **Invalid 44 / N.E. 38 / N.S. 5**로 적힌 행이다. `push`, `pop`, `call`, `jmp`, `arpl`,
`bound`, `lds`, `les` 같은 **32비트 시절 명령어**로 64비트 모드에서는 쓸 수 없다.

→ **어셈블러가 맞게 거부한 것이다. 오히려 정상 동작의 증거다.**

### ①-B. 매뉴얼은 "된다"는데 거부한 것 — <!-- num:valid거부 -->17건

원래 56건이었고 그중 약 40건이 **우리 입력 오류**여서 9/19에 고쳤다. 남은 17건을
**오늘 도구 7종(as 2.42/2.45/2.46.1/2.47 + clang 18/23.1/24)** 에서 다시 확인했다.

| 건수 | 입력 | as 2.42~2.47 | clang 18/23/24 | 원인 분석 |
|---:|---|---|---|---|
| 5 | `vpmovqd xmmword ptr [eax], xmm0` | 전부 거부 `operand size mismatch` | 전부 거부 | **매뉴얼 표기 오류로 확정**(아래 별도 분석). 우리 입력은 매뉴얼 줄을 그대로 옮긴 것이고, 매뉴얼 줄 자체가 같은 페이지의 다른 정보와 모순된다 |
| 4 | `sysexit`, `sysret` | 전부 거부 `ambiguous operand size` | **수용 → `sysexitd`(`0f 35`)** | **매뉴얼 표기의 구조적 한계**(아래 별도 분석). 두 SDM 행의 니모닉 글자가 같아 구분할 수단이 없다. `sysexitd`/`sysexitq`로 쓰면 **두 행 모두 시험 가능** |
| 3 | `mov ds, qword ptr [eax]` | 전부 거부 `operand type mismatch` | 전부 거부 | 세그먼트 레지스터에 8바이트 메모리. 재심에서 CPU 실험으로 실제 접근 폭을 확인해 **구현 버그 아님**으로 정리 |

| 1 | `udb` | 2.42·2.45 거부 / **2.46.1·2.47 수용 `d6`** | 전부 거부 | 매뉴얼에 `D6 UDB`로 정식 정의. **버전 지원 차이** |

**→ 이 17건 안에서 어셈블러가 잘못한 것은 0건이다.** (전체 결론이 아니다 — 예외 ⑥의 LAR/LSL 참조) 그중 **7건(VPMOVQD 5 + VSCATTERDPD 2)은 매뉴얼 표기 오류로 확정**했고, **4건(SYSEXIT/SYSRET)은 매뉴얼 표기로 두 행을 구분할 수 없는 한계**로 정리했다. **이 11건은 우리 입력을 고치면 다음 라운드에서 시험할 수 있다.** 남는 6건은 재심 완료 5건(LAR/LSL·MOV Sreg)과 버전 차이 1건(UDB)이다.

#### ①-B 심층 분석: VPMOVQD 5건은 매뉴얼 표기 오류가 맞다 (2026-09-21 확정)

**"왜 `xmmword ptr`로 썼나?"** — 매뉴얼 줄을 그대로 옮겼기 때문이다. PDF 원문(p.2054)은 이렇게 적혀 있다.

```
EVEX.128.F3.0F38.W0 35 /r   VPMOVQD xmm1/m128 {k1}{z}, xmm2
```

`m128` = 16바이트 = `xmmword ptr`. 추출과 생성은 매뉴얼대로 했다. **틀린 것은 매뉴얼 줄이다.**
같은 페이지 안에서 세 가지 근거가 이를 뒤집는다.

| 근거 | 내용 |
|---|---|
| ① 같은 줄의 설명 | "Converts **2** packed quad-word integers from xmm2 into **2** packed double-word integers" → 2 × 32비트 = **64비트(m64)** |
| ② 같은 페이지 Operand Encoding 표 | Tuple Type = **`Half Mem`** = 메모리 크기는 벡터 길이의 **절반**. EVEX.128이면 **64비트** |
| ③ 형제 명령어 줄 | VPMOVDB `m32` · VPMOVDW `m64` · VPMOVQB `m16` · VPMOVQW `m32` · VPMOVWB `m64` — **전부 줄어든 크기로 적혀 있다. VPMOVQD만 `m128`** |

도구로도 확인된다.

```
vpmovqd xmmword ptr [eax], xmm0   → 거부           (매뉴얼 줄 그대로)
vpmovqd qword ptr [eax], xmm0     → 62 f2 7e 08 35 00   EVEX.128 = 우리가 노린 바로 그 행
vpmovqd xmmword ptr [eax], ymm0   → 62 f2 7e 28 35 00   EVEX.256 (m128은 ymm 소스와 짝)
```

**결론 두 가지.**

1. **매뉴얼 표기 오류가 맞다.** 도구 7종이 전부 거부하고, 매뉴얼 자신의 설명·Tuple Type·형제 줄이
   모두 `m64`를 가리킨다. VPMOV* 계열 메모리 입력 450건 중 **이 행에서 나온 5건만** 거부됐다.
2. **그래도 우리가 고칠 수 있다.** 오퍼랜드 열의 `m128` 대신 **Tuple Type을 읽어 메모리 크기를 정하면**
   이 행을 실제로 시험할 수 있다(`qword ptr` → EVEX.128 인코딩 생성). 즉 **거부 17건 중 5건은
   다음 라운드에서 해소 가능**하다. 1단계 추출에 Tuple Type 열을 추가하는 것이 과제다.

#### ①-B 심층 분석 2: VSCATTERDPD 2건도 매뉴얼 표기 오류다 (2026-09-21 확정)

같은 방법을 "판단 보류"로 남겨둔 VSCATTERDPD에 적용했더니 **같은 결론**이 나왔다.

VSIB 명령어는 **인덱스 레지스터 개수 = 데이터 원소 개수**다. 인덱스가 dword(32비트)이고
원소가 qword(64비트)면 **인덱스 레지스터는 데이터 레지스터의 절반 크기**여야 한다.
매뉴얼의 쌍둥이 명령어를 나란히 놓으면 바로 보인다.

| EVEX 길이 | VPSCATTERDQ (매뉴얼) | VSCATTERDPD (매뉴얼) | 실제로 필요한 것 |
|---|---|---|---|
| 128 | `vm32x {k1}, xmm1` | `vm32x {k1}, xmm1` | 일치 ✓ |
| 256 | `vm32x {k1}, ymm1` | **`vm32y {k1}, ymm1`** | `vm32x` — VPSCATTERDQ 쪽이 맞다 |
| 512 | `vm32y {k1}, zmm1` | **`vm32z {k1}, zmm1`** | `vm32y` — VPSCATTERDQ 쪽이 맞다 |

**둘 다 "dword 인덱스 + qword 원소"인데 VSCATTERDPD만 인덱스를 전체 크기로 적었다.**
PDF 원문(p.2080, p.2202)에서 직접 확인했다.

도구 관측:

```
vscatterdpd [eax + ymm1] {k1}, ymm0   → 거부  invalid VSIB address   (매뉴얼 줄 그대로)
vscatterdpd [eax + xmm1] {k1}, ymm0   → 67 62 f2 fd 29 a2 04   EVEX.256 = 노렸던 행
vscatterdpd [eax + ymm1] {k1}, zmm0   → 67 62 f2 fd 49 a2 04   EVEX.512 = 노렸던 행
vpscatterdq [eax + xmm1] {k1}, ymm0   → 67 62 f2 fd 29 a0 04   쌍둥이, 매뉴얼 그대로 수용
```

EVEX 바이트가 `29`(256비트) / `49`(512비트)로 갈리는 것까지 같다. opcode만 `a2` ↔ `a0`으로 다르다.
**scatter 계열 입력 32건 중 거부는 이 2건뿐이고, 쌍둥이 VPSCATTERDQ는 전부 수용됐다.**

→ **판단 보류 → 매뉴얼 표기 오류 확정.** 그리고 이것도 **우리가 고칠 수 있다.**
VSIB 인덱스 크기를 오퍼랜드 열 대신 **"인덱스 폭 : 원소 폭" 비율로 계산하면** 이 행을 실제로 시험할 수 있다.

#### ①-B 심층 분석 3: SYSEXIT/SYSRET 4건은 매뉴얼 오류가 아니라 **표기의 구조적 한계**다

매뉴얼에 이 두 줄이 나란히 있다.

```
0F 35           SYSEXIT   Valid   Fast return to privilege level 3 user code.
REX.W + 0F 35   SYSEXIT   Valid   Fast return to 64-bit mode privilege level 3 user code.
```

**니모닉 글자가 완전히 같다.** 오퍼랜드가 없으니 `REX.W`를 표현할 문법적 수단도 없다.
SYSRET(`0F 07` / `REX.W + 0F 07`)도 똑같다. 우리는 매뉴얼 글자 그대로 `sysexit`을 넣었고,
as는 **어느 행인지 모르겠다고 거부**했다.

| 입력 | GNU as | 맞는 SDM 행 |
|---|---|---|
| `sysexit` (매뉴얼 표기) | **거부** `ambiguous operand size` | — |
| `sysexitd` | 수용 `0f 35` | REX.W 없는 행 |
| `sysexitq` | 수용 `48 0f 35` | REX.W 행 |
| `sysret` | **거부** `ambiguous operand size` | — |
| `sysretd` / `sysretq` | 수용 `0f 07` / `48 0f 07` | 각각의 행 |

→ **두 행 모두 시험할 수 있다.** 도구가 쓰는 크기 접미사(`d`/`q`)를 붙이면 된다.
매뉴얼 오류도 아니고 도구 결함도 아니다. **매뉴얼 표기만으로는 두 행을 구분할 수 없는 것**이다.

#### 여기서 as와 clang의 태도가 갈린다 — 그리고 as 쪽이 안전하다

| 입력 | GNU as | Clang |
|---|---|---|
| `sysexit` | **거부.** "모호하다, 명시하라" | **수용.** 조용히 `sysexitd`(`0f 35`)를 고른다 |
| `sysret` | **거부** | **수용.** 조용히 `sysretd`(`0f 07`) |

**clang은 경고 없이 REX.W 없는 행을 고른다.** 매뉴얼 글자를 그대로 clang에 넣으면
`0F 35` 행만 시험되고 `REX.W + 0F 35` 행은 **한 번도 시험되지 않은 채 "성공"으로 넘어간다.**
as의 거부는 불편해 보이지만 **"당신이 지정한 행이 둘 중 무엇인지 모르겠다"는 정확한 신호**다.

> **이 4건은 뿌리가 예외 ④와 같다.** 같은 니모닉 글자를 여러 SDM 행이 공유하는 문제다.
> 다만 예외 ④(264건)는 어셈블러가 조용히 하나를 골라서 **안 보이는 반면**,
> SYSEXIT은 as가 거부해서 **눈에 띄었을 뿐**이다.

##### 덤으로 나온 것: 비REX.W 행에는 **두 도구가 공통으로 받는 표기가 없다**

`data/cases.csv`에 등록하면서 확인됐다.

| 입력 | GNU as | Clang |
|---|---|---|
| `sysexit` (매뉴얼 표기) | 거부 | **수용** `0f 35` |
| `sysexitd` | **수용** `0f 35` | 거부 |
| `sysexitq` | 수용 `48 0f 35` | 수용 `48 0f 35` |

REX.W 행(`48 0f 35`)은 `sysexitq`라는 공통 표기가 있지만, **비REX.W 행(`0F 35`)은
as와 clang이 받는 글자가 서로 다르다.** 차등 테스트에서 "같은 입력을 두 도구에 넣는다"는
전제가 이 행에서는 성립하지 않는다. SYSRET도 같다.

#### ①-B에서 새로 나온 것: clang이 레지스터를 조용히 바꾼다

`lar`/`lsl`은 as가 거부하는데 clang은 받아준다. 그런데 **쓴 것과 다른 레지스터로 바꿔서 조립한다.**

| 입력 | clang 18 | clang 23.1 | clang 24(trunk) |
|---|---|---|---|
| `lar ecx, rcx` | `lar ecx,ecx` (`0f 02 c9`) | **`lar ecx,cx`** | `lar ecx,ecx` |
| `lsl rcx, ecx` | `lsl rcx,rcx` (`48 0f 03 c9`) | — | — |

사용자가 `rcx`라고 썼는데 결과는 `ecx`(또는 `cx`)다. **경고도 없다.** 게다가 **clang 버전마다 고른
레지스터가 다르다.** 이건 우리가 확정 판정할 준비가 안 된 새 관측이라 **예외 ⑤로 넘겨 추적한다.**

### 오늘 새로 확인된 것: LAR/LSL의 REX.W 행을 as가 만들지 못한다 (왕복 실패 2번째 유형)

미확정으로 남아 있던 "clang이 레지스터를 조용히 바꾼다"를 파고들다가 **더 큰 것**이 나왔다.
clang의 치환은 곁가지였고, 문제는 **GNU as 쪽**이다.

**먼저 매뉴얼부터.** PDF 원문(p.651, p.691)의 REX.W 행이 서로 반대로 적혀 있다.

```
LAR   REX.W + 0F 02 /r   LAR r32, r64/m16      ← 목적지 r32, 원본 r64
LSL   REX.W + 0F 03 /r   LSL r64, r32/m16      ← 목적지 r64, 원본 r32
각주 1: Regardless of operand size, only bits 15:0 of a register source operand are used.
```

REX.W 비트 **하나**로 두 자리의 폭을 따로 정할 수는 없다. 각주가 "원본은 하위 16비트만 쓴다"고
하므로 원본 폭은 의미가 없는데, 표기는 그걸 폭으로 적어 두 행이 어긋나 보인다.
**우리 생성기는 이 표기를 그대로 옮겨 `lar ecx, rcx` / `lsl rcx, ecx`를 만들었고 as가 거부했다.**

**그런데 대칭으로 써 보면 진짜 문제가 드러난다.**

| 입력 | GNU as 2.42~2.47 | Clang 18 |
|---|---|---|
| `lar ecx, ecx` | `0f 02 c9` | `0f 02 c9` |
| `lar rcx, rcx` | **`0f 02 c9`** ← REX.W가 사라진다 | `48 0f 02 c9` |
| `lsl rcx, rcx` | **`0f 03 c9`** | `48 0f 03 c9` |

**as는 `rcx`라고 쓴 것을 조용히 32비트 인코딩으로 바꾼다. 경고가 없다.**
AT&T 문법으로도, 크기 접미사를 붙여도 마찬가지다 — `lar %rcx,%rcx`, `larq %rcx,%rcx` 모두 `0f 02 c9`다.

### ⚠️ 판정 정정 (2026-09-21, 외부 검토 반영)

처음에 **"as는 어떤 문법으로도 REX.W 형식을 만들 수 없다"고 적었으나 틀렸다.**
`rex64` 의사 프리픽스를 쓰면 만들어진다.

```
lar rcx, rcx          → 0f 02 c9        ← 기본 렌더링. REX.W가 빠진다
rex64 lar rcx, rcx    → 48 0f 02 c9     ← 원하는 행이 나온다
```

**이 사실은 결론을 약화시키는 게 아니라 강화한다.** ISA 표현력의 한계가 아니라
**어셈블러의 기본 인코딩 선택 문제**임이 확정되기 때문이다. 사용자가 유효한 SDM 행을
명시적으로 지정(`rcx`)했는데 경고 없이 다른 행을 고른다.

### 이미 보고된 결함이다

외부 검토에서 확인했다 — binutils **bug gas/32813 "Missing REX prefix for LSL"**.
보고자 댓글: *"Earlier versions of gas correctly added the REX prefix, and other assemblers
(I tested nasm and XED) also encode this correctly with a REX prefix."*

원인도 특정됐다. 2022년 커밋 **"x86: correct handling of LAR and LSL"** 이 레지스터 크기 일치를
강제하고 디스어셈블러를 16비트 전용(`Mw`)으로 분리하면서 생긴 **회귀**다. 같은 커밋이
`lar ecx, rcx` 거부(예외 ①-B 2건)의 원인이기도 하다.

**우리가 처음 찾은 것이 아니다.** 대신 **우리 파이프라인이 실제로 보고된 binutils 결함을
독립적으로 재현해 냈다**는 검증 사례가 된다.

**그래서 왕복이 깨진다.** 네 버전 전부에서 같다.

```
바이트     48 0f 02 c9          ← SDM의 REX.W + 0F 02 /r 행 (Valid)
objdump →  lar rcx,rcx          ← 올바른 표시
as      →  0f 02 c9             ← REX.W가 사라진 다른 바이트. 오류도 경고도 없다
```

| 도구 | 2.42 | 2.45 | 2.46.1 | 2.47 |
|---|---|---|---|---|
| objdump 표시 | `lar rcx,rcx` | 〃 | 〃 | 〃 |
| 그 글자를 as에 | `0f 02 c9` | 〃 | 〃 | 〃 |
| 원본과 같나 | **다름** | **다름** | **다름** | **다름** |

LSL(`48 0f 03 c9` → `0f 03 c9`)도 같다.

#### 예외 ⑥(LSS)과 비교하면 — 이쪽이 더 위험하다

| | LSS/LFS/LGS (예외 ⑥) | LAR/LSL REX.W (오늘 확인) |
|---|---|---|
| objdump 표시 | **틀림** (`FWORD` = 48비트) | **맞음** (`lar rcx,rcx`) |
| 그 출력을 as에 | **거부** — 시끄럽게 실패 | **수용, 다른 바이트** — **조용히 실패** |
| 알아채기 | 에러가 나서 바로 보인다 | **아무 표시가 없다** |

**거부는 눈에 띄지만 조용한 바이트 변경은 안 띈다.** 역어셈블 → 수정 → 재조립 흐름에서
이런 손실은 그대로 통과한다.

#### 어디까지 확정인가

- **확정:** `48 0f 02 c9`는 SDM의 Valid 행이고, objdump 출력을 as에 다시 넣으면 **바이트가 달라진다.**
  as에는 이 인코딩을 만드는 문법이 없다. 2.42·2.45·2.46.1·2.47에서 재현. clang은 만들 수 있다.
- **미확정:** 두 인코딩의 **실행 의미가 다른지는 확인하지 않았다.** 32비트 쓰기는 상위 32비트를
  0으로 채우므로 결과가 같을 수 있다. **그래서 오늘은 버그 건수를 3→4로 올리지 않는다.**
  올리려면 CPU 실행으로 두 인코딩의 결과를 대조해야 한다.
- **우리 파이프라인이 이걸 놓친 이유:** 매뉴얼 행이 비대칭(`r32, r64`)이라 우리는 `lar ecx, rcx`를
  만들었고 as가 거부했다. **대칭형 `lar rcx, rcx`를 만들었다면 잡혔을 것이다.**
  → 예외 ④의 "REX.W 미부착 21건"에 lar 4 · lsl 4가 들어 있던 것이 같은 뿌리였다.

## 예외 ⑥ — 확정 결함 1종류 3사례: objdump의 LSS/LFS/LGS

### 무엇이 문제인가

```
매뉴얼 p.658   REX.W + 0F B2 /r   LSS r64, m16:64   Valid
                                            └ 16비트 셀렉터 + 64비트 오프셋 = 80비트

1) 매뉴얼대로 조립   lss rcx, tbyte ptr [rax]   →  48 0f b2 08      수용
2) 역어셈블          48 0f b2 08                →  lss rcx,FWORD PTR [rax]
                                                          └ FWORD = 48비트 (틀림)
3) 그 글자를 다시 조립                          →  거부
                    Error: incorrect register `rcx' used with `l' suffix
```

**역어셈블 결과가 입력으로 되돌아가지 않는다.** 바이너리를 분석해 코드를 복원하는 작업이 여기서 막힌다.

### 오늘 확인한 재현 범위 (도구 9종)

| 도구 | `48 0f b2 08` 표시 | 그 출력을 다시 조립 |
|---|---|---|
| objdump 2.42 (Ubuntu 기본) | `lss rcx,FWORD PTR [rax]` | **as 거부** |
| objdump 2.45 (소스 빌드) | 같음 | as 거부 |
| objdump 2.46.1 (소스 빌드) | 같음 | as 거부 |
| **objdump 2.47 (최신, 소스 빌드)** | **같음** | **as 거부** |
| Godbolt gas 2.42 | 같음 | 거부 |
| Godbolt gas 2.44 | 같음 | 거부 |
| clang 18 / 23.1 / 24 | — | **수용** (`48 0f b2 08` 동일 바이트) |
| llvm-objdump 18 | `lss rcx, [rax]` (크기 생략) | — |

**두 가지가 드러난다.**

1. **binutils 내부가 서로 안 맞는다.** 같은 프로젝트의 objdump가 낸 출력을 같은 프로젝트의 as가 거부한다.
   **2.42부터 최신 2.47까지 네 버전 모두 그렇다.**
2. **clang은 그 출력을 받아준다.** 즉 objdump의 출력이 문법적으로 불가능한 게 아니라,
   **as가 `FWORD`(48비트)와 `rcx`(64비트) 조합을 허용하지 않는 것**이다.
   llvm-objdump는 크기를 아예 안 적어서 이 문제를 피한다.

### 왜 3건인가

LSS(`0F B2`) · LFS(`0F B4`) · LGS(`0F B5`)는 하는 일이 같은 형제 명령어다.
**서로 다른 버그 3개가 아니라 한 결함의 세 명령어다.**

### 곁다리 관측: 옵션에 따라 수용이 갈린다

`-mintel64`가 없으면 as는 SDM 표기 그대로인 `lss rcx, tbyte ptr [rax]`도 거부한다
(`operand size mismatch`). **Godbolt에서도 같았다** — 옵션을 안 주면 2.42·2.44 모두 거부한다.
"어셈블러가 거부했다"는 진술에는 **옵션을 함께 적어야 뜻이 통한다.**
