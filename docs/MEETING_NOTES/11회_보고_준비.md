## 2. 기록 중 틀렸거나 주의해야 할 것

1. **버그 수가 계속 바뀌었다**: 7 → 5 → 8 → 4 → 3. 지금의 "3건"도 별개의 버그 3개가 아니라 **objdump 표시 결함 1종류**다.
2. **MOVDIR64B 에러 원인 설명이 절반만 맞다.** 생성된 입력 `movdir64b cx, zmmword ptr [eax]`에는 문제가 두 개 있다.
   - `zmmword ptr`: m512는 512바이트 블록이지 zmm 크기 지시자가 아니다.
   - `cx`: 64비트 모드에서는 16비트 주소 레지스터를 쓸 수 없다. 레지스터 폭이 주소 폭과 맞으면 되므로 `ecx`+`[eax]`, `rcx`+`[rax]` 모두 가능하다.

   as는 첫 번째 문제만 보고한다. triage 코드(`m7_triage.py`의 `WRONG_REGISTER_WIDTH`)는 MOVDIR64B를 SENDUIPI와 같은 묶음에 넣고 SENDUIPI의 설명을 그대로 붙였다. 그래서 "64비트 레지스터로 바꾸면 된다"는 틀린 문장이 남았다(`rcx, zmmword ptr [rax]`도 거부됨).
3. **결과 파일의 버전이 서로 맞지 않는다.** `combos.csv`와 `tests.s`는 9/15에 다시 생성됐는데, `asm_result.csv`(5단계)는 8/24 파일 그대로다. 소스가 2줄 바뀌었고(1517, 2503) 2줄이 새로 생겼다(1028, 7277).
4. **"false_alarm 1,558"은 모두 "어셈블러가 정상"이라는 뜻이 아니다.** 약 120행은 **우리 생성기의 결함**(combiner_*, generator_*, extractor_* 카테고리)인데, 고치지 않고 false_alarm으로 남겨 두었다. 또 1,585행 중 1,578행은 새 기준으로 다시 검토하지 않았다(`not_reassessed`).
5. **"SDM 100% 커버"**는 모든 행에서 입력을 1개 이상 만들었다는 뜻일 뿐이다. 그 행을 제대로 검증했다는 뜻이 아니다.
6. **"CPU 19건 통과"**는 실행해서 결과를 모았다는 뜻일 뿐이다. 기대값과 대조한 것이 아니다.
7. **objdump 결함의 최신 버전 재현 (9/16 확인)**: binutils **2.47**(Ubuntu 패키지)에서도 똑같이 `lss rcx,FWORD PTR [rax]`로 표시된다. `-M intel64` 옵션을 줘도 같고, 이 출력을 다시 어셈블하면 거부된다. 아직 binutils bugzilla에서 기존 보고를 검색하지 않았고, 새로 보고하지도 않았다.
8. 형섭 확인: 교수님이 **도구 제작을 지시하셨다**. 다만 회의록(1~10회)에는 그 지시가 적혀 있지 않다. 지시 내용(목적: 퍼징 시작 입력 생성, 이후 AT&T 문법으로 확장)을 회의록에 보충해야 한다.

## 3. 의문점에 대한 답

### Q1. 테스트 케이스가 매뉴얼대로 만들어졌나?
**추출은 매뉴얼대로 됐다. 생성은 형식은 따르지만 교수님이 요청한 규칙과 다르다.**

| 교수님 요청 (4·5회) | 현재 생성기 |
|---|---|
| 메모리: `[base+index*scale+disp]`, `[rip+disp]` 섞기 | `[eax]` 3,461개, **rip-relative 0개** (`[eax]`는 32비트 주소라 0x67 프리픽스가 붙는다) |
| 즉시값: 해당 크기의 최대값을 16진수로 | imm8은 거의 전부 `1`. imm16/32는 `0x100`/`0x10000`(imm8로 줄어들지 않게 한 선택이라 이유는 있음) |
| 랜덤으로 약 10번 생성 | 행마다 1~2개의 **고정 대표값** |
| (7회) 원인 구분이 가능한 입력 | 모든 오퍼랜드가 같은 줄(`xmm0, xmm0, xmm0`)이 **2,161줄** → 오퍼랜드 순서 오류를 찾아낼 수 없음 |
| — | AVX-512 마스크·브로드캐스트가 있는 1,640행 중 실제로 `{k1}` 등을 넣은 줄은 **64줄** |

예시: `ADD r32, r/m32`(03 /r) 행은 `add ecx, ecx`로 생성됐다. 그런데 as는 01 c9를 만들었다. 즉 **의도한 인코딩 행은 실제로 테스트되지 않았다.**

### Q2. 에러는 왜 났나? (매뉴얼상 Valid인데 as가 거부한 56건, 직접 재현)

| 건수 | 원인 | 누구 탓 |
|---|---|---|
| 18 | 매뉴얼 표기 `k1+1`, `zmm2+3`을 그대로 넣음 → as는 이를 덧셈 식으로 읽음 | **생성기** |
| 10 | 크기가 고정된 m512 블록(FXSAVE 등)에 `zmmword ptr`를 붙임 (clang은 받아줌) | **생성기** (as/clang 엄격도 차이로도 볼 수 있음) |
| 7 | `<EAX>`, `<XMM0-7>` 같은 암묵 오퍼랜드를 명시 오퍼랜드로 넣음 | **생성기** |
| 4 | `rep lods al` — 매뉴얼의 표기 관례를 그대로 옮김 | **생성기** |
| 2 | `imm8/r` 문자열이 그대로 들어감 | **추출기** |
| 1+1 | `senduipi ecx`, `umonitor cx` — 모드/폭 제약을 반영하지 못함 | **생성기** |
| 4 | SYSEXIT/SYSRET: 매뉴얼대로 오퍼랜드 없이 쓰면 as가 크기를 못 정함 | **판단 보류** (흥미로운 사례) |
| 2 | LAR/LSL 비대칭 폭 | 재심에서 구현 버그 아님으로 정리 |
| 2 | VSCATTERDPD vm32y/vm32z | **판단 보류** (매뉴얼 표기 문제일 수 있음) |
| 1 | MOV Sreg, qword ptr | 재심에서 구현 버그 아님으로 정리 (CPU 실험 근거) |
| 1 | UDB | 매뉴얼에는 있지만 as/clang이 지원하지 않음 |
| 1 | VPMOVQD m128 | 매뉴얼 표 오탈자로 추정 |

→ **56건 중 약 40건은 우리 쪽(추출기·생성기) 문제**다. 그대로 남아 있으니 먼저 고친 뒤 다시 돌려야 한다.

### Q3. 버그·에러가 나면 도구는 어떻게 동작해야 하나?
하나의 "통과/실패"로 끝내지 말고, 아래처럼 나눠서 보고해야 한다.

- **입력 생성 오류** (우리 탓) / **지원 차이** (UDB) / **표기 차이** (alias, 크기 생략) / **도구 결함 후보** (LSS 표시) / **도구 크래시·타임아웃** (절대 버리지 않음) / **검사 불가** (미지원 구문)
- 각 결과에 원본 입력, 의도한 SDM 행, 실제 바이트, 도구 버전을 함께 남긴다.
- 현재 코드의 결함(기존 검토 문서에도 있음): 어셈블러 크래시(SIGSEGV)를 일반 "rejected"로 분류함, 배치에서 의도한 인코딩과의 불일치를 최종 상태에 반영하지 않음(118건), 검사 도구 실패를 배치 성공으로 처리함.

### Q4. 퍼징 연구에서는 언제 쓰이나?
- **차등 테스트의 오라클**: 같은 입력을 as/clang/objdump/llvm-objdump(나아가 QEMU, 3회 언급)에 넣고 결과가 다를 때 원인을 분류한다.
- **시드(seed) 생성기**: 매뉴얼 행에서 문법에 맞는 입력을 만들어 퍼저의 시작 입력으로 쓴다. AsFuzzer(비정상 문법)와 반대 방향이다.
- **결과 분류·중복 제거**: 퍼저가 낸 수천 개 차이를 alias·표기·생성 오류로 걸러 사람이 볼 것만 남긴다.
- 주의: 파서 크래시를 찾는 퍼징이라면 "거부된 입력"을 버리면 안 된다. 그래서 도구의 역할(필터인지, 주석인지)을 먼저 정해야 한다.
