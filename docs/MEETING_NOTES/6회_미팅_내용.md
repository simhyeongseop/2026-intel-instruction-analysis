### **1. 파싱 오류 수정 및 1차 컴파일 테스트 환경**

* 
**이슈 해결:** 이전 작업에서 오퍼랜드에 매뉴얼의 각주 표시(숫자)가 딸려 들어가는 파싱 문제가 있었으나, 이를 수정하고 테스트 셋을 다시 구성했습니다.


* 
**테스트 환경:** 우분투 환경에서 GCC(`binutils`)와 Clang을 활용해 생성된 어셈블리 코드를 컴파일 테스트했습니다. 명령어 파라미터 타입별로 랜덤하게 캔디데이트 셋을 뽑아 테스트 케이스를 생성했습니다.



### **2. 에러 케이스 심층 분석 (교수님 피드백)**

발생한 에러들이 실제 우리의 스크립트 버그인지, 컴파일러의 정상적인 동작인지 면밀히 분석했습니다.

* 
**모드(Architecture Mode) 차이:** * `Invalid instruction` 에러 중 일부는 AMD64와 Intel64의 지원 명령어 차이 때문입니다. 특정 명령어는 64비트 환경 자체에서 지원하지 않으므로 이는 정상적인 반려로 간주했습니다.


* 
**부호 확장(Sign Extension) 범위 초과:** * 32비트 Immediate 값을 64비트 레지스터에 할당할 때 에러가 발생했습니다.


* 교수님 확인 결과, 컴파일러는 부호 확장(Signed Extension)을 수행하는데, 32비트로 표현할 수 있는 부호 있는 정수 범위를 초과하는 양수 값을 넣으면 오버플로우로 간주해 거부합니다. (예: `-1`은 정상 처리됨 ).




* **컴파일러 간(GCC vs Clang)의 문법 해석 차이:**
* 
**`INVLPG` 명령어:** 메모리 사이즈를 `QWORD PTR`로 임의 지정했을 때, GCC의 `binutils`는 사이즈 지정자를 무시하고 기본 사이즈(`BYTE PTR`)로 컴파일을 통과시켜 버립니다. 반면, Clang은 문법을 정확히 체크하여 해당 지정자가 붙으면 `Invalid instruction` 오류를 뱉어냅니다.


* 
**`XLAT` 명령어:** Clang에서 `RBX` 레지스터를 사용해 메모리 오퍼랜드를 참조할 때 "사이즈가 맞지 않는다(byte size vs RBX)"는 경고(Warning)를 발생시키는 특이 동작을 확인했습니다.





### **3. 다음 단계: 2차 파이프라인 (역어셈블 교차 검증)**

지금까지는 어셈블리 코드가 오브젝트 파일(.o)로 **컴파일 성공/실패 여부**만 확인했다면, 이제는 컴파일된 결과물이 **우리가 의도한 대로 만들어졌는지** 뜯어보는 과정이 추가됩니다.

* **검증 로직:**
1. 생성한 어셈블리 코드를 컴파일하여 바이너리(오브젝트 파일)를 만듭니다.


2. 
`objdump -d -M intel` 명령어를 사용하여 해당 바이너리를 인텔 문법의 어셈블리 코드로 다시 역어셈블(Disassemble)합니다.


3. 최초 생성했던 코드와 역어셈블된 코드를 1:1로 비교 검증합니다.




* **분석 포인트 (Alias vs Bug 구분):**
* 
**에일리어스(Alias):** `XLAT` 명령어가 `XLATB` 등으로 축약되거나, 더 짧은 별칭 명령어로 자동 변환되는 컴파일러의 정상적인 편의 기능입니다.


* 
**컴파일러 버그(Bug):** 원래 16비트를 꽉 채워 데이터를 넣었는데 컴파일러가 멋대로 8비트로 강제 축소(Truncate)해버리거나 형태를 망가뜨리는 등 실제 컴파일러의 번역 오류입니다.


* 비교 도구를 통해 에일리어스와 버그를 분류하고, 버그 리포트를 작성할 수 있는 패턴을 찾습니다.





### **4. 향후 심화 확장 연구 (Illegal Instruction)**

* 교수님께서 과거 발견하신 치명적인 컴파일러 버그 케이스를 언급하셨습니다.
* 코드를 컴파일할 때는 아무 에러 없이 바이너리를 생성하지만, 막상 실행(Execute)하면 잘못된 기계어 매핑으로 인해 `SIGILL (Illegal Instruction)` 오류를 내며 프로그램이 뻗어버리는 현상입니다.


* 역어셈블 파이프라인이 안정화되면, 현재의 캔디데이트 조합을 넘어 더 다양한(예상치 못한) 오퍼랜드 인자 값들을 넣어 이와 같은 숨은 런타임 버그들을 찾아보는 것으로 연구를 확장하기로 했습니다.

다음 과제는 기존 자동화 스크립트에 "역어셈블(Disassemble) 비교 파이프라인 추가 개발하기"입니다.

구체적으로 코딩해서 구현해야 할 **3단계 과정**은 다음과 같습니다.

**1. objdump 실행 자동화**

* 기존에는 `gcc -c`로 어셈블리 코드를 `.o` 파일(오브젝트 파일)로 만드는 것까지만 검사했죠? 


* 이제는 성공적으로 만들어진 `.o` 파일에 대고 `objdump -d -M intel` 명령어를 실행하도록 파이썬 스크립트(또는 쉘 스크립트)를 추가해야 합니다. (이렇게 하면 기계어로 번역됐던 파일이 다시 인텔 문법의 어셈블리 코드로 복원됩니다).



**2. '원본' vs '복원본' 텍스트 비교 로직 작성**

* 형섭님이 맨 처음에 랜덤으로 생성했던 '원본 어셈블리 코드'와, 방금 objdump를 통해 뱉어낸 '복원된 어셈블리 코드'를 서로 비교하는 코드를 작성하세요.



**3. 달라진 결과물 분류하기 (Triage 2.0)**

* 두 코드를 비교했는데 글자가 **다르게 나온 경우**, 이게 왜 다른지 원인을 분석해서 리포트를 뽑아야 합니다.


* 
**에일리어스(Alias)인 경우 (정상):** 컴파일러가 알아서 더 짧은 별칭으로 바꾼 경우입니다 (예: `xlat`을 썼는데 `xlatb`처럼 명령어 뒤가 생략되거나 바뀌어 나오는 경우).


* 
**실제 버그인 경우 (비정상):** 16비트로 꽉 채워서 넣었는데 컴파일러가 지멋대로 8비트로 잘라먹은 경우 등, 명백한 컴파일러의 해석 오류입니다. 교수님이 진짜 찾고 싶어 하시는 게 바로 이겁니다.


(참고로 "컴파일은 정상적으로 되는데 실행하면 뻗어버리는 Illegal instruction 케이스 찾기"는 이번 파이프라인이 완성된 이후 나중에 진행할 심화 과제이니 당장 신경 쓰지 않으셔도 됩니다.)
