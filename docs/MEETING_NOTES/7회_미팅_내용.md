**x86 instruction 테스트 결과 해석**, 특히 **Intel syntax 기반 assembly/disassembly 결과 차이 분석 방법**에 대한 피드백


**전체 요약**

이번 미팅에서는 영어 샘플 기반으로 생성한 테스트 결과를 교수님과 함께 검토했습니다. 사용자는 GPT/Claude 등을 이용해 보고서를 만들었지만, 결과 해석이 어려워 교수님께 확인을 요청했습니다. 교수님은 objdump/disassembly 결과와 원래 source assembly가 다르게 보이는 사례들을 보며, 이것이 실제 오류인지, assembler/disassembler의 표현 차이인지, 테스트 케이스 생성 방식의 문제인지 구분해야 한다고 피드백했습니다.

**교수님 핵심 피드백**

1. **source와 objdump 결과가 다르다고 바로 오류로 보면 안 됨**

예를 들어 source에서는 `QWORD PTR` 등이 들어갔는데 objdump 결과에서는 다르게 나오거나 생략되는 경우가 있었습니다. 교수님은 이런 차이가 실제 instruction 의미의 오류라기보다, assembler/disassembler가 size directive를 생략하거나 자동 추론한 결과일 수 있다고 설명했습니다.

특히 `M`처럼 메모리 operand로만 되어 있고 size가 명확히 주어지지 않은 경우에는, `QWORD PTR` 같은 size directive를 무조건 넣는 것이 오히려 테스트 케이스 생성상의 문제가 될 수 있다고 했습니다.

2. **memory operand의 size directive는 register 크기 등을 보고 유추해야 함**

`LEA`, `LSS`, `LFS` 같은 instruction에서 memory operand size가 애매한 경우가 있었고, 교수님은 이때 destination register 크기 등을 보고 적절한 size directive를 넣어야 한다고 말했습니다.

예를 들어 destination이 16-bit register라면 memory operand도 그에 맞는 size로 생성해야 하는데, 무작정 `QWORD PTR`을 넣으면 테스트 자체가 잘못될 수 있습니다.

3. **일부 차이는 assembler가 허용하거나 무시하는 표현일 수 있음**

교수님이 직접 간단히 테스트해 보면서, 어떤 경우에는 size directive를 생략해도 compile이 되고, `QWORD PTR` 같은 표현이 있어도 assembler가 사실상 무시하거나 동일하게 처리하는 것 같다고 언급했습니다.

따라서 다음과 같은 구분이 필요합니다.

- compile 자체가 안 되는 경우
- compile은 되지만 objdump 결과가 다른 경우
- source 표현만 다르고 binary 의미는 같은 경우
- 실제로 encoding/decoding이 잘못된 가능성이 있는 경우

4. **문제 케이스를 카테고리별로 그룹핑해야 함**

교수님은 다음 미팅 전까지 결과를 그냥 나열하지 말고, 유형별로 묶어서 분석하라고 했습니다.

예시:

- `M` operand 관련 문제
- `M16:64` 같은 memory format 관련 문제
- size directive 생략/추론 문제
- register size change 문제
- alignment 관련 문제
- alias 관련 문제
- compile error 여부
- source와 objdump 표현 차이

이렇게 그룹핑하면 어떤 문제가 반복되는지 빠르게 볼 수 있고, 실제 오류인지 아닌지 판단하기 쉬워진다고 했습니다.

5. **다음부터는 교수님께 묻기 전에 직접 assembler로 돌려보기**

교수님은 미팅 전에 문제 케이스를 직접 compile/disassemble 해보고, 그 결과를 기반으로 질문하라고 했습니다. 단순히 GPT 보고서 결과만 들고 오기보다는, 실제로 `gcc`, `as`, `objdump` 등을 이용해 확인한 뒤 교수님께 가져오면 논의가 훨씬 빨라진다는 취지였습니다.

6. **compile error가 없었다면 의미 있는 결과일 수 있음**

사용자가 “compile error는 없었다”고 하자, 교수님은 만약 정말 compile error가 없다면 instruction manual을 꽤 잘 따른 것이라고 볼 수 있다고 말했습니다.

다만 compile은 되지만 objdump 결과가 다른 경우는, 더 다양한 random test case를 만들어 확인해야 한다고 했습니다.

**구체적으로 확인해야 할 항목**

다음 미팅 전까지 하면 좋을 작업은 이 정도입니다.

1. 현재 발견된 123개 “추가 확인 필요” 케이스를 유형별로 분류하기

2. 각 케이스에 대해 source assembly, compile 가능 여부, objdump 결과, 차이 원인을 표로 정리하기

3. `M` operand처럼 size가 명시되지 않은 경우, PTR size를 어떻게 생성했는지 확인하기

4. destination register 크기를 기반으로 memory operand size를 유추하도록 테스트 케이스 생성 방식을 점검하기

5. `LSS`, `LFS`, `LEA` 등 교수님이 언급한 instruction을 우선적으로 다시 확인하기

6. `QWORD PTR`, `WORD PTR`, `TBYTE PTR`, `FWORD PTR` 등이 실제로 assembler에서 어떻게 처리되는지 소규모 실험하기

7. “source와 objdump가 다름”을 무조건 error로 표시하지 말고, 의미가 같은 표현 차이인지 따로 판단하기

**연구 방향 관련 코멘트**

교수님은 현재 연구의 핵심을 이렇게 정리했습니다.

> Intel syntax의 규칙을 지켜서 assembly text를 만들었는데도 assembler/disassembler가 제대로 처리하지 못하는 사례를 찾는 것이 이 스터디의 주제에 가깝다.

즉, 단순히 특이한 syntax나 표준에서 벗어난 표현으로 생기는 오류는 현재 연구 주제와 맞지 않을 수 있습니다.

교수님이 예전에 말했던 `push offset` 관련 GCC/Clang 차이도 다시 확인해 보니, 둘 다 스펙상 허용되는 방식이라 명확한 오류라고 보기 어렵다고 했습니다. 그래서 그 케이스는 논문/보고서의 핵심 오류 사례로 넣기는 애매하다고 판단했습니다.
