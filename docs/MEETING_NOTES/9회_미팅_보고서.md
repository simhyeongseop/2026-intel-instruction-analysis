## 1. Clang 확장 및 비교 분석

**방법:** 기존 GNU `as` 검증 파이프라인에 `clang`(LLVM 통합 어셈블러)을 추가해, 같은 7,276개 테스트 케이스를 각각 개별 어셈블한 뒤 combo_id 기준으로 대조했다. 인코딩까지 정확히 비교하기 위해 objdump 역어셈블 **텍스트**가 아니라 **hex 바이트**를 직접 비교하도록 구현했다.

**결과 (`out/clang_compare.csv`, 7,276건):**

| 카테고리 | 건수 | 의미 |
|---|---|---|
| both_ok_same_bytes | 7,058 | 둘 다 성공, 바이트까지 완전히 동일 |
| both_ok_diff_bytes | 48 | 둘 다 성공했지만 인코딩이 다름 |
| as_only | 56 | as만 성공 (대부분 clang이 MPX 니모닉을 모름) |
| clang_only | 18 | clang만 성공 |
| both_reject | 96 | 둘 다 거부 |

### 🔑 핵심 성과 — 기존 "버그 7건" 중 2건 오판정 발견·정정

8회 미팅 PPT에서 이미 "진짜 버그"로 보고했던 항목:

> `CALL r/m32`: SDM은 64비트 모드에서 N.E.(인코딩 불가)로 명시하는데 `as`가 `call dword ptr [eax]`를 조용히 받아준다 → **as 버그로 확정**

Clang 비교 과정에서 이 항목을 다시 들여다보다가, `as`가 만든 바이트(`67 66 ff 18`)의 ModRM 필드를 직접 디코딩해봤다:

```
ModRM = 0x18 = 0001 1000 (binary)
       mod=00  reg=011(=3)  rm=000(eax)
```

reg=3은 `FF /2`(근접 호출)가 아니라 **`FF /3`(원거리/far 호출)**이다. `data/db/isa_db.csv`에서 CALL 오피코드 표를 대조하니:

| 오피코드 | 형식 | 64비트 모드 |
|---|---|---|
| `FF /2` | `CALL r/m32` | **N.E.** ← 원래 테스트가 노리던 폼 |
| `FF /3` | `CALL m16:16` | Valid |
| `FF /3` | `CALL m16:32` | Valid |

즉 `as`는 SDM이 금지한 근접 호출을 만든 게 아니라, **SDM이 허용하는 원거리 호출로 정상 인코딩**한 것이었다. clang도 같은 계열(far call)로 해석해 두 어셈블러가 일치했다(66 프리픽스로 far 크기만 다름). `JMP r/m32`도 동일 패턴(ModRM reg=5, `FF /5` far jmp).

**조치:** `pipeline/m7_triage.py`의 판정을 `bug` → `false_alarm`으로 수정, **진짜 버그 7건 → 5건**으로 정정. 8회 미팅 PPT 원본에도 정정 안내를 추가했다.

## 2. objdump 디스어셈블 결과 검증 심화

**방법:** 기존 roundtrip(원본 vs objdump 텍스트 비교) 결과 중 "different" 1,456건 전부에 대해, **objdump가 보여준 텍스트를 다시 어셈블**해서 원본과 바이트가 실제로 같은지 재검증하는 도구(`pipeline/m10_reassemble_check.py`)를 만들었다. "텍스트만 다르고 바이트는 같다"는 기존 판정을 도구로 재확인하는 절차다.

**결과 (1,456건 중):**

| 카테고리 | 건수 |
|---|---|
| byte_roundtrip_same (표기만 다름, 안전) | 1,326 |
| byte_roundtrip_diff (진짜 바이트 차이, 개별 확인) | 5 |
| relative_target_reassembly_artifact (검증 방법 자체의 한계) | 99 |
| reassemble_failed (재어셈블 문법 불일치) | 26 |

### 🔑 신규 발견 — objdump 자체의 디스어셈블 표시 결함 3건

`LSS`/`LFS`/`LGS`의 REX.W(64비트 목적지) 형태를 실제로 확인:

```
소스: lss rcx, m16:64 형태   ->  as가 만든 바이트: 67 48 0f b2 08
objdump 표시:                    lss    rcx, FWORD PTR [eax]   (6바이트 크기)
```

`REX.W + 0F B2 /r LSS r64, m16:64`는 SDM이 명시한 그대로 정확히 인코딩됐다(m16:64 = 2+8 = 10바이트, 관례상 `TBYTE PTR`). 그런데 **objdump가 REX.W 유무와 무관하게 항상 `FWORD PTR`(6바이트, m16:32용 표기)로 보여준다.** 이 텍스트를 그대로 다시 어셈블하면 `as`가 `"incorrect register 'rcx' used with 'l' suffix"`로 거부한다 — `as` 자신도 "rcx엔 FWORD가 아니라 TBYTE가 맞다"는 걸 알고 있다는 간접 증거다.

이건 `as`의 인코딩 버그가 아니라 **binutils 패키지 안의 objdump 쪽 디스어셈블 표시 결함**이다 (기존 `register_width/name_changed` 카테고리에 `unsure`로 판단보류돼 있던 항목을 이번에 원인까지 확정).

**조치:** 진짜 버그 5건 → **8건**으로 갱신 (as 버그 5건 + objdump 버그 3건, 성격이 다르므로 구분 표기).

## 3. 절대주소 및 주소체계 테스트

**방법:** 형섭 승인 하에 "격리된 자식 프로세스 + 타임아웃"으로만 실제 실행하는 안전한 하네스(`pipeline/m11_execute.py`)를 구축. GNU `as`/`ld`로 고정 주소(`-Ttext=0x400000`, `-fno-pie` 스타일)에 실제 ELF 실행파일을 만들고, `subprocess.run(timeout=N)`으로 실행한 뒤 종료코드/시그널을 관찰했다.

**결과 (6개 시나리오, 전부 예측과 일치):**

| 시나리오 | 예측 | 실제 | 의미 |
|---|---|---|---|
| `call_valid_function_ptr_64bit` | exit0 | exit0 | 대조군 — 정상 함수 호출 |
| `call_garbage_upper32_64bit` | SIGSEGV | SIGSEGV | 주소 상위 32비트를 쓰레기 값으로 덮으면 non-canonical 주소가 되어 #GP → SIGSEGV |
| `call_via_32bit_register_truncated` | exit0 | exit0 | 이 로드 주소(0x400000)는 32비트 안에 들어가 결정적으로 정상 |
| `truncate_high_stack_address_to_32bit` | SIGSEGV | SIGSEGV | **스택(항상 4GiB 초과 고주소)을 32비트로 자르면 SIGSEGV** — `/proc/self/maps` 실측으로 미매핑 공백 확인 |
| `jmp_null_address` | SIGSEGV | SIGSEGV | 널 포인터 점프 |
| `call_misaligned_valid_range_address` | SIGSEGV | SIGSEGV | 함수 끝+1바이트 실행 → 우연히 쓰기 명령으로 해석돼 읽기전용 페이지 쓰기 위반 |

가장 의미 있는 사례는 `truncate_high_stack_address_to_32bit`다 — 64비트 스택 주소를 32비트 레지스터 연산으로 자르면(`mov eax, eax`) 완전히 다른(미매핑) 주소가 되어 크래시가 난다는 걸 **직접 실행으로 증명**했다. 이게 형섭이 요청한 "32비트 vs 64비트 표현의 실제 위험 시연"이다.

## 4. N.E./이상 케이스 실제 CPU 동작 확인

**방법:** 손으로 만든 시나리오가 아니라, **파이프라인이 이미 찾아낸 데이터에서 자동으로 대상을 고르는 도구**(`pipeline/m12_execute_edge_cases.py`)를 만들었다. `out/asm_result.csv`에서 SDM이 Invalid/N.E./N.S.로 명시했는데 `as`가 실제로 어셈블에 성공한 케이스(상대분기 계열 제외) 19건을 실제로 실행했다.

**결과:**

| combo_id | 니모닉 | 소스 | mode_support | 실행 결과 |
|---|---|---|---|---|
| 323~341 | BNDCL/BNDCU/BNDCN/BNDMK/BNDMOV | `bndcl bnd0, dword ptr [rax]` 등 | N.E. | exit0 |
| 419 | CALL | `call dword ptr [eax]` | N.E. | SIGSEGV |
| 970/971 | DEC | `dec cx` / `dec ecx` | N.E. | exit0 |
| 1308/1309 | INC | `inc cx` / `inc ecx` | N.E. | exit0 |
| 1436 | JMP | `jmp dword ptr [eax]` | N.S. | SIGSEGV |
| 1511/4122 | LAHF/SAHF | | Invalid | exit0 |
| 1541 | LEAVE | `leave` | N.E. | SIGSEGV |
| 1544/1545 | LGDT/LIDT | `lgdt [eax]` / `lidt [eax]` | N.E. | SIGSEGV |
| 3294/3297 | POP | `pop fs` / `pop gs` | N.E. | exit0 |

### 🔑 핵심 결론 — 이 프로젝트 전체에 적용되는 방법론적 발견

ModRM 바이트를 직접 디코딩하고 `isa_db.csv`와 대조한 결과, **19건 대부분이 "N.E. 폼이 실행됐다"는 뜻이 아니었다**:

- **DEC/INC cx·ecx**: `48+rw`(단일바이트, 64비트 모드에서 REX와 충돌 → N.E.)와 `FF /1`(ModRM 폼, Valid)이 Intel 문법("dec cx")으로는 구분 불가. 실제 인코딩(`66 ff c9`, `ff c9`)은 `FF /1` — 애초에 N.E. 폼을 테스트한 게 아니었다.
- **LEAVE**: SDM에 완전히 동일한 니모닉/오퍼랜드("LEAVE", 오퍼랜드 없음)로 16/32/64비트 세 행이 있는데, 32비트 행(N.E.)은 **Intel 문법으로 선택할 방법 자체가 없다**. SIGSEGV는 N.E.와 무관 — 유효하지 않은 rbp로 스택 연산을 하다 난 것.
- **LGDT/LIDT**: m16&32(N.E.) vs m16&64(Valid) 구분도 문법으로 안 됨. SIGSEGV의 진짜 원인은 N.E.와 무관하게 **특권 명령어를 유저 권한(ring 3)에서 실행**해서 난 것(#GP).
- **BNDCL 등 MPX 계열**: 이 WSL 커널/CPU가 **MPX를 아예 지원하지 않음**(`/proc/cpuinfo`에 `mpx` 플래그 0건, 직접 확인)을 근거로, SDM 명시대로 오퍼랜드와 무관하게 전부 NOP로 동작.

즉 **CALL/JMP(1절)까지 포함해 총 6개 니모닉 그룹**에서 똑같은 근본 원인이 반복 확인됐다: *SDM이 같은 Intel 문법 텍스트를 레지스터/주소 폭이 다른 여러 표 행으로 나눠 문서화하는데, 테스트 생성기가 그 폭 차이를 문법만으로는 구분하지 못해 의도한(N.E.) 행이 아니라 다른 유효한 행을 실수로 테스트하게 된다.* 이건 `as`의 버그도 SDM 위반도 아니라 **이 프로젝트 자동 생성 파이프라인 자체의 구조적 한계**이며, 개별 버그 발견보다 방법론적으로 더 중요한 결론이라고 판단한다.
