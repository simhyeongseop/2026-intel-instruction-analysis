# 결과의 유효 범위와 버그 판정 기준

최종 갱신: 2026-09-15

이 문서는 저장된 실험 결과를 어디까지 해석할 수 있는지와 `bug`를 어떤 의미로 사용하는지를 정의한다. 현재 작업 흐름은 [파이프라인 설명](PIPELINE.md), [검사 도구 안내](TOOL_GUIDE.md), [2026-09-14 사례 재검토](CASE_REVIEW_2026-09-14.md)를 기준으로 한다. 퍼징 연구 활용성에 대한 비판적 평가와 보완 우선순위는 [2026-09-15 연구 검토](FUZZING_RESEARCH_REVIEW_2026-09-15.md)에 정리했다. 이전 판정 문서는 `archive/prototypes/RESULT_VALIDITY_before_tool_2026-09-14.md`에 보관했다.

## 판정의 층위

한 입력에 대해 다음 사실을 분리해서 기록한다.

1. **매뉴얼 행**: Intel SDM의 opcode, operand, mode, 예외 조건과 입력이 맞는가.
2. **어셈블러 결과**: GNU `as`와 Clang이 입력을 수락했는가, 생성한 `.text` 바이트가 무엇인가.
3. **역어셈블 결과**: `objdump`가 그 바이트를 어떤 니모닉·operand 문자열로 표시했는가. 표시 문자열의 차이는 바이트 차이와 별개다.
4. **재어셈블 결과**: 역어셈블 문자열을 다시 조립했을 때 바이트가 보존되는가.
5. **실행 결과**: 실제 CPU·OS에서 관찰한 예외와 상태. 이 결과는 해당 환경에서의 증거이며 모든 CPU를 대표하지 않는다.

따라서 `as`가 입력을 자동으로 다른 유효한 형태로 바꾸었다는 사실만으로 버그라고 하지 않는다. 원본 의도, 실제 바이트, 역어셈블 표기, 재어셈블 가능성을 각각 확인해야 한다.

## 현재 수치의 의미

- DB 4,210행에서 조합 7,277개가 만들어졌고, 실제 어셈블 입력은 7,276개(고유 source 6,024개)다.
- 기존 triage CSV는 1,585행이다. 2026-09-14 재심을 적용한 현재 분포는 `bug` 3, `false_alarm` 1,558, `unsure` 24다.
- 세 `bug` 행은 LSS/LFS/LGS의 같은 유형인 GNU `objdump`의 far pointer 크기 표시 결함이다. 이는 CPU가 잘못 실행했다는 뜻이 아니다.
- UDB는 SDM의 `D6`/`#UD` 명세와 도구 거부가 재현되지만, 해당 버전의 지원 약속 위반을 입증하지 못해 `unsure`로 둔다.
- MOV Sreg 메모리형과 LAR/LSL 사례는 기존 구현 버그 주장을 철회하고 관찰 또는 표현 차이로 기록했다. 재심 결과는 `legacy_*` 열에 보존된다.

## 도구의 현재 역할

`python scripts/asm_linter.py`는 한 줄 또는 파일을 받아 매뉴얼 DB의 후보 행, GNU/Clang 수락 여부, 바이트, 역어셈블·재어셈블 차이를 JSON 또는 텍스트로 보고한다. `pipeline/m13_lint.py`는 기존 7,276개 조합과 보충 사례를 같은 규칙으로 일괄 검사한다. 정적 입력 분석이 완료되지 않은 경우에는 `incomplete`로 남기며 통과로 간주하지 않는다.

현재 일괄 검사 결과는 7,283건(보충 사례 7건 포함)이며 `accepted` 4,401, `needs_review` 2,763, `rejected` 116, `incomplete` 3이다. 이는 매뉴얼 전체 ISA나 모든 CPU·OS 조합의 완전한 검증률을 뜻하지 않는다.

## 버그로 올리는 조건

`bug`는 다음 증거가 함께 있을 때만 사용한다.

- 해당 입력이 매뉴얼의 특정 유효 행을 명확히 선택한다.
- 도구가 그 행의 요구를 위반한 결과를 재현한다.
- 다른 정상적인 표기·도구·재어셈블 또는 실행 증거로 단순한 별칭, 표기 방식, 지원 범위, 입력 생성 오류를 배제한다.
- 재현 환경과 도구 버전을 기록한다.

조건이 부족하면 `false_alarm`(정상적인 다른 표현·행으로 해석됨), `unsure`(추가 증거 필요), 또는 `incomplete`(검사 자체 미완료)로 남긴다. 이 기준은 GNU/Clang의 수락 여부를 Intel ISA의 정답으로 대체하지 않는다.

## 다음 검증 작업

새 니모닉이나 매뉴얼 행을 추가할 때는 `data/cases.csv`에 사례를 먼저 등록하고, `asm_linter.py`의 JSON 결과와 필요 시 `tests/review_cpu_cases.c`의 실행 증거를 함께 남긴다. 결과를 갱신한 뒤 `python pipeline/run.py --only triage`와 테스트를 다시 실행한다.
