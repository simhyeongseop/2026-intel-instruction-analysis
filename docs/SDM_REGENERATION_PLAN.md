# SDM 원문 기반 조합 생성기 재작성·전체 재검토 계획 (2026-10-09)

## 사용자 결정 (2026-10-09)

- 원문이 최우선이다. 검토자(에이전트)의 해석은 근거로 쓰지 않는다.
- MOV만이 아니라 지금까지 생성한 모든 니모닉·인스트럭션(ISA 4,210행)을 재검토한다.
- 총론을 이제 처음 봤으므로 조합 생성기(m3_combine)를 새로 쓴다는 기준으로 진행한다.
- 결정 1(64비트 모드 주소): 각 명령 절의 표·Description 원문을 근거로 정한다.
- 결정 2(방향 쌍 레지스터-레지스터): 공통 소스로는 '도달 불가'로 표시하고, GNU 소스에만 `{load}`/`{store}`를 붙인다.
- 화면: 조회와 최종 검사 도구 모두 터미널.

## 새 생성기 원칙

1. 오퍼랜드 값마다 근거를 붙인다: 어느 원문(명령 절의 표 칸·각주·Op/En·Description 문장, 또는 총론 기호 정의 SYMxxx·총론 절)이 그 값을 허용하는지.
2. 근거의 우선순위: 명령 절(표, 각주, Op/En, Description) > 총론. 둘이 충돌하거나 원문이 모호하면 값을 만들지 않고 `미확인`으로 두며, 두 원문을 함께 기록한다.
3. 원문이 값을 정하지 않는 곳(예: 나열된 레지스터 중 무엇을 쓸지)에는 기계적인 고정 선택 규칙만 쓴다. 규칙 자체를 문서화하고, 선택이 원문 해석처럼 보이지 않게 한다.
4. 기존 m3_combine과 과거 결과는 그대로 두고, 새 결과는 별도 snapshot에 쓴다. 기존 ID와의 대응은 lineage로 남긴다.

## 오퍼랜드 표기의 근거 분포 (tokens.csv 기준)

- 총론 3.1.1.3 정의로 바로 설명: 155종, 행-오퍼랜드 7,646건.
- 총론 정의의 조합(예: `/` 대안): 30종, 121건.
- 총론 3.1.1.3에 정의가 없음: 83종, 1,999건. 명령 절이나 총론 다른 절이 필요하다.
  예: `zmm1`, `xmm3/m128/m32bcst`(정의는 zmm/m512/m32bcst만 있음), `k2`, `tmm1`, `m2byte`, `mem`, `r32a`, `k1+1`, `<XMM0-7>`.

## 재검토 방법 (사용자 확인 필요)

- 주 에이전트: 새 생성기가 각 값의 근거를 자동 추적한다. 근거가 없거나 충돌한 행을 기계적으로 나열한다.
- Sol(Opus 에이전트): 명령 절 원문이 필요한 행(정의 없는 표기, 각주가 있는 행, Description이 크기·제약을 정하는 행)을 원문과 대조한다.
- 대조 후 불일치·미확인과 대표 사례를 사용자 확인 목록으로 만든다. MOV 44개 검토는 새 생성기 결과로 다시 한다.

## 재작성 설계 초안 (2026-10-11)

### 지금 생성기의 문제

- 현재 흐름은 `m2_tokenize`(오퍼랜드 표기 분해) → `m3_combine`(표기 이름 → 대표값) → `m4_generate`(소스 줄)다.
- `m3_combine`(847줄)은 총론을 읽기 전에 만들었다. 이름 규칙(`r32`→`eax`, `m128`→`xmmword ptr [...]`)과 폐기된 해석 규칙으로 값을 고르고, 값마다 원문 근거가 붙지 않는다.
- 원문 재검토로 오퍼랜드마다 종류·폭·제약과 근거가 정해졌다(Sol 검토 + 완화 A~D + `data/rules/` 하드코딩). 새 생성기는 이 결과를 입력으로 쓴다.
- 지금 생성기로 만든 23,216케이스 중 216개는 표 행에 도달하지 못한다(`generator_issues.csv` 95행).

### 새 생성기가 하는 일

1. 입력:
   - `isa_db.csv`
   - 원문 검토 결과: `sdm_review_compare.load_sol` + `uniform_status`
   - 하드코딩: `source_conflict_cases`, `encoding_check_overrides`, `unreachable_forms`, `pdf_confirmed_corrections`, `extraction_corrections`
2. 오퍼랜드마다 대표값을 원문 검토 결과(종류·폭·레지스터 목록·메모리 제약)로 고른다. 값마다 근거 인용(SYM/쪽)과 선택 규칙 이름을 붙인다. 원문이 값을 정하지 않는 곳(어느 레지스터를 쓸지)만 고정 선택 규칙을 쓴다.
3. 케이스마다 의도한 표 행과 SDM 기대 결과를 적는다:
   - `reach`: 이 표 행의 인코딩이 나와야 함
   - `reject`: 64비트 무효라 거부돼야 함
   - `alias_no_test`: 소스로 시험 불가, 같은 문법의 유효 행 번호를 함께 적음
4. `generator_issues.csv` 유형별 처리:
   - `imm1_shift_alias`: C0/C1 행에 imm8=1을 쓰지 않는다.
   - `far_return`: `retf`를 쓴다.
   - `operand_size_prefix`: `pushw`를 쓴다.
   - 같은 레지스터 반복(TCMM*): 원문이 다른 레지스터를 요구하면 서로 다른 레지스터를 고른다.
   - `evex_not_forced`: 형식별 강제 방법을 쓴다.
   - `negative_source_alias`: `alias_no_test`로 둔다.
   - `tool_unsupported`: 그대로 두고 도구 미지원으로 기록한다.
5. 결정 6: Sol만 값을 적은 1,410줄을 생성 값과 대조한다.
6. 출력: 새 snapshot 디렉터리. 기존 combo ID와의 대응(lineage)을 남기고, 기존 `m3_combine`과 과거 결과는 지우지 않는다.

### 판정 기준 (사용자 결정 2026-10-11)

- 각 케이스는 **SDM 기대 결과 대 GNU as**, **SDM 기대 결과 대 clang**을 따로 판정한다.
- GNU와 clang을 서로 비교한 결과는 판정에 쓰지 않는다. 두 도구 바이트가 같은지는 참고 기록으로만 남긴다.
  - 이유: 기준은 SDM이다. 두 도구가 똑같이 틀리면 도구 간 비교로는 못 찾는다. 도구가 서로 다르다는 사실은 결론에 아무것도 더하지 않는다.
- 바꿀 곳:
  - `check_conflict_rows`의 '통과'가 요구하던 '두 바이트 같음'과 '통과(GNU 단독)' 구분을 도구별 판정 두 칸으로 바꾼다.
  - 음성 별칭은 도구별로 'SDM대로 거부 / 유효 행으로 조립'만 기록한다.
- 기존 9단계(`clang_compare`)와 과거 결과는 이력으로 남기고, 새 판정에는 쓰지 않는다.
