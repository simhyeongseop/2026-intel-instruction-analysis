## 4. 작업 방식: LLM은 코드를, 판정은 도구가

**슬라이드** (세 단 배치, 단 제목만 굵게. 글자 24pt 허용)

| LLM 에이전트 | 나 | 검증 장치 |
|---|---|---|
| Python 코드 작성 | 판정 기준 결정 | 회귀 테스트 156개 |
| 도구 실행·자료 검색 | 원문 PDF 직접 확인 | 실행 기록(버전·코드 해시) |
| 초안 분석 | 결론 검토·수정 지시 | 근거 파일(쪽수·소스 행) |

- 결과 숫자 = 실제 도구 4개의 출력 + 대조 코드 (LLM 판단 아님, 파랑)
- 검토로 고친 것: 근거 없는 후보 1건 철회 · 자체 오류 3건 수정 (빨강)

**대본**
작업 방식을 말씀드리겠습니다. 코드 작성과 도구 실행에는 LLM 에이전트를 활용했습니다. 다만 결과 숫자는 LLM이 판단한 것이 아니라, 실제 어셈블러와 역어셈블러 네 개가 낸 출력을 대조 코드가 판정한 것입니다. 같은 입력과 같은 도구 버전이면 항상 같은 결과가 나옵니다.
제 역할은 판정 기준을 정하는 것이었습니다. SDM 원문을 최우선으로 하고, 도구끼리는 비교하지 않으며, 근거가 부족하면 미확인으로 둔다는 기준입니다. 원문이 애매한 경우는 PDF를 직접 확인해 결정했습니다.
검증 장치로는 회귀 테스트 156개, 실행마다 도구 버전과 코드 해시를 남기는 기록, 그리고 원문 쪽수와 소스 행으로 된 근거 파일을 두었습니다.
실제로 검토 과정에서 근거가 없는 버그 후보 하나를 철회했고, 발표 준비 중에는 생성 규칙의 오류 세 건을 찾아 고친 뒤 전체를 다시 돌렸습니다.

## 5. 생성 코드 ①: `m2_generate.py`의 흐름

**슬라이드** (왼쪽: 세로 흐름 6단계, 오른쪽: "값 규칙" 상자. 글자 22pt 허용)

입력: SDM 표 행(`isa_db.csv`) + 원문 검토(오퍼랜드 기호·폭) + 행 상태

1. `load_rows()` — 표 행마다 오퍼랜드 기호 목록을 붙임 (예: `r/m32`, `imm8`)
2. `apply_row_spelling()` — 표 이름만으로 행을 고를 수 없는 경우 철자 지정 (`retf`, `movabs` 등)
3. `operand_choices()` — 기호 하나 → 넣을 값 후보 (`r/m32` → 레지스터 / 메모리)
4. `build_row_cases()` — 후보를 조합해 변형 생성 (주소 3형태, 즉시값 최대, 마스크, 반올림)
5. 예상 결과 — 64비트 칸 Valid → reach, 아니면 reject, 같은 문장이면 시험 불가 (`mark_aliases()`)
6. 저장 — `cases.csv`(케이스마다 근거 칸) + `cases.s`

**값 규칙** (`case_rules.py` 표에서만 고름, 파랑 상자)
- 레지스터: SDM 목록 순서, 행 안에서 겹치지 않게
- 메모리: `[rax]` · `[rax+rbx*4+0x10]` · `[rip+0x10]`
- 즉시값: 그 폭에만 맞는 값 + 부호 있는 최대값

**대본**
테스트케이스는 m2_generate.py가 만듭니다. 입력은 1단계에서 뽑은 SDM 표 행과, 원문을 다시 확인해 정리한 오퍼랜드 기호입니다.
먼저 표 행마다 오퍼랜드 기호 목록을 붙입니다. 표 이름만으로는 도구가 그 행을 고를 수 없는 경우, 예를 들어 먼 복귀 RET는 retf처럼 도구 철자를 따로 지정합니다.
다음으로 기호 하나마다 넣을 값의 후보를 만듭니다. r/m32라면 32비트 레지스터 하나와 32비트 메모리 하나입니다. 이 후보들을 조합해서 메모리 주소 세 가지 형태, 즉시값 최대값, 마스크, 반올림 변형을 만듭니다.
예상 결과는 매뉴얼의 64비트 모드 칸으로 정하고, 마지막에 케이스마다 어떤 원문 기호를 근거로 그 값을 골랐는지 함께 저장합니다.
중요한 점은 값을 임의로 고르지 않는다는 것입니다. 레지스터, 주소, 즉시값은 모두 case_rules.py의 정해진 표에서만 고르고, 각 규칙에 원문 쪽수를 적어 두었습니다.

## 6. 생성 코드 ②: 표 한 행 → 케이스

**슬라이드** (위: SDM 행 한 줄 / 가운데: 생성 결과 표 / 아래: 한 줄 설명. 표 22pt 허용)

SDM 행: `83 /0 ib   ADD r/m32, imm8   Valid`

| 변형 | 생성된 입력 | 근거 |
|---|---|---|
| base | `add ecx, 0x12` | r/m32 → 레지스터 (SYM028), imm8 (SYM030) |
| alt1 | `add dword ptr [rax], 0x12` | r/m32 → 메모리 (SYM037) |
| alt1:sib | `add dword ptr [rax+rbx*4+0x10], 0x12` | 주소 형태: SIB |
| alt1:rip | `add dword ptr [rip+0x10], 0x12` | 주소 형태: RIP 상대 |
| imm_max | `add ecx, 0x7f` | imm8 부호 있는 최대값 |

- `eax`가 아니라 `ecx`인 이유: 같은 표의 고정 레지스터(`ADD EAX, imm32`)와 주소용 `rax`·`rbx`는 피함
- 예상 결과: 64비트 Valid → 5개 모두 reach · `VADDPS` 같은 AVX-512 행은 마스크·브로드캐스트·반올림까지 16개

**대본**
실제 예를 보겠습니다. SDM 표의 ADD r/m32, imm8 한 행에서 케이스 5개가 나옵니다.
r/m32 자리에는 레지스터 형식 하나와 메모리 형식이 들어가고, 메모리는 기본 주소, SIB 주소, RIP 상대 주소 세 가지로 만듭니다. 즉시값은 8비트에만 맞는 값과 부호 있는 최대값 두 가지입니다.
레지스터로 eax가 아니라 ecx를 쓴 것은 의도한 것입니다. 같은 ADD 표에 EAX를 고정으로 쓰는 다른 행이 있어서, 그 행과 문장이 겹치지 않게 피했습니다.
오른쪽 근거 칸처럼 모든 값에 원문 기호 번호가 붙어 있어서, 왜 이 입력을 만들었는지 케이스마다 추적할 수 있습니다. AVX-512 명령은 같은 방식으로 마스크, 브로드캐스트, 반올림 변형까지 만들어 한 행에 16개 정도가 됩니다.

## 9. 결과 그룹 ②: SDM과 다른 결과

**슬라이드** (같은 형식)

**다른 유효 형식 선택** — GNU 25 · clang 181
- 같은 동작의 다른 opcode 선택 (MOV·ADD 등 방향, 즉시값 형식) (clang 130)
- MOVQ·VMOVQ: 같은 이름의 opcode가 둘 (GNU 24 · clang 28)
- REX.W 없이도 같은 동작이라 생략 (LAR·SMSW 등) (clang 10)
- PEXTRW 레지스터 형식을 다른 opcode 행으로 (clang 9)
- PUSH·POP 1바이트 형식 선택 (clang 4)
- IRET: 매뉴얼이 허용한 동의어 (GNU 1)

**표기·철자 차이** — GNU 4 · clang 44
- `{er}` 위치: 매뉴얼 순서(GPR 뒤)를 clang은 거부, GPR 앞만 받음 (clang 40)
- PUSH imm16·XBEGIN rel16: clang에 16비트 철자 없음 (clang 3)
- SYSEXIT·SYSRET: 두 형식 이름이 같아 구별 불가 (GNU 2)
- LAR·LSL REX.W 형식: 문법으로 지정 불가 (GNU 2 · clang 1)

**도구 미지원** — GNU 26 · clang 40
- MPX: GNU 2.44부터 기본 꺼짐, clang 미지원 (GNU 26 · clang 26)
- MOVSXD 16·32비트: LLVM은 역어셈블만 지원 (clang 8)
- INT1·UD0·UDB: LLVM 미구현 (clang 6)

**매뉴얼 ≠ 실제 동작** — GNU 3 · clang 3
- MOV Sreg, r/m64: 표는 64비트 메모리, 도구·CPU는 2바이트 (GNU 3 · clang 3)

**버그 후보** (빨강) — GNU 0 · clang 28
- CLRSSBSY·RSTORSSP `qword` 거부 (6) · call·jmp `word ptr` 조립 (6) · AVX512PF Intel 문법 거부 (16)

- 이 장은 글자 20pt 허용. 두 단 배치 가능(왼쪽: 다른 형식·철자, 오른쪽: 미지원·매뉴얼·버그 후보)

**대본**
다음은 SDM과 다르게 나온 그룹입니다. 첫째, 같은 문장에 맞는 유효 형식이 여럿이라 도구가 다른 쪽을 고른 경우로, 가장 많습니다.
둘째는 표기 차이입니다. 매뉴얼에서 두 형식의 이름이 같아 구별할 수 없거나, 도구마다 철자 관례가 다른 경우입니다.
셋째는 도구가 일부러 지원하지 않는 경우입니다. GNU는 2.44부터 MPX를 기본으로 끄고, LLVM은 MOVSXD 32비트 형식을 역어셈블에서만 지원합니다.
넷째는 매뉴얼 표기와 실제 CPU 동작이 다른 경우입니다. 마지막으로 원인을 설명할 수 없는 버그 후보가 clang에 28개 남았습니다.

## 10. 버그 후보 ①: CLRSSBSY · RSTORSSP (clang 6개)

**슬라이드** (위: SDM 표기 / 가운데: 관측 표 / 아래: 원인 한 줄. 글자 24pt 허용)

**SDM 표기**
- 표: `F3 0F AE /6  CLRSSBSY m64` (Vol.2A 3-150)
- 기호: "m64 — A memory quadword operand" · 동작: 8바이트 정렬 토큰

| 입력 | GNU | clang |
|---|---|---|
| `qword ptr` (64비트) | 통과 (파랑) | **거부** (빨강) |
| `dword ptr` (32비트) | 거부 | 통과 |

**원인**: LLVM `X86InstrSystem.td`가 피연산자를 `i32mem`(32비트)으로 정의 · 보고됨 #95232

이미지(작게): `captures/1_clrssbsy.png`

**대본**
첫 번째 후보입니다. 매뉴얼 표는 CLRSSBSY의 피연산자를 m64로 적고, 총론은 m64를 쿼드워드, 즉 64비트 메모리라고 정의합니다. 동작 설명도 8바이트로 정렬된 토큰을 다룹니다. Intel의 공식 인코더 XED도 64비트입니다.
그런데 clang은 64비트 표기를 거부하고 32비트 표기를 받습니다. GNU는 정확히 반대입니다. LLVM 소스를 보면 이 명령의 피연산자가 32비트 메모리로 정의되어 있습니다.
바이트 자체는 같아서 잘못된 기계어를 만들지는 않지만, 크기 검사와 출력이 매뉴얼과 반대입니다. 2024년에 보고됐고 아직 해결되지 않았습니다.

## 11. 버그 후보 ②: call · jmp `word ptr [m]` (clang 6개)

**슬라이드** (같은 배치)

**SDM 표기**
- `FF /2  CALL r/m16` **N.E.** (64비트에서 인코딩 불가) · `FF /3  CALL m16:16 · m16:32` Valid
- 먼 호출 메모리 = "4-byte or 6-byte far address" → 2바이트 형식 없음

| 입력 | GNU | clang |
|---|---|---|
| `call word ptr [rax]` | **거부** (정답, 파랑) | `FF 18` 6바이트 먼 호출 (빨강) |

**원인**: LLVM 먼 호출 정의가 크기를 검사하지 않음(`opaquemem`) · 보고됨 #88516

이미지(작게): `captures/6_call_word.png`

**대본**
두 번째 후보입니다. 매뉴얼 표에서 16비트 간접 호출은 N.E., 즉 64비트 모드에서 인코딩할 수 없는 형식입니다. 먼 호출의 메모리는 4바이트 또는 6바이트라고 설명합니다. 그러니 2바이트 메모리에 맞는 형식이 없고, 거부가 정답입니다. GNU는 거부합니다.
clang은 크기 표기를 무시하고 6바이트를 읽는 먼 호출로 조립합니다. LLVM의 먼 호출 정의가 메모리 크기를 검사하지 않기 때문입니다.
다만 word ptr 같은 크기 표기는 매뉴얼이 정한 문법이 아니라 도구 관례라서, 세 후보 중 근거가 가장 약합니다. 2024년에 보고됐고 미해결입니다.

## 12. 버그 후보 ③: AVX512PF (clang 16개)

**슬라이드** (같은 배치)

**SDM 표기**
- 표: `VGATHERPF0DPS vm32z {k1}` (Vol.2D 8-12)
- Vol.1 §15.6.1.2: 마스크는 Intel 문법에서 **첫 피연산자 뒤**

| 입력 | GNU | clang |
|---|---|---|
| `vgatherpf0dps [rax+zmm0] {k1}` | 통과 (파랑) | **거부** (빨강) |

**대본**
세 번째 후보는 AVX512PF 16개입니다. 매뉴얼 표는 마스크를 메모리 뒤에 적고, Vol.1은 Intel 문법에서 마스크를 첫 피연산자 뒤에 쓴다고 직접 설명합니다. XED와 GNU도 같은 순서입니다.
clang은 이 입력을 거부하고, 자신이 출력한 문장을 다시 넣어도 거부합니다. AT&T 문법으로는 조립되므로 지원을 끊은 것도 아닙니다.
매뉴얼 해석과 상관없이 도구 안에서 모순이라, 세 후보 중 근거가 가장 확실합니다. 보고된 기록은 찾지 못했고, 원인과 기여 방향은 마지막 장에서 자세히 말씀드리겠습니다.

## 15. AVX512PF 이슈 상세: 어디가 문제이고, 기여할 수 있나

**슬라이드** (이 장만 글자 20pt 허용, 표 18pt 허용. 위: 명령 설명 / 가운데: 비교 표 / 아래 두 단: LLVM 위치 · 기여)

**어떤 명령인가**
- Xeon Phi(KNL·KNM) 전용 "흩어진 주소 미리 읽기" 힌트 (16개 명령)
- 인덱스 벡터(zmm)의 주소 최대 16곳을 캐시로 미리 가져옴, 마스크 `k1` 비트가 1인 원소만
- PF0 → L1, PF1 → L2 · gather는 읽기용, scatter는 쓰기용(독점 상태로 가져옴)

**어디가 충돌하나** — `{k1}`의 위치

| 기준 | 표기 | 입력 예 | 결과 |
|---|---|---|---|
| Intel 매뉴얼 | `VGATHERPF0DPS vm32z {k1}` | `vgatherpf0dps [rax+zmm0] {k1}` | clang **실패** (빨강) |
| LLVM Intel 정의 | `{${mask}}, $src` | `vgatherpf0dps {k1}, dword ptr [rax+zmm0]` | clang **실패** (빨강) |
| LLVM AT&T 정의 | `$src {${mask}}` | `vgatherpf0dps (%rax,%zmm0) {%k1}` | clang **성공** (파랑) |

- 매뉴얼대로 쓰면 명령 정의와 충돌, LLVM 정의대로 쓰면 입력 처리기와 충돌 → Intel 문법으로는 쓸 방법이 없음

**LLVM의 어느 부분인가** (왼쪽 단)
- `X86InstrAVX512.td` 10438행: `{$src {${mask}}|{${mask}}, $src}` (`|` 왼쪽 AT&T, 오른쪽 Intel)
- `X86AsmParser`: 맨 앞 `{k1}`을 반올림 장식으로 읽다가 거부

**기여할 수 있나** (오른쪽 단)
- 보고 기록 없음 (PR #122051 본문에 "unsure how to change" 언급만)
- 수정안: Intel 정의를 `$src {${mask}}`로 1줄 변경 + Intel 문법 테스트 추가 (현재 AT&T 테스트만 있음)
- 남은 일: 패치 빌드·테스트 통과 확인 → 이슈·PR 제출

이미지(작게, 오른쪽 아래): `images/sdm-8-12.png`, `images/sdm-vol1-page-394.png`
링크(작은 글씨, 맨 아래):
- LLVM 소스: https://github.com/llvm/llvm-project/blob/0d261d1ca552c95a8f007e061c787ac7132fbcbc/llvm/lib/Target/X86/X86InstrAVX512.td#L10438
- Godbolt Intel 실패: https://godbolt.org/z/of1hfozfa · AT&T 성공: https://godbolt.org/z/Goo8f9jvd

**대본**
마지막으로 AVX512PF 문제를 자세히 보겠습니다. AVX512PF는 Xeon Phi 전용 명령으로, 인덱스 벡터가 가리키는 흩어진 주소들을 캐시로 미리 가져오는 힌트입니다. 마스크 k1의 비트가 1인 원소만 가져오고, PF0은 L1, PF1은 L2 캐시로 가져옵니다.
문제는 k1의 위치입니다. 매뉴얼은 메모리 주소 뒤에 쓰라고 하고, 그대로 쓰면 clang이 실패합니다. LLVM의 Intel 문법 정의는 반대로 마스크를 앞에 두는데, 그 순서로 써도 LLVM의 입력 처리기가 맨 앞 k1을 반올림 장식으로 읽다가 거부합니다. AT&T 정의는 매뉴얼과 같은 순서라서 성공합니다. 그래서 지금은 Intel 문법으로 이 명령을 쓸 방법이 없습니다.
원인은 LLVM 소스 X86InstrAVX512.td 10438행의 Intel 쪽 문법 문자열입니다. 이 부분을 AT&T처럼 메모리 뒤에 마스크를 두도록 한 줄 바꾸고, 지금은 없는 Intel 문법 테스트를 추가하면 됩니다.
보고된 이슈는 찾지 못했고, 다른 패치 설명에 "어떻게 고칠지 모르겠다"는 언급만 있었습니다. 그래서 오픈소스 기여로 이어갈 수 있다고 봅니다. 다만 수정한 LLVM을 빌드해 테스트를 통과하는지는 아직 확인하지 않았고, 이것이 다음 단계입니다. 감사합니다.

## 부록: 질문 대비 메모 (슬라이드 아님)

- 자체 오류 3건: ① `call/jmp dword ptr [m]`은 m16:16(4바이트 먼 포인터, 유효)과 같은 문법이라 거부 시험에서 뺌, ② VMOVW·VPBROADCASTB/W의 r64 입력은 원문 근거가 약해 제거(Intel XED도 32비트만), ③ `data16` 철자는 GNU 전용이라 clang 결과를 "도달 불가(등록)"로 분류.
- 분류 세부(GNU/clang): 다른 표현 = 별칭 행 24/181 + IRET 동의어 1/0 + SYSEXIT·SYSRET 2/0 + LAR·LSL 2/1 + PUSH·XBEGIN 0/3 + ER/SAE 반올림 위치 0/40. 미지원 = MPX 26/26 + INT1·UD0·UDB 0/6 + MOVSXD r16·r32 0/8. 버그 후보 = CLRSSBSY·RSTORSSP 6 + call·jmp word 6 + AVX512PF 16.
- "SDM은 어셈블러 문법 명세가 아니지 않나?" → AVX512PF는 Vol.1이 Intel 문법 위치를 직접 말하고, 무엇보다 LLVM이 자기 출력을 못 읽는다. 먼 호출 `PTR` 표기는 SDM에 없어서 근거가 약하다고 인정.
- CPU 실행 관측(선택): 2,082건 실행, 정상 종료 1,973.
- 정확한 버전: `GNU assembler (GNU Binutils) 2.47.20260726`, `clang version 23.1.3 (llvm-project 0d261d1ca552)`, 커널 6.18.33.2-microsoft-standard-WSL2, Python 3.12.3. Binutils는 소스 빌드, LLVM은 공식 Linux-X64 바이너리(`~/opt`).
- 실행 옵션: GNU as `--64 -mintel64`, clang `-target x86_64-linux-gnu`, 둘 다 `.intel_syntax noprefix`. 이 CPU에는 AVX-512가 없어 CPU 관측은 지원 기능에 한정.
- 자세한 근거: `docs/PRESENTATION_REVIEW_2026-10-13.md`, `docs/AVX512PF_OPINION_2026-10-13.md`.
