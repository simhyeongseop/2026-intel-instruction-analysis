## 2. 지난 미팅에서 받은 과제

**슬라이드**
- Intel 소스 → 조립 → **AT&T로 역어셈블** → 다시 조립 → 다시 역어셈블
- 원래 바이트·어셈블리와 같은지 비교
- Intel과 AT&T 경로의 결과는 같아야 한다 → 다른 케이스를 추린다
- 목적: 어셈블러(GAS, clang)·역어셈블러(objdump, llvm-mc) 결함 탐지

**대본**
지난번에 교수님께서 화이트보드에 그려 주신 흐름입니다. Intel 구문으로 조립한 바이너리를 objdump로 AT&T 구문으로 풀고, 그걸 다시 조립해서 다시 풀었을 때 처음과 같은지 보라고 하셨습니다.
이론상 Intel로 돌든 AT&T로 돌든 결과 바이너리는 같아야 하니까, 다른 곳이 나오면 어셈블러나 역어셈블러 중 하나의 결함 후보가 됩니다. 매뉴얼에만 있는 특수 문법이 제대로 처리되는지도 함께 보는 것이 목적이었습니다.

## 3. 아키텍처

**슬라이드** (위: 기존 파이프라인 한 줄, 아래: 새 5단계 확대 그림. 그림은 상자와 화살표만)

기존: ① 추출 → ② 생성 → ③ 조립 판정(SDM 대 as·clang) → ④ 역어셈블 대조(SDM 대 objdump·llvm-mc) → **⑤ 왕복 대조(새로 추가)**

5단계 그림:

```
                 ┌─ AT&T 텍스트 ─ 다시 조립 → Ba ─ 다시 풀기 ─┐
 3단계 바이트 B0 ─┤                                            ├─ B0·Ba·Bi 비교
                 └─ Intel 텍스트 ─ 다시 조립 → Bi ─ 다시 풀기 ─┘
```

- 바이트가 다르면 다시 풀어서 **명령도 다른지** 확인

**대본**
기존 파이프라인은 SDM에서 표를 뽑아 케이스를 만들고, 3단계에서 조립 결과를, 4단계에서 역어셈블 결과를 각각 SDM과 대조했습니다. 이번에 그 뒤에 5단계를 붙였습니다.
5단계의 시작점은 3단계에서 어셈블러가 만든 바이트 B0입니다. 이걸 AT&T와 Intel 두 가지로 풀고, 각각 다시 조립해서 Ba, Bi를 얻습니다. 화이트보드 그림의 AT&T 경로에 Intel 경로를 하나 더 붙여서 두 경로를 비교할 수 있게 했습니다.
바이트가 다를 때는 다시 풀어서 명령까지 다른지 봅니다. 같은 명령을 다른 바이트로 쓰는 경우가 있기 때문입니다.

## 5. 비교 조건

**슬라이드**
- 같은 계열끼리만 왕복 (GNU ↔ GNU, LLVM ↔ LLVM, 도구끼리 비교하지 않음)
- objdump를 as와 같은 **Intel64 해석**으로 맞춤 (`-M intel64`)
- 분기 상대 주소 104건은 비교에서 제외 (대상 주소가 바뀌기 때문)

| 판정 | 뜻 |
|---|---|
| 바이트 같음 | B0 = 재조립 바이트 |
| 바이트 다름·명령 같음 | 같은 명령의 다른 인코딩 |
| 바이트 다름·명령 다름 | 다른 명령이 됨 → **검토 대상** |
| 재조립 거부 | 자기 출력을 받지 못함 → **검토 대상** |

**대본**
비교 조건은 세 가지입니다. 첫째, 같은 계열 도구끼리만 왕복합니다. GNU 출력을 clang에 넣는 식의 교차는 하지 않았습니다. 지금까지처럼 도구끼리 비교하지 않는다는 원칙을 지키고, 한 도구가 자기 출력을 다시 받는지를 봅니다.
둘째, objdump 설정을 맞췄습니다. as는 Intel 해석(-mintel64)으로 조립하는데 objdump 기본값은 AMD 해석이어서, MOVSXD 16비트 4건이 설정 차이만으로 거부로 나왔습니다. 실험 기준이 Intel SDM이라서 objdump도 Intel64로 맞추고 다시 돌렸습니다.
셋째, 레이블로 가는 분기 104건은 자리만 다른 바이트라서 비교에서 뺐습니다.
판정은 네 가지입니다. 아래 두 줄, 다른 명령이 되거나 자기 출력을 거부하는 경우가 검토 대상입니다.

## 7. "바이트 다름·명령 같음"은 오류가 아님

**슬라이드** (표 24pt 허용)

| 예 | 처음 B0 | 출력 | 재조립 |
|---|---|---|---|
| MOV r8, r/m8 (GNU) | `8a ca` | `mov cl,dl` | `88 d1` |
| VPSLLW (LLVM) | `62 f1 75 08 f1 c2` (EVEX) | `vpsllw xmm0, xmm1, xmm2` | `c5 f1 f1 c2` (VEX) |

- 같은 명령을 쓰는 인코딩이 둘 이상 → 어셈블러는 하나만 고름
- LLVM 1,935건 중 1,932건이 EVEX → 더 짧은 VEX

**대본**
같은 명령을 바이트로 쓰는 방법이 여러 개인 경우입니다. MOV는 방향 비트에 따라 8A와 88 두 가지로 같은 명령을 쓸 수 있고, 어셈블러는 그중 하나만 고릅니다.
LLVM에서 이 그룹이 많은 이유는 AVX-512 명령입니다. 마스크도 512비트 레지스터도 안 쓰는 EVEX 명령은 VEX로도 쓸 수 있는데, llvm-mc 출력에는 EVEX라는 표시가 없어서 다시 조립하면 더 짧은 VEX가 나옵니다. 1,935건 중 1,932건이 이 경우입니다.
명령은 같으므로 오류로 보지 않고 별도 그룹으로 분리해 두었습니다.

## 8. 주목할 결과 ①: LLVM 먼 간접 CALL·JMP

**슬라이드**
- 캡처: `captures/7_far_call.png`
- `ff 18`(먼 호출) → Intel 출력 `call [rax]` → 재조립 `ff 10`(**가까운 호출**) (빨강)
- AT&T 출력 `lcalll *(%rax)`는 그대로 `ff 18` (파랑)
- Intel 경로 25건 중 21건, LLVM 23.1.3과 최신 main 모두 재현

**대본**
첫 번째 주목할 결과입니다. ff 18은 메모리에 있는 세그먼트와 주소로 가는 먼 호출입니다. llvm-mc는 이걸 Intel 구문으로 call [rax]라고 출력합니다. 그런데 이 출력을 다시 조립하면 ff 10, 즉 가까운 호출이 나옵니다. 명령의 뜻이 바뀝니다.
같은 바이트를 AT&T로 출력하면 lcalll이라고 먼 호출임을 표시하고, 다시 조립해도 그대로 돌아옵니다. 그래서 Intel 경로만 틀리고 AT&T 경로는 맞습니다.
먼 CALL·JMP 형식 6개 중 5개에서 이렇게 다른 바이트가 나왔고, 최신 LLVM main을 직접 빌드해서 확인해도 그대로였습니다.

## 9. 주목할 결과 ②: GNU LSS·LFS·LGS (64비트)

**슬라이드**
- 캡처: `captures/8_lss_fword.png`
- `48 0f b2 08` → Intel 출력 `lss rcx,FWORD PTR [rax]` → as가 **거부** (빨강)
- AT&T 출력 `lss (%rax),%rcx`는 그대로 조립 (파랑)
- LSS·LFS·LGS × 주소 3형태 = 9건, Intel 경로에서만

**대본**
두 번째는 GNU 쪽입니다. 64비트 레지스터로 세그먼트 포인터를 읽는 LSS 명령입니다. 메모리 크기는 2바이트 세그먼트에 8바이트 주소, 총 10바이트입니다.
objdump는 이걸 FWORD, 6바이트로 출력합니다. 같은 GNU의 as는 64비트 레지스터에 FWORD를 받지 않아서 자기 도구의 출력을 거부합니다. AT&T 출력은 크기 표기가 없어서 문제없이 돌아옵니다. LFS, LGS도 똑같고, 주소 형태 3개씩 해서 9건입니다.

## 10. 왜 이렇게 나왔나

**슬라이드**
- **LLVM 먼 호출**: Intel 출력에 먼/가까운 구분이 없음 → 다시 조립하면 가까운 호출 (빨강)
- **GNU LSS**: objdump가 REX.W(64비트 크기)를 보지 않고 FWORD로 출력 (빨강)
- 오류 아님: LAR·LSL·MOV Sreg 8건은 GAS가 일부러 REX.W를 뺌(`NoRex64`) (파랑)
- 미조사: LLVM POPFW·PUSHFW·PUSH imm16(Intel 4건), MOV Sreg r16(AT&T 1건)

**대본**
원인을 정리하겠습니다. LLVM 먼 호출은 Intel 출력이 먼 호출과 가까운 호출을 같은 철자로 쓰기 때문입니다. 크기 표기도 없어서 다시 조립할 때 정보가 사라지고, 어셈블러는 가까운 호출로 읽습니다. AT&T는 lcall이라는 다른 이름을 쓰니까 문제가 없습니다.
GNU LSS는 objdump 소스에서 이 오퍼랜드의 크기를 정할 때 64비트 표시인 REX.W를 보지 않아서, 10바이트여야 할 것을 6바이트 FWORD로 출력합니다. 이 두 건은 오류로 판단했습니다.
GNU에서 다른 명령이 된 8건은 LAR, LSL, 세그먼트 MOV입니다. GNU 명령표에 REX.W를 내지 않는다고 명시돼 있어서 의도된 설계로 보고 오류에서 뺐습니다. 아래 5건은 아직 조사하지 않았습니다.

## 부록: 질문 대비 메모 (슬라이드 아님)

- **21건 구성**: 먼 CALL·JMP 형식에서 나온 B0 `ff 18`·`ff 28`류 18건(주소 3형태, 3단계에서 `word ptr`·`dword ptr`로 쓴 입력도 clang이 같은 바이트를 만듦) + `66 ff 18`, `48 ff 18`, `66 ff 28` 3건.
- **먼 호출 기존 보고**: #88516·#95232(어셈블러가 크기 표기 무시), #48335(`lcall tbyte ptr` REX.W 누락)는 어셈블러 쪽. 역어셈블 Intel 출력의 왕복 문제는 GitHub 검색에서 찾지 못함(중복 부재를 단정하지 않음).
- **LSS 근거**: binutils `i386-dis.c`의 `Mp`(f_mode)가 REX.W를 보지 않음(2.47과 master 0aeb555 동일). as -mintel64는 `tbyte ptr`만 받음.
- **MOVSXD 4건**: objdump 기본(AMD64)이면 `movsxd cx,edx`. `-M intel64`로 맞춘 뒤 4·5단계 재실행에서 이 4건만 바뀜(재조립 거부 → 바이트 같음).
- **GNU 명령 같음 187건**: 레거시 59건(방향 비트, MOV 등), EVEX→VEX 40건, VEX→VEX 18건, EVEX→EVEX 70건(그중 14건은 objdump 출력에 `{evex}` 표기). LLVM은 1,932건이 EVEX→VEX, 레거시 3건.
